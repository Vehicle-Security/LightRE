# minilua：LightRE 的 ARM64 混淆测试样本

现在优先使用大函数版 `large/deliverable/minilua`，用于测试真实解释器经过强控制流混淆后的分析复杂度：

```text
读取 /work2/LightRE/docs/USAGE.md，分析 /work2/LightRE/samples/minilua/large/deliverable/minilua，workspace 使用 /work2/minilua-analysis，然后打开结果供我查看。
```

在页面按 RVA 搜索 **`0x4d58`（luaV_execute，40,589 条指令、162,356 字节）**。这是单个函数的真实机器指令数，基线为 1,099 条；按每页 200 条读取需要 203 页。LightRE 若只识别到部分指令，应与保存的完整参考比较，不能把识别结果当作函数实际大小。

方法是只对解释器主循环拆分基本块（`split_num=5`），再平坦化两轮；通过多层状态分派放大真实控制流，没有通过 NOP 或复制函数凑长度。Clang `-Os` 加紧凑链接后，二进制为 **264,728 字节**，加演示脚本总共 **265,007 字节**，仍满足原 300 KB 预算。10 组差分用例、40 次实际执行通过。它提供与商业样本相近的大函数规模，具体保护机制并不等同。

重建：`bash scripts/build.sh --large`。参考和证据在 [大函数报告](large/reports/verification.md)、[大函数 manifest](large/manifest.json)。原来的小函数版 `deliverable/minilua` 保留，便于先定位基础问题；其目标为 `luaH_get @ 0x85a0`、`luaH_set @ 0x8ea8`。

详细入口、对照文件和复测命令见 [使用说明](BUILD.md)。以下保留第一阶段的小样本构建需求；大函数版是其中允许的独立“基本块拆分 + 平坦化”实验，混淆目标为 `luaV_execute`。

## 一、项目目标

构建一个供逆向工具测试使用的 **Linux AArch64 ELF 可执行文件**，基于 LuaJIT 仓库中的 `src/host/minilua.c`。

目标样本需要：

1. 包含真实、较复杂的程序逻辑，而不是简单口令校验程序。
2. 对少量核心函数实施**控制流平坦化**，增加 CFG 恢复和反编译难度。
3. 保持程序可正常运行。
4. **最终交付目录全部普通文件的总大小不超过 300,000 字节。**
5. 提供完整构建过程、参考文件、验证结果，方便定位逆向工具的问题。

本项目用于测试我开发的逆向工具，不需要加壳、反调试、隐蔽执行或其他规避机制。

## 二、目标平台与构建要求

### 必须满足

- 架构：AArch64，64 位、小端。
- 格式：Linux ELF 可执行文件。
- 链接：动态链接。
- 启用 PIE。
- 最终目标文件去除普通符号表和调试信息。
- 默认使用 `-O2`；若超出大小预算，可以尝试 `-Os`。
- 不静态链接 libc。
- 不使用 UPX 或其他压缩壳。

目标程序应能在以下至少一种环境中实际运行：

- 原生 Linux AArch64；
- `qemu-aarch64` 配合匹配的 AArch64 sysroot。

如果采用 QEMU，记录实际使用的命令和 sysroot 路径。

### 预算口径

300,000 字节限制只针对 `deliverable/` 目录内的文件，不包含：

- 源码；
- 编译器；
- 系统动态库；
- sysroot；
- 未剥离参考文件；
- 构建日志；
- 反汇编；
- 测试报告。

因此，交付目录不是自包含运行环境，运行依赖应在外部报告中明确说明。

## 三、源码选择和版本固定

使用以下项目中的 minilua：

- 仓库：[https://github.com/LuaJIT/LuaJIT](https://github.com/LuaJIT/LuaJIT)
- 文件：`src/host/minilua.c`

要求：

1. 固定到具体 commit，不使用浮动分支作为最终构建输入。
2. 记录 commit、下载 URL 和原始文件 SHA-256。
3. 保留原始源码和许可证声明。
4. 所有修改保存为补丁，便于审查。
5. 不删除解释器功能来人为缩小体积，除非先报告原因并获得确认。

注意：minilua 是精简 Lua 解释器，不是 LuaJIT JIT 引擎。测试脚本必须以其实际支持的能力为准。

## 四、控制流混淆要求

### 混淆范围

第一阶段只对以下函数实施控制流平坦化：

- `luaH_get`
- `luaH_set`

如果固定版本中的函数名称或组织方式不同，先确认对应实现并在报告中说明。

第一阶段不要混淆 `luaV_execute`，也不要全程序平坦化，以免体积膨胀或失去可诊断性。

### 不启用的特性

第一阶段禁止启用：

- 伪控制流 / bogus control flow；
- 字符串加密；
- 指令替换；
- 全局基本块拆分；
- 反调试；
- 自修改代码；
- 加壳。

后续可增加“基本块拆分 + 平坦化”的独立实验版本，但不得替代主交付样本。

### 工具选择

优先使用支持 AArch64、支持函数级选择的 LLVM 控制流混淆实现。

Agent 必须先检查工具的真实实现和文档，确认：

- 支持的 LLVM 版本；
- AArch64 后端是否可用；
- 函数级选择方式；
- pass 的启用参数；
- pass 的执行阶段；
- 与所用优化等级的兼容性。

**不得假设普通 Clang 支持 `-mllvm -fla`，也不得混用不同 OLLVM 分支的参数。**

固定混淆器仓库、commit、构建参数和工具版本。

如果函数属性、内联或优化导致混淆未生效，应调整构建方式。必要时可对目标函数添加 `noinline`，但基线版本也必须应用同样的非混淆修改，以保证可比性。

如果找不到可用的混淆器，应先报告阻碍和替代方案，不得悄悄交付普通二进制。

## 五、需要构建的版本

### 1. 基线版本

- 无控制流混淆；
- 与混淆版使用同一个编译器构建、相同优化等级和链接参数；
- 同样的源码，除混淆开关或混淆标记外保持一致；
- 保留未剥离版本和对应的 stripped 版本；
- 用于差分测试与 CFG 对照。

### 2. 混淆版本

- 仅对指定函数做控制流平坦化；
- 保留未剥离版本；
- 从该未剥离文件复制并 strip，生成最终交付文件。

**不得重新编译一个“带符号参考版本”来代替原文件的参考版本。** 未剥离参考文件和最终文件必须来自同一次链接。

所有参考文件均放在交付目录之外。

## 七、功能测试要求

必须真实运行基线版和混淆版，覆盖：

1. 整数、浮点运算及条件分支；
2. 数字键、字符串键的表读写；
3. 表扩容、缺失键查询；
4. 闭包及捕获变量修改；
5. 递归调用；
6. 可变参数；
7. 元表和 `__index`；
8. `pcall` 及错误路径；
9. 大量临时对象分配，触发自动 GC；
10. 语法错误输入。

测试应确定性运行，避免依赖：

- `pairs` 的输出顺序；
- 指针地址字符串；
- 时间；
- 未固定种子的随机数；
- 宿主环境差异。

差分检查包括：

- 标准输出；
- 标准错误；
- 退出码；
- 是否超时。

设置合理超时。若错误消息包含可执行文件路径，应做最小且明确的路径归一化，不能通过大范围忽略输出掩盖差异。

若某项能力不受 minilua 支持，记录原因并提供合理替代测试，不能直接跳过而不说明。

## 八、混淆效果验证

不能仅凭编译成功、文件变大或输出正常判定混淆成功。

对两个目标函数分别提供基线和混淆版的反汇编或 CFG 证据，说明：

- 是否引入状态变量或等价状态表示；
- 是否引入中央分派逻辑；
- 原始基本块之间的直接控制流是否被状态分派替代；
- 状态更新后如何回到分派逻辑；
- 优化是否消除了平坦化。

尽量记录：

- 函数代码大小；
- 基本块数量；
- 间接跳转数量；
- 分派结构。

若没有可靠 CFG 工具，可以用带地址的反汇编片段进行人工说明。无法可靠测量的指标标记为“未测量”，不得编造。

如果目标函数被内联或优化变形，必须解释实际分析位置；必要时使用双方一致的 `noinline` 配置重新构建。

## 九、大小控制

计算 `deliverable/` 下所有普通文件的实际字节数总和，要求：

text

```text
total_size <= 300000
```

不以压缩包大小或 `du` 的磁盘块占用作为验收依据。

若超预算，按以下顺序处理：

1. 确认已 strip，交付目录没有调试文件或多余文件；
2. 使用 `-Os`；
3. 检查 section GC 等链接配置；
4. 检查混淆器是否误混淆了全部函数。

如果仍超预算，不得静默取消某个目标函数的混淆。应报告实际大小和可选方案，等待确认。
