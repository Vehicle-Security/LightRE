## 开发基线

以下约定作为开始开发时的统一依据，后文展开其细节；长期能力按需加入，不要求一次实现。

| 对象 | 当前约定 |
| --- | --- |
| LightRE | 工具代码、Skill 说明和工具依赖，与分析产物分开 |
| workspace | 用户可见、位置和名称动态决定的外部分析根目录，可组织同一类 VM 的多个 SO 版本 |
| SO 分析目录 | workspace 下的 `<名称>-<短SHA>/`，固定对应一份原始 SO，独立保存 SQLite、源码、知识、证据、运行和任务 |
| Web | 可选的结果浏览与反馈入口，每次读取一个 SO 的持久分析结果，不现场调用分析工具；长期自动化不依赖 UI |
| Goal Loop | 规划中的长期自动化支柱：Python 循环调用 codex exec，验证当前工程，未通过时自动续跑 |
| SQLite | 每 SO 一份，维护实体映射、版本选择及结构化状态；源码变化通过发布入口同步更新索引 |
| harness | workspace 内按兼容情况共享代码，各 SO 保存自己的参数、JNI 假设、运行证据与验证结论 |
| 公共知识 | 从多版本分析中有意提炼，保存在 workspace 顶层 Markdown，引用原始依据，指导新版本调查 |
| 开发节奏 | 每次交付一个可运行、可验证的小增量，用户体验后再确定下一步 |

“SO 版本”指内容不同的原始文件；“源码版本”指对同一 SO 的某个还原结果的多次修改。不同 SO 的同一 RVA、源码 ID 或验证状态不合并。下文的路径和名字均为示例，不要求预先创建整棵目录。

**V0.1 基础版本的人工验收反馈已落实。** 本版本先由分析入口调用 Rizin 保存函数和完整汇编，再让 Web 只读 workspace 和 SQLite；最终功能、界面与验证记录见 [V0.1 milestone](milestones/v0.1/DELIVERY.md)。后续范围见 [小步实现计划](IMPLEMENTATION_PLAN.md)，用法见 [V0.1 使用说明](milestones/v0.1/USAGE.md)。差分闭环是后续逐步达到的目标。

V0.1 每个 Web 进程固定浏览启动时指定的一份 SO 结果。更换目标由 Skill 重启服务，页面不提供工作区切换。

当前 V0.2 在此基础上增加自动初次还原、候选文件展示与修改建议续做，已于 2026-11-01 通过用户人工验收，见 [V0.2 交付记录](milestones/v0.2/DELIVERY.md)。当前按原始函数 RVA 定位 `source/src/` 模块中的候选片段，SQLite 维护可重建的最小路径索引。分析入口由 Ghidra 自身枚举函数，统一导出范围、汇编、分组与参考，再由 LightRE 整理模块初稿；后台默认 8 批并发调用 Codex CLI；初稿不算 LLM 已处理。当前函数上下文统一到 knowledge.md，由 Markdown 库按 RVA 章节读写，不再一函数一知识文件。分析与评论使用工作区内的持久任务队列，评论优先，同级 FIFO，批次之间让位，支持暂停/继续和单任务取消；详见 [队列设计](milestones/v0.2/TASK_QUEUE.md)。尚不实现下文的完整发布版本、函数合并/拆分或动态验证。

下一小步按 [V0.31 计划](milestones/v0.31/PLAN.md)，先用已知源码的简单 Android ARM64 测试 SO 建立 unidbg 纯 native harness、Python 调用、Run 保存与重放，再接入修复 harness 的最小任务循环。模型只修改授权 harness，测试库、固定预期和检查器保持不变。[V0.3](milestones/v0.3/PLAN.md) 是后续完整差分与语义修复的总体方案；真实 VM、DG JNI、minilua Android SO、候选构建分别后移，不作为 V0.31 前置。

源码和知识的实际目录以 [V0.2 使用说明](milestones/v0.2/USAGE.md)为准；下文的 `versions/`、`exports/` 和 `runs/` 是长期布局示例，不表示当前已实现。

## 目标与边界

LightRE 配合 Codex 使用，提供简单的本地 Python API、功能说明、持久资料和一个轻量函数浏览器。核心目标是面向强混淆 ARM64 SO，以函数或明确的逻辑入口为单位，让 LLM 持续还原 VM/OLLVM 逻辑，借助 unidbg 运行原实现与候选实现并差分比较，逐步恢复原机器码语义。

最终产物是一份简单可读、可编译、可独立执行并可继续维护的等价源码工程，供后续二次开发。长期执行以 [Goal Loop](GOAL_LOOP.md) 为支柱：用户提交一次目标，Python 外层循环调用 `codex exec`，验证当前源码、构建和运行结果，将未完成项反馈给下一轮，满足交付条件后才结束。源码整理、命名、类型、接口与代码优化属于同一目标的工作范围；函数候选和原 VM 的运行观察是中间材料。该工程级循环尚未实现，不等同于当前批量候选任务。

Web 保持现有的辅助浏览与可选反馈定位，不继续以扩充 UI 为主线。调查、源码修改、执行比较、恢复和最终交付均须可在不启动 Web、无人逐轮确认的条件下完成。

完整源码恢复闭环是：**读取知识、Evidence 与 Unknown → 分析并重写候选 → 构建候选 → unidbg 双边运行与比较 → 保存反例和新证据 → 修正并重跑累计用例。** Harness 尚不可运行时先补齐初始化与环境；暂时没有候选时仍可执行原实现收集观察。该闭环逐步建立；V0.31 的最小链路是 **运行固定测试 SO → 保存真实错误 → exec 修复 harness → 原样保存返回 → 外层重新运行核对**，不要求实现完整证据库、源码版本发布或 VM 检查点。

Codex 主导推理、实验和多轮优化，根据功能说明编写普通 Python 脚本组合调用 LightRE API。LightRE 负责执行基础操作、外部验证、持久化与续跑决策，默认直接调用 CLI，无需 SDK 或独立 Agent 平台。Agent 可以更换或退出，新会话能从工作区重建理解。内部允许分析 CFG 和基本块；Web 可查看函数和伪代码、提交评论，页面代码保持只读。

文件和 SQLite 是持久数据来源。知识在进程内按 RVA 复用，文件变化时重新加载，每批完成后原子保存一次，内容未变不重写；不依赖退出时保存。其他批次内临时状态、上下文裁剪和下一步决策由 Agent 处理。首版不做独立 Agent 平台、通用工具适配框架、MCP、任务队列服务、缓存层或 bundle 导入导出。

VM/OLLVM 的具体调查方法由 Agent 按问题选择，不预建通用 VM 解码器、去混淆流水线或策略引擎。需要的专用脚本随实验保存；先让观察和推断可积累、实验可重跑。能执行原 VM 只是运行观察，恢复其中被虚拟化的逻辑仍需进一步分析，结论保留验证范围。

通用性首先体现在可复用的实验、状态准备、比较和资料保存能力；不同保护方案的调查方法由 Agent 随样本积累。目标是逐步扩大已恢复范围，不承诺有限测试可证明任意 ARM64 SO 的全部行为。运行环境不支持、关键依赖缺失或路径尚未探索时保留 Unknown，不能据此宣布全部还原。

## 主要入口：目录 + Agent Skill

用户以目录和自然语言目标发起任务，例如：

> 用 LightRE 打开 ../dg-samples/dC6BDAE，展示函数和汇编。

LightRE 的产品入口设计为 Agent Skill，说明 API 能做什么、输入输出和持久化约定。Agent 根据任务理解目录、确定目标 SO，编写脚本调用 API 并开展调查；不要求用户手动枚举依赖或拼接完整参数。底层工具命令仍由 Python 函数直接调用，Web 的路径导入保留为辅助入口。

输入目录是相关材料的范围，不等于一个 binary。Agent 根据用户目标、文件格式、ELF 依赖和目录内容区分主要 SO、其他版本、依赖库及配套资源。目标唯一时直接选用；无法区分多个候选时才询问。同一类 VM 的多个版本可以放在同一个 workspace，每份 SO 有独立目录、SQLite 与全部版本知识；共享 harness，并逐步提炼有依据和适用范围的公共知识。

目录、分析目标和已识别资料足以启动调查，不强制用户先写输入配置。LightRE 根据 Agent 请求创建或恢复外部 workspace；用户可指定位置，也可把新版本加入已有 workspace。目标与来源位置按 binary 登记，输入角色及未知关系记入其知识文档，运行实际采用的文件按原规则固定并记录。后续发现新依赖时补充资料，不必重新导入整个目录或预建通用输入描述语言。

用户请求浏览时，工作区创建或恢复后启动或复用 Web，页面可访问就打开并返回地址，不等待全量分析完成。当前 Skill 的分析入口自动通过非交互 Codex 批量生成候选，Web 评论加入同一调度队列。规划中的完整还原目标由 Python 外层 Goal Loop 统一推进，无需 Web 或重复聊天；任务中的 Codex 不递归启动其他 Codex 来代替外层执行器。浏览器无法在容器中启动时，浏览请求仍提供服务地址。

Skill 和 API 文档随实际功能一起完善。V0.1 即提供最小聊天入口：用户说“用 LightRE 打开这个目录，展示函数和汇编”，Agent 识别目标、调用读取能力、启动或复用 Web 并返回实际地址，用户无需填写 Python 启动命令、监听地址或端口。开发验证可让 Agent 显式读取项目内的 Skill 说明，不要求先做全局安装；完整工作区等能力按后续增量加入。本文只约定方案，不表示入口已经实现。

## 最小 API 职责

API 指可从项目源码直接导入的 Python 函数，开发测试不要求安装 Skill 或启动 HTTP 服务。功能说明只需给出参数、返回值、文件位置、失败含义和短示例，Agent 自行组合调用。

以下是逐步形成的长期职责，不是 V0.31 的接口清单。V0.31 只增加启动 Java harness、提取结果、保存/重放 Run 和驱动最小任务循环所需的普通函数，复用已有工作区能力；不先实现完整 Evidence、Context 或源码发布 API，也不增加 Web 功能。

- 定位或创建外部 workspace，打开其中选定 SO 的分析目录，读取函数汇编、当前代码、知识和关联证据。
- 运行指定 harness 和输入，保存实际配置、源码及原始输出，返回 Run 和产物位置。
- 登记有用的 Evidence，并按函数或 Run 查询。
- 保存函数候选与更新最佳版本，启动或定位 Web。

调查脚本可以筛选数据、解码字节码或设置实验观测点，需要复现的脚本放入 runs。结构化数据更新通过 API 完成，沿用地址身份、版本和文件发布约定，避免每个脚本自行修改 SQLite 形成不同格式。Web 直接复用同一套函数；不维护另一套业务实现。具体函数随闭环需要实现，不先铺满所有分析工具的 API。

## 工作区与数据

**Workspace 是用户可见的分析根目录，可以研究同一类 VM 的多个 SO 版本。每份 SO 的分析目录仍独立保存 SQLite、源码、Knowledge、Evidence、Unknown、Run、任务和验收结论。** 保留原来每 SO 一套数据的结构，不新增统一数据库或 binary_id。Workspace 只在外层组织这些目录、共享 harness 和提炼出的公共知识。

LightRE 仓库只放工具源码、文档、Skill 说明及工具依赖；workspace 由 LightRE 按聊天请求动态创建或打开。**位置和目录名由用户或当前上下文决定。** 未指定时使用 `<Skill调用目录>/<名称>-analysis`。调用目录是开始执行 Skill 时的 cwd，须在切到工具目录前记录；相对输入及 workspace 路径先据此解析为绝对路径，调用脚本时显式传入 `--workspace`。不得混进 LightRE 或样本 Git 仓库；调用目录位于这些仓库内时选择相应仓库外的可见位置，并说明原因。创建前说明拟用路径，创建后返回完整路径和 Web 地址；不要求用户再次确认常规目录创建，不写入隐藏缓存。扫描输入时跳过生成目录，避免再次导入原始副本或候选 SO。

例如用户可说“用 LightRE 分析这些 VM 版本，workspace 放在 `./vm-analysis`”。相对路径按 Skill 调用目录解析，该路径仅是例子。也可直接给出已有 workspace，加入新的 SO 版本；创建多个项目或放在其他仓库外位置均可。Web 改显示名称只改元数据，不移动目录。

每个 SO 分析目录内有自己的 `index.sqlite`，完整 SHA256 在该库元数据中保存一份权威值。选定该目录就确定原始 SO，实体不重复存哈希；同内容在本 workspace 内复用原分析目录，内容不同建立新目录，旧结果不覆盖。各数据库之间不联表，不把不同版本的同 RVA、源码 ID 或 Evidence ID 当成同一个实体。

每份 SO 使用 `<名称>-<短SHA>/` 作为可读分析目录。名称默认取样本来源目录名，可指定；无来源目录时用 SO 文件名去掉 `.so`。短 SHA 默认 4 位，重名且内容不同则延长新目录的前缀，已有目录不动，不能只凭短 SHA 判断身份。原始副本不变，候选和导出不改变 SO 身份。

来源资源目录按 binary 记录；例如 `bytecode/` 下的 `.bin` 是配套输入，不能直接当作确定的 VM 结构或原生依赖。已确认 DG 使用现有 4 份 `.bin`，minilua 使用 `.lua` 用例并由自身解析器生成内部字节码；真实 VM 加载入口与前态仍需适配，不以开发生成器或外部 luac 加载器为前置。导入不递归复制整个输入目录，只保留目标 SO；实际使用的依赖和输入按路径与内容依据固定。共享资源可引用同一文件，避免重复复制。

```text
<LightRE工具目录>/                 # 工具代码及工具依赖，与调用目录无关

<用户选择的可见 workspace>/
  harnesses/default/               # 多版本兼容的运行代码
    pom.xml
    src/main/java/
    README.md                     # 运行接口、使用方法及逐版本兼容记录
  knowledge/overview.md           # 按需创建，逐步提炼出的公共 VM 知识
  dC6BDAE-d65f/
    binary/original.so
    index.sqlite                  # 只管理当前 SO
    harness.json                  # 共享 harness 引用与当前 SO 参数
    dependencies/
    ghidra/                       # 按需创建
    knowledge.md                  # 当前版本的知识；函数使用 RVA 二级标题
    versions/f001/v001.c
    exports/<export_id>/
    runs/<run_id>/
    tasks/<task_id>/
      task.md
      state.json
  other-version-abcd/              # 独立一套目录和 SQLite，按需创建
    index.sqlite
    ...
```

目标是通过多个版本的逆向总结公共 VM 知识，加快后续版本分析。各 SO 的知识、证据和验证状态始终独立，公共知识是有意提炼的结果，不能直接把某个版本的全部知识当作其他版本事实。入口 RVA、opcode 对应、字节码布局、JNI 细节等具体结论仍归属实际版本；可共享的设计规律、识别方法和实验经验写入顶层知识，注明来源、适用条件及已知例外。共享 harness 只表示复用可兼容运行代码，不表示逻辑或验证结论相同。

只维护一份权威内容：

| 内容 | 保存位置 |
| --- | --- |
| 当前 SO 的 SHA256、显示名称、来源目录、格式版本、revision | 该 SO 的 SQLite 元数据 |
| 原始地址实体、源码实体索引、引用、当前最佳版本 | 该 SO 的 SQLite |
| 代码正文、声明名称、源码 ID 与来源注释 | versions 文件；SQLite 只索引身份、名称、路径、来源与检查状态 |
| 用于二次开发的源码交付物 | exports 文件，从选定版本生成的独立快照 |
| 当前 SO 的知识正文 | 该 SO 分析目录中的 knowledge.md，函数以 RVA 二级标题定位 |
| 提炼出的公共 VM 知识 | workspace 顶层 knowledge Markdown，附来源与适用范围 |
| 证据摘要、条件、来源、地址关联、有效状态 | SQLite |
| 当前可编辑的共享 harness 与 JNI 实现 | workspace/harnesses/<name> 文件 |
| SO 使用的 harness 及版本差异参数 | 该 SO 分析目录的 harness.json，不在 SQLite 重复维护 |
| 依赖 SO、APK 和资源 | 按需保存的文件，按相对路径与内容哈希引用 |
| 恢复源码编译的候选 SO 与构建依据 | 当前 SO 的 `runs/<build_run_id>/build/libcandidate.so`、`build.log` 与 `build.json`，其他验证 Run 引用实际路径及产物哈希 |
| 原始 trace、当次 harness 副本、输入、运行输出与检查点 | 当前 SO 的 runs 文件；该库登记运行状态及路径 |
| Web 评论与任务要求 | tasks/<id>/task.md；提交时快照在 reviewed.c |
| 任务处理状态与检查点 | tasks/<id>/state.json；模型输出与日志同目录，不在 SQLite 复制 |

SQLite 保存映射索引和少量结构化权威状态，不保存可独立修改的知识或代码正文。源码索引可从已登记文件重建，SO 元数据、版本选择及证据登记仍由该库保存，不能把整个数据库当作可随意删除的缓存。各 SO 的配置与数据库文件引用相对其分析目录解析，`../harnesses/default` 可指向同一共享工程；运行入口显式传入 SO 分析目录，不依赖当前 shell 目录。备份时停止写入，整体复制外部 workspace 及其引用的固定资源，无需复制 LightRE 工具仓库。

不预建 Markdown 索引库、Context 快照库、跨版本数据库或任务数据库。SQLite 按实际操作增加必要表；公共知识直接读 Markdown，不额外同步到各 SO 的数据库。任务由轻量入口调用 Codex，不增加队列服务。Markdown 无需重新索引或文件监听，整理长知识前保留旧文件，原始 trace 不做 compact。

## 快速打开与按需分析

当前默认由 Ghidra 统一静态分析来源：

1. 已有所选 SO 的完整产物时，直接读取函数列表、汇编和代码，打开页面不启动分析工具。
2. 新样本由 Ghidra Headless 自身枚举函数，统一导出名称、范围、指令、参考伪代码和分组，保留项目；不导入 Rizin 的目标列表。
3. 单函数反编译失败保留目录项、汇编和错误，Agent 可继续分析；整体自动分析超时或导出失败不发布不完整目录。
4. LLM 在模块初稿上批量改进，默认 8 批并发；后台复用已保存的 Ghidra 结果。
5. Rizin 作为可选查询工具，不参与默认函数清单生成。工具推断的边界仍需证据修正；显式重导出时保留未变候选，变化条目的旧代码归档并记录关联。

工具通过命令或脚本直接调用。需要的参数、工具版本、退出状态和持久产物记入 Run。耗时调用可设超时、可取消；单函数失败不阻断其他函数。Ghidra 对同一项目的写入先串行执行。

Agent 生成的脚本和 Web 使用同一组 Python API；Agent 可以直接导入项目源码调用，不必启动 Web 或通过 HTTP 写入。Web 负责展示结果、保存评论任务及触发 Codex 执行。CLI 如有需要只作薄包装，Rizin 和 Ghidra 各自只接入当前需要的命令。

## 地址、命名与函数版本

### RVA 是什么

RVA（Relative Virtual Address，相对虚拟地址）表示相对模块映像基准的偏移。本项目用它标识同一 SO 内的函数、全局变量和指令位置：

```text
运行时虚拟地址 VA = 对应模块基址 BASE + RVA

例如 BASE = 0x70000000，函数 RVA = 0x1c07c
则函数运行时地址为 0x7001c07c。
```

ASLR 或模拟器加载位置改变时，BASE 和 VA 可以变化，同一份 SO 的 RVA 不变。不同 SO 可能有相同 RVA，因此地址始终在所属 SO 分析目录内解释；跨 SO 或对外引用时附带原始 SO 的完整 SHA256。

RVA 不是文件中的字节偏移。对 ELF，以最低 `PT_LOAD` 的 `p_vaddr` 为本项目的静态映像基准，并记录工具的地址调整；BASE 指该静态基准在本次运行中的对应地址。常见 SO 的静态基准是 0，此时 ELF 虚拟地址通常与 RVA 相同；非零基准或工具重定位时先换算。Rizin/Ghidra 地址不能不加判断直接当 RVA，读取原始文件还需按 ELF 段布局转换文件偏移。

### 稳定身份与命名

选定 SO 分析目录就确定原始 binary，原始地址实体只用“类型 + RVA”唯一定位。它与还原后的源码声明分开：源码文件保存实际声明名称，当前 SO 的 SQLite 索引其名称与来源，便于查询和导航。例如：

```text
(function, 0x1640c) -> cleanup_tagged_slots
(global,   0x5a844) -> runtime_flags
```

API 调用、版本、证据关联和评论任务明确所属 SO 分析目录，不给每个实体增加 SHA256 字段，也不在每次查询时重新计算文件哈希。只有跨 SO 引用或独立导出时，才从该 SO 的 SQLite 元数据统一附上 SHA256；这是来源标识，不是另一份可编辑的身份记录。

源码直接使用可读名称，尚未理解时可使用 `fcn_0001640c` 等临时名称。稳定身份保存在声明注释中，不要求 C 标识符本身携带地址。现有 `functions.name` 保持原始分析名称，当前源码名称从实际声明派生；名称仅供显示、搜索及作用域内的符号解析，不作关系键。重命名由 Agent 修改声明和相关引用，生成新版本并更新索引。历史版本保留其真实名称，Web 不用当前名称替换历史文本。先由 Agent 处理选定代码范围，不预建通用重构引擎。

当前一对一函数链路继续直接按原始入口 RVA 关联。默认源码注释 ID 由后端按 RVA 生成，已有 ID 在改名和搬文件时保留；只有确实新增无独立原始入口的声明时，才由后端另行分配不变 ID，不虚构 RVA。局部变量与参数由 Agent 在函数内直接修改，不分配稳定 ID、不建映射表；普通文本替换不能当作安全变量重命名。跨函数改名必须同时修改定义、声明及相关引用，单 RVA 保存接口尚不足以保证工程一致性。实施边界和检查结果见 [函数身份、命名与调用导航](SOURCE_NAVIGATION.md#实现前确认的身份规则)。

直接调用按地址关联，函数内分支不算 callee。间接调用保存调用点及有证据的候选目标，未解析时保留间接表达式。动态目标根据所属模块和加载布局转换地址；模块外目标先保存模块/符号或目标记录，不要求建设多模块联合分析模型。TLS、GOT 及指向对象按需要区分，不提前建设完整类型系统。

LLM 可以重写整个函数。每次保存一个新版本，记录来源、输入依据、检查状态和未解决问题。最新候选与当前最佳版本分开。Agent 提交时明确是否替换最佳版本并给出理由，不建设自动评分框架；更短、更好看或功能相似不足以证明语义正确。

先完整写入不可变代码版本文件，再通过统一发布入口用 SQLite 事务登记版本、选择结果和更新索引及 revision；完整流程见下文“SQLite 索引与更新”。读取者只展示已登记的文件。中断留下未登记文件可以以后清理，不增加文件与数据库的分布式事务。

### 同一份源码与声明注释

**Web 的源码正文直接读取项目中保存的版本文件，编译也读取同一版本文件。** 页面允许隐藏保留的机器定位及生产者注释，并增加语法高亮、行号和可点击定位；代码正文与普通注释保持文件原文，不替换名称、改写函数或维护页面专用代码。界面显示正在读取的文件和版本；工具原始伪代码与 Agent 还原代码分别标明来源。隐藏机器注释不改变原文件、构建输入或评论绑定的原始片段摘要。

每个还原函数、全局变量有一个 SO 内稳定的源码 ID，例如 `f001`、`g001`，创建后不随改名、移动文件而改变。其全局身份是“原始 binary SHA256 + 源码 ID”；不同 SO 的同名源码 ID 不合并。原始地址身份仍用类型和 RVA，两者通过来源注释关联。无需给局部变量建立全局地址表。

工作目录内的源码不重复写 binary 文件名和原始 SO 的 SHA256。函数采用独占一行的固定标记与 JSON 对象，明确记录稳定 ID 和来源 RVA，并用相同 ID 的结束标记界定正文：

```c
// @lightre.begin {"v":1,"id":"f001","origins":["0x1640c","0x17000"]}
void cleanup_tagged_slots(void) {
    /* ... */
}
// @lightre.end {"id":"f001"}
```

`v` 是标记格式版本；`origins` 是原始函数 RVA 数组，允许空数组。重命名和移动保留 ID，合并、拆分使用多对多来源关联。独立导出通过工程来源说明附上原始 SO 身份，不改写已选源码正文。全局声明的来源扩展须明确实体类型，不用裸地址混淆函数与全局变量；局部变量不加入来源索引。多来源及空来源为后续能力，当前索引仍要求每段对应一个原始 RVA。

完整格式、词法扫描、错误处理、字节范围索引和刷新协议以 [Web 源码定位与结构化标记](SOURCE_NAVIGATION.md) 为准。固定前缀识别记录，标准 JSON 解析字段，begin/end 状态检查配对；读取时跳过字符串等词法上下文，无需用跨函数正则或花括号计数提取正文。结构化格式提高可校验性，性能主要来自复用解析结果和按索引读取，不承诺仅替换正则即可提速。

声明注释是代码身份和来源映射的依据，SQLite 保存可重建的查询索引，不维护另一份可独立修改的来源正文。一个文件可以含多个声明，后续索引按源码 ID 定位文件版本及字节范围，行号仅作阅读位置。来源关联不代表已证明原始代码均被覆盖；详细证据、派生依据、逻辑入口及未解决项仍在 Evidence/Knowledge。当前已实现 JSON 标记、稳定 ID 保留、词法解析、旧格式兼容及显式无损迁移；索引仍为单 RVA 到模块路径，多对多和统一发布 revision 尚未实现。

### VM 的逻辑边界

一个原生解释器函数可能执行多个字节码入口，一个恢复出的功能也可能跨越多个原生函数。因此原生 RVA 是追溯锚点，不强制对应一个最终源码函数。需要时在知识、版本关联和 Run 参数中补充字节码资源身份、入口偏移及影响含义的执行上下文，区分不同逻辑入口；字节码偏移不能冒充原生 RVA。

原始地址与还原源码之间按多对多来源关联处理，不把 RVA 作为还原函数的唯一主键：

| 情况 | 源码身份与来源 |
| --- | --- |
| 一对一还原 | 一个源码 ID 关联一个原始函数 RVA |
| 多函数合并 | 合并结果使用一个源码 ID，`origins` 列出多个原始函数 RVA |
| 一个函数拆分 | 各结果使用不同源码 ID，可以关联同一个原始函数 RVA，并按需注明指令范围或逻辑入口 |
| 抽取公共 helper | 分配独立源码 ID，通过 `derived_from` 注明来源源码实体，不虚构原生函数入口 |

例如合并可记录 `{"v":1,"id":"f003","origins":["0x1640c","0x17000"],"replaces":["f001","f002"]}`；拆分结果 `f004`、`f005` 都可以来自 `function@0x1c07c`，但用各自已确定的字节码入口或指令范围进一步说明。以上关系限定同一 binary，派生 ID 在该 binary 内不复用；跨版本的相似性先记录在知识中，不直接合并代码身份。

改名或移动文件保留 ID；真正合并、拆分时为新逻辑声明分配新 ID，旧 ID 和历史版本继续可追溯，记录被替代关系，不把旧实体静默改成另一个含义。一次涉及多个声明的发布用已有 SQLite 事务和 revision 一起选择新结果，避免 Web 显示新调用者和旧 callee 的混合组合。一个原始函数在 Web 可定位多个还原结果，一个合并结果也可从多个原始地址进入，展示其完整定义，不重复生成源码副本。

最终导出保留原生地址、逻辑入口与还原函数的映射。内部仍可分析 handler、指令片段和基本块，Web 无需增加 CFG 或基本块面板，也不预建通用 VM 类型系统。这些能力随实际合并或拆分需求逐步加入，不扩展首版函数与汇编浏览的范围。

## SQLite 索引与更新

### 唯一身份约定

所有 API、注释、证据、调用关系和 Web 导航遵循同一套稳定身份。原始函数在独立 SQLite 中直接用整数 RVA 作键，原始全局变量由表或显式类型与 RVA 区分；不要求增加第二套字符串主键，也不使用名称或数据库行号作业务身份。选定 SO 后无需增加 binary_id 字段。以下带类型前缀的写法用于解释或跨类型引用，不要求在每张表中重复存储：

| 实体 | binary 内带类型引用示例 | 身份依据 |
| --- | --- | --- |
| 原始函数 | `native:function:0x1640c` | 类型和规范化 RVA，名称不参与身份 |
| 原始全局变量 | `native:global:0x5a844` | 类型和规范化 RVA |
| 还原函数 | `source:f001` | 声明注释中的稳定源码 ID |
| 还原全局变量 | `source:g001` | 声明注释中的稳定源码 ID |

`source:f001` 与注释中的 `f001` 是同一身份的完整写法和简写，不是两个不同编号。跨 SO 使用原始 SO 的 SHA256 加带类型的稳定身份；需要定位具体代码时再带版本 ID，行号和名称都不作唯一键。源码 ID 由后端创建/发布入口在当前 SO 内分配并检查唯一性，不复用已登记过的 ID；现阶段默认按入口 RVA 生成，后续无入口声明才另行分配。索引重建不得重新编号。原始 RVA 按统一数值格式规范化，不能因大小写或补零生成重复实体。局部变量与参数不分配稳定身份，也不加入全局索引。

原始实体与源码实体间的来源映射是多对多关系，不能强行压成一个地址主键。合并只让旧源码结果退出当前选择，不删除原始 SO 中仍存在的函数实体。

发布还须保持地址定位的连续性：后端从旧发布记录核对来源继承，每个此前已关联源码的原始 RVA 在新发布中仍能找到可读取的当前声明。多个原始函数合并后，所有原始 RVA 均指向同一份新源码；再次改名、移动或合并也不丢来源。LLM 漏写来源或破坏身份时拒绝发布并保留旧结果，而不是清空映射或按名字猜测。完整约束及合并示例见 [地址定位约束](SOURCE_NAVIGATION.md#地址定位必须保持的约束)；当前一对一实现尚不能保证合并场景。

### SQLite 具体保存什么

- **映射索引**：原始实体、当前源码实体、名称、文件路径、文件哈希、版本、标记及正文字节范围、原始来源和实体间引用。Web 通过索引定位文件，再直接读正文，不逐次扫描所有源码。
- **版本与选择记录**：已登记的不可变文件、候选版本、当前选定版本集与 revision。最新候选不自动替换最佳结果。
- **结构化状态**：当前 SO 元数据、Run 登记、Evidence 及关联、与代码版本绑定的验证范围和结论。代码、知识、trace 和任务正文继续放文件，不与其他 SO 的状态混合。

具体表按需加入，初期不预建完整 schema。唯一约束覆盖实体 ID、同一源码实体的版本和当前唯一选择，关系使用外键且每个连接启用 `PRAGMA foreign_keys = ON`；其他 SO 的实体不直接作为本库外键。历史名称与引用按其源码版本索引，不能用一个无版本的名称字段覆盖全部历史。

源码索引是派生数据，版本选择和验证结果是权威记录，两者在同一个数据库中也有清楚边界。重建前者不清空后者，索引修复不能改变最佳版本或把未验证代码变成已通过。

### 修改与发布：替换当前索引，不只追加

首个需要源码索引的版本使用简单方式：**每次改变当前 SO 的选定版本集，就从该版本集完整重建当前源码索引，在其独立 SQLite 的一个事务内替换。** 不触碰其他版本的目录和数据库。初期不做复杂的逐行增量更新；相同文件内容哈希的解析结果可在进程内复用，变动文件重新解析，最终仍完整事务替换当前索引。

1. Agent 修改草稿，经同一发布入口写成新的不可变版本文件；多文件修改一起提交。现有已登记文件保持不变。
2. 解析声明注释、实际名称、来源和可确定的引用，计算文件哈希，准备登记结果。必需声明 ID 缺失或重复、标记损坏、格式版本不支持、来源不属于当前 SO 等情况拒绝登记；不以一次不完整扫描清空正常索引。
3. 保存候选时只登记该版本及其索引，不改变当前最佳选择。选择新最佳版本时，发布入口串行读取当前 revision，构造完整的目标版本集，检查其中声明 ID、命名作用域和引用是否一致。尚不能解析的间接或外部引用保留为显式 unknown/外部目标，不能伪造绑定。
4. 开启 SQLite 事务，登记新版本、更新选择，删除旧的“当前源码索引及其派生来源/引用”，插入完整目标集合并递增当前 SO 的 revision，一次提交。任何校验或写入失败都回滚到旧选择与索引。每次 Web 读取在同一数据库读事务中取得 revision、索引和文件版本，再读取对应不可变文件。

这不是删除整个数据库重建。原始函数索引、候选和历史版本、证据、Run 与验证结果不随当前源码索引一起清空。原始静态清单需修正时，完整扫描结果替换其声明范围内的当前索引，片段分析仅更新明确范围；不能把尚未扫描到或尚未还原的函数误删。

例如删除或拆分一个声明时，旧声明及其旧名称、文件位置、来源和调用边会退出当前源码索引；新的集合完整写入，不依靠 Agent 记得逐条删旧行。仍在当前版本中调用已移除声明的代码必须一起修正，或明确保留未解析引用及未完成状态，不能静默丢掉这条调用。

### 历史、异常修改与恢复

保留的历史不是残余数据：被版本、Run、Evidence 或任务引用的旧实体和文件仍可回溯，但历史查询与当前查询分开，不能作为当前函数返回。未登记的临时文件或没有任何保留记录引用的孤立索引可在显式整理时清除；不为消除“旧数据”删除仍有验证价值的反例或历史来源。

支持的源码更新方式是“编辑草稿 → 发布新版本 → 同步索引”。发布中断时，数据库仍指向完整旧文件；先写好的未登记新文件不会被 Web 当作当前结果。无需文件系统与 SQLite 的分布式事务。

不依赖常驻文件监听保证一致性。启动、显式同步及 Web 读取目标源码时检查登记哈希；如果已登记文件被外部原地修改或删除，明确显示不同步/文件缺失，不继续展示该文件的旧名称索引、旧位置或通过结论。变动作为新版本重新发布，或恢复原文件后再读取；不能把新内容冒充原已验证版本。校验只读取实际需要的文件，不每次全量重新索引所有资料。

提供一个显式校验/重建源码索引的操作：从登记的选定版本集校验文件，重建派生表；失败时保留原选择并报告具体文件或引用问题。先用“改名、移除声明、合并、拆分、发布中断、外部改文件”这些小例子逐项验收，再考虑增加索引功能。

## 还原源码与二次开发

先选择一个函数或明确的功能范围，恢复其真实运算、分支、数据结构和副作用，逐步扩大覆盖范围。VM 还原应把已解析的虚拟指令行为组织成可读逻辑，消除仅为混淆服务的分派与状态跳转；必要的算法状态和数据仍须保留。单纯翻译原解释器、继续用原 SO 代算，或只复现少数输入的输出，都不足以完成该范围的源码还原。

分析中允许保存不完整伪代码；最终交付的范围需具备明确的函数接口、必要类型、全局状态及外部依赖，能按说明构建并独立调用。语言先根据二次开发需要选择一种，不建设多语言生成框架。JNI 和环境接口尽量与恢复出的核心逻辑分开；未还原调用或占位实现明确标出，依赖这些占位的路径保留未验证状态。

持续用 unidbg 执行原函数，并在相同输入、初始状态和可比环境下运行还原实现，比较返回值、输出内存及相关外部副作用。差异反馈给 Agent 继续调查。记录测试范围及未覆盖问题；人工修改建议与运行验证结果分别保存，不能用“看起来合理”代替执行比较。

### 函数级差分的最小约定

总体架构采用 ARM64 + unidbg：原始 SO 与恢复源码编译的候选 SO 在两个独立实例中运行同一逻辑用例，提取声明的输出和副作用，再将差异反馈给 Agent。两边共享状态构造规则，各自持有独立内存与对象。

```text
原始 SO → unidbg A → 原始观察
                              → 比较 → 保存反例 → Agent 修正
候选源码 → ARM64 SO → unidbg B → 候选观察
```

构建记录、输入/状态契约、入口与 ABI、结果规范化、函数及分段粒度统一维护在 [动态差分设计](DIFFERENTIAL_EXECUTION.md)，本文不另列一份比较协议。harness 的目录与共享规则见 [下文](#agent-生成与共享-unidbg-harness)。minilua 的 Android SO 适配及 `.lua` 输入方案同样见差分专题；当前统一路线仍待实现。

### 累计回归与组合验证

新反例保留为后续回归，验证结果绑定实际候选和依赖；从单函数逐步扩大到调用链与连续调用。用例内容留存、组合版本记录、环境假设和结论分类见 [累计回归约定](DIFFERENTIAL_EXECUTION.md#累计回归与组合验证)。任务如何据此继续或停止由 [Goal Loop](GOAL_LOOP.md) 规定。

### 源码导出

交付时由 Agent 将选定代码版本组织成普通源码工程，放到新的 exports/<export_id>，提供最小构建/运行说明，并记录原函数地址、所用版本和验证依据。选中的源码文件按原文复制，保持 Web 审阅、实际构建和交付文件中的名称、代码及身份注释一致；额外构建文件和接口胶水单独提供，不在导出时暗中重写代码。跨函数引用和依赖一起处理，避免只有互相缺失的函数片段。单函数交付可以很小，无需重建整个 SO 才有可用成果。

导出物是独立交付快照，不与分析版本双向同步。每次导出写新目录，不覆盖已用于二次开发的代码。用户从该快照继续开发，LightRE 保留产生它的分析版本和 Evidence。先由普通脚本完成组织与导出，不预建发布平台。

## 证据、知识与可恢复 Context

本节是完整恢复流程的数据职责。V0.31 首先按 [逐轮记录约定](GOAL_LOOP.md#最小落地先完整保存返回正文) 保存原始 prompt、完整最终返回、进程信息和实际检查；下一轮引用这些记录及当前文件即可。自动提取记忆、知识归纳与专用检索 API 后续按实际需要加入，不是 harness 或最小 loop 的依赖。

三者是资料用途，不是三个服务：

- Evidence：工具观察到什么、在什么条件下观察到、原始产物在哪里。
- Knowledge：Agent 或人工的当前理解、假设、冲突和下一步，用 Markdown 表达。
- Context：当前任务需要读取的代码、知识和证据，由 API 读取返回，Agent 再选择使用。

### 证据

每份 SO 有独立证据库，一条记录可以关联该 SO 的多个函数、全局变量或调用点。例如“调用点 A 调用了函数 B”只保存一次，双方都能查到。公共知识引用其他版本证据时使用“SO 身份 + Evidence ID / Run 路径”，不复制成当前 SO 的观察，也不继承其验证结论。

最少字段为 `id、run_id、kind、summary、data、artifact_ref、status`。类型区分 static、concrete、symbolic、forced、differential。输入、环境、初始状态和干预记录可引用所属 Run，不重复复制。

只把需要继续使用的观察登记为证据，不把每条指令或每个 trace 事件写进 SQLite。大量事件保留在运行文件，用路径及行号、偏移或事件范围定位，需要时分段读取。不建设通用 trace 查询引擎。

原始产物保留。证据错误时更新其有效状态和更正说明，原始观察仍可追查；不做追加式事件账本。工具观察与 LLM 假设分开，支持和反驳当前结论的依据都保留。

有后续价值的失败实验也登记 Evidence，不能只保存成功结果。例如缺少 JNI 实现导致中断、间接调用未能解析、候选实现出现差分不一致。Run 保留实际输入、初始化与环境配置、脚本、错误和已有输出；Evidence 摘要指出观察到的失败及其条件。差分反例保留两边实现版本、可重放输入和输出差异，后续候选将其作为回归用例。工具执行失败只说明本次实验未完成，不能推断目标逻辑不存在或不可达。

### 知识与 Context

函数 Markdown 简要记录当前理解、证据 ID、假设与冲突、下一步、人工备注。人工直接用编辑器修改，Agent 更新时保留人工备注。仅在长文需要整理时归档，不给每次编辑建立版本或结论依赖图。

### 跨版本提炼公共知识

Workspace 顶层 `knowledge/overview.md` 是逐步积累的公共 VM 知识，不是各版本知识的合并副本。先在每份 SO 中保留具体观察，再由 Agent 对比多个版本，提炼可复用的设计规律、识别线索、实验方法和已知变体。一个版本产生的通用猜测也可保留，但必须标为假设，不能提前当作已确认共性。

公共条目最少记录结论或假设、适用条件、支持它的 SO 与 Evidence/Run 引用、已知反例或差异。公共条目引用相对 workspace 根目录，并注明原 SO 身份；原始证据仍在各自 SQLite 和 Run 中，不增加公共 SQLite、同步服务或知识继承机制。

分析新版本时，Agent 读取这些条目作为调查起点和待检查清单，优先验证可能复用的规律，从而减少重复摸索。该版本仍需生成自己的观察、知识与验证记录；确认适用、发现变体或推翻旧假设后，再更新公共条目的范围和依据。不能把旧版本地址、opcode、解码参数或“通过”状态直接复制为新版本事实。这样形成“逐版本逆向 → 对比总结 → 指导新版本 → 新证据修正总结”的积累过程。

### Unknown 与失败尝试

保留此前讨论其他工具时关注的“暂时无法处理也要留下记录”这一做法；具体失败案例必须有本项目的实验依据，不把对其他项目的讨论直接写成样本事实。

Unknown 是知识 Markdown 中的“未解决项”章节，不另建数据库、文件层或知识服务。当前 V0.2 的函数问题写入该 SO 的 `knowledge.md` 对应 RVA 章节，使用三级或更深标题。当前版本的环境与共性知识、跨版本公共知识按后续实际需求加入；公共知识中可以保留跨版本规律的疑问及来源引用，但不替代每个 SO 的具体 Unknown。其他位置引用其文件路径、函数 RVA 和局部编号，不重复维护正文。

每项用稳定的局部编号记录：**问题、状态（open / blocked / resolved）、已尝试方法及 Run/Evidence 引用、当前缺口、下一步或重试条件**。`blocked` 表示有明确缺失条件，不等同于逻辑已还原。未经过实验的疑问也可登记，但保持假设性质。例如：

- JNI 依赖缺失：Evidence 保存缺失签名与调用位置，Unknown 说明还需什么行为或资源才能继续运行。
- 间接调用仍有未知目标：Evidence 保存已观察目标及对应输入，Unknown 保留未覆盖范围和后续探测方法。
- 还原实现差分失败：Evidence 保存反例，知识记录被反驳的假设，Unknown 指向尚未解释的差异。

解决后将原项标为 resolved，补充解决依据，不删除失败尝试。整理知识时保留开放项及关键失败路线的摘要和引用，详细日志仍在 Run。Agent 续做先检查这些记录；没有新输入、环境修正或分析方法时，不机械重复已失败的尝试。无法继续时留下明确缺口与续做条件，不能把失败或未知当成完成。

### Context 读取

提供按 SO 分析目录和函数地址读取 Context 的函数，返回：

1. 当前代码与知识、上次运行状态及续做笔记。
2. 所需汇编或工具参考结果。
3. 当前 SO 的直接调用关系、相关全局变量，以及注明来源和适用范围的公共知识摘要。
4. 关联证据摘要与原始文件引用，包括已知冲突。
5. 相关 Unknown、关键失败尝试及重试条件；长记录保留继续读取的引用。

原始地址关联多个还原声明时，Context 返回相关源码 ID 与版本清单，可再选择一个源码 ID 深入读取，不静默将一个原始 RVA 当成唯一源码函数。

用条数、文本长度和事件范围限制输出，保留继续读取的引用。Agent 决定 token 预算和临时裁剪；不要求系统计算精确 token 或保证跨版本构建完全相同的 Context。

发布代码时登记实际采用的代码版本、证据 ID 和产物引用，必要时保存在 Run 的输入清单中。无需截获外部 Agent 的完整聊天、系统提示词或模型配置。新会话从当前持久资料重建 Context，不依赖原 Agent 的内存。

## Agent 迭代与动态去混淆

### VM、控制流平坦化与 MBA

LightRE 的首要目标是恢复 VM 混淆承载的真实业务逻辑，重点处理其中的控制流平坦化与 MBA（混合布尔算术）。下列方法是待实现的核心分析路线，不代表当前批量候选流程已有动态执行、表达式求解或等价验证能力。Agent 负责选择问题和解释结果，静态工具、执行环境与求解器负责提供可复现依据；不以多次调用 LLM 或润色伪代码代替这些能力。

阶段目标与逐步检查见 [VM 语义恢复里程碑](VM_RECOVERY_MILESTONES.md)。取指、解码、dispatch、指令语义和逻辑控制流分别形成可检查的局部模型，按选定入口逐步扩展；不是先清理所有 OLLVM/MBA 后才开始理解 VM。

解码模型须允许调查滚动密钥等历史状态依赖，但当前没有样本证据确认存在该机制。先检查解码结果的数据依赖，再按证据恢复初始化、更新及控制转移后的状态衔接；不存在相关依赖时保留简单模型，不默认 XOR、逐指令更新或单个 key。状态模型通过从有效前态连续预测多步来检查，不能逐步读取原 trace 的中间状态冒充独立解码。状态相关时，解码缓存与逻辑 CFG 节点不能仅按 VPC 合并；强制改变 VPC/PC 前必须核对解码状态与相关内存是否相容。具体子目标见里程碑 M2 的条件分支。

需要区分原生代码 CFG、VM 字节码的逻辑控制流与恢复后的业务控制流。解释器自身的分派承载虚拟指令语义，额外的平坦化则可能隐藏 handler 内部或业务块之间的关系；二者可能叠加。观察到 dispatcher 或循环不能直接断言它是可删除的混淆。

| 分析问题 | 优先方法 | 保存的依据 |
| --- | --- | --- |
| VM 如何取指、解码和改变虚拟状态 | 静态定位取指与分派，unidbg 定点记录字节码位置、解码操作数、虚拟寄存器/栈及内存变化 | 有执行上下文的 handler 状态转换、逻辑入口与字节码来源 |
| 平坦化如何隐藏真实后继 | 对状态更新、分支条件和间接目标做反向切片，结合实际块转移及局部求解 | 真实工作块、转移条件、状态更新位置，区分自然观察、强制探索和待确认边 |
| MBA 表达式表示什么运算 | 提取固定宽度表达式，常量传播与规则化简，按需结合专用方法及 SMT 位向量检查 | 原表达式、候选表达式、位宽、前提、求解结果或反例 |
| 恢复结果是否保留业务行为 | 构建候选，从含义一致的输入及状态双边执行，比较输出与声明副作用 | 源码内容依据、实际用例、环境、差异及累计反例 |

OLLVM 是一组混淆变换，不能与平坦化完全等同。当前优先处理控制流平坦化；虚假控制流、表达式替换、间接跳转或块拆分按实际证据分别调查，不假定目标一定用了某个标准 OLLVM 版本。MBA 与指令替换可能重叠，不能凭一段复杂表达式就确定其来源。

控制流平坦化的局部处理步骤如下：

1. 从真实执行和静态 CFG 提出 dispatcher、状态存储、真实工作块和返回分派路径的候选。状态可能在寄存器、栈或别名内存中，也可能多级/编码存储；先用重复运行的实际读写和转移检查。
2. 以状态更新、分支条件、计算跳转目标为切片终点，导出必要指令或 P-code 的定义/使用和内存依赖。P-code 与位向量表达式提取尚未接入，不能把伪代码临时变量直接当作可靠 SSA。
3. 对一个工作块恢复“入口相关状态 → 条件、实际后继、出口相关状态与副作用”的局部关系。例如 `A → dispatcher → B` 可整理成 A 到 B 的逻辑边，但要先保留沿分派路径发生的有效状态更新、内存写入和调用，不能只改跳转。
4. 后继依赖输入时保留条件边；相关 MBA 可先化简再求目标。用 unidbg 的实际转移核对，缺失方向按需构造输入、局部求解或强制探索。未观察边保持未知；分支仅在明确前提下被证明不可达，才能在该范围删除。
5. 多级或多轮平坦化按局部区域逐步处理，再验证组合关系；先保存逻辑 CFG 和来源映射，生成候选后做分段及函数级差分。不要先不可逆地 patch 原始 SO，也不要把 VM 语义分派当作可随意删掉的混淆分派。

MBA 的局部处理步骤如下：

1. 从取指地址、状态更新、条件或输出向后切片，得到带实际位宽的表达式及真实输入。暂不相关的表达式可以保持原状，先解决挡住 VM 分析的部分。
2. 常量传播、复制消除及已验证的位运算/算术规则先行；对适用的线性 MBA 做布尔项/系数规范化。复杂表达式按子表达式分解，非线性或包含未知内存关系的部分保留范围与缺口。
3. LLM、规则或局部搜索提出简单候选，使用 SMT 位向量检查差异；求解器用于检查模型，不保证一次 `simplify` 就恢复最简源码。候选被反例否定时，保留反例并改进候选；超时不视为等价。
4. 化简涉及条件或状态跳转时回到 CFG 更新后继关系；涉及内存或业务输出时用 unidbg 做局部和完整调用回归。纯表达式证明不覆盖未建模的调用、内存副作用或整个业务行为。

例如，对 w 位无符号位向量，`(x XOR y) + ((x AND y) << 1)` 与 `x + y` 在模 2^w 下等价；原机器代码若只使用截断结果，可用它恢复加法。若后续使用 ARM64 NZCV 等标志，还要单独恢复标志来源，不能因结果等价就假定标志也相同。所有重写仍按实际机器语义检查。

MBA 优先分析影响分派状态、分支条件、内存地址和外部输出的表达式。保留 ARM64 W/X 寄存器宽度及零扩展、截断、溢出、移位和相关 NZCV 标志语义；不能按无限精度整数直接化简，也不能在生成 C 时引入有符号溢出或移位未定义行为。局部表达式只包含其真实输入；内存读取和调用具有顺序或副作用时必须保留相应约束，不能把不同读取任意合并为同一个变量。

线性 MBA 可尝试布尔项与算术系数的规范化，非线性表达式按需切片、分解或交给求解器；不假定单一算法适用于全部变体。LLM 可以提出更简单的候选，但在固定位宽和明确前提下检查 `original != simplified` 是否可满足：SAT 保存反例，UNSAT 仅证明所建模型和前提内的等价，超时或 unknown 保持未验证。随机与边界输入可以筛错，不能代替证明；路径条件下的等价不能扩展为全局等价。

平坦化与 MBA 相互反馈：先化简一个状态更新可能暴露真实后继；恢复一个后继和路径条件也可能使下一段 MBA 可解。虚拟指令的行为还需结合真实内存读写与外部调用解释。最终将选定字节码入口的虚拟语义组织为业务运算和分支，消除仅为虚拟化或混淆服务的分派，保留必要算法状态；不以复制解释器循环作为完成。

最小开发检查分别取一个条件工作块的真实后继恢复，以及一个 32/64 位 MBA 表达式的提取、候选与等价检查，再在 VM 的取指或 dispatch 切片中联合使用。现有 minilua 构建显式启用平坦化，large 另有块拆分和多轮平坦化；它可作为控制流调查起点，但没有据此确认 MBA 专项覆盖。MBA 需补充有确定变换来源与等价基线的受控表达式，再对目标中实际观察到的表达式验证。当前这些分析能力均待实现，不修改 V0.2/0.3 的实际完成状态。

unidbg 是具体执行和观测环境，局部符号表达式及 SMT 检查需要另外接入，不假定它自动提供符号执行。强制探索需准备相容状态并记录修改，未覆盖边仍保持未知；未执行或仅被强制走过的分支不能直接删除，也不能据此宣称自然可达。先用一个真实 VM 逻辑入口打通运行、关键切片、化简、源码构建与差分；随后按实际瓶颈扩展，而不预建通用 VM 策略引擎。

### 调查与续做

```text
打开 SO → 建立/读取函数索引 → Agent 选择函数与问题
                              ↓
读取资料 → 提出假设 → 静态调查或执行实验 → 保存有用观察
    ↑                                           ↓
    └──────── 继续调查 ← 检查候选 ← 重写函数 ────┘
                              ↓
                     发布版本 → Web 自动更新
```

以控制流平坦化为例：Agent 根据汇编提出 dispatcher、状态变量、状态更新和不透明谓词假设，再用 unidbg 实验记录状态转换、内存读写及外部调用，必要时结合符号求解或强制执行，恢复有效控制流和数据依赖后重写函数。

先围绕一个选定函数完成“分析—实验—保存—重新打开”的闭环，再扩大到批量。巨型混淆函数内部按问题、地址范围和执行片段调查，不要求一次将全函数汇编放入 LLM。

单次 `codex exec` 内可自主完成多轮调查、实验和工程修改，无需为每个工具调用重启模型。外层默认每轮独立 exec，由程序完整保存返回正文及执行记录，按实际检查结果组织下一轮 context；session resume 仅为可选优化。记录、失败交接和停止机制统一见 [Goal Loop](GOAL_LOOP.md#轮次记忆与纠错)，最小实现范围见 [V0.31](milestones/v0.31/PLAN.md)，不在本文另维护一套执行协议。CLI 退出码或模型声明均不能代替实际核验。

Web 评论发起的任务沿用同一迭代流程：Agent 读取评论、代码和已知失败项，先读取已保存的 Ghidra 结果，按需调用 Ghidra 或 Rizin 补充静态信息，调整 unidbg harness 或输入进行实验，根据新证据重写并比较候选。每轮围绕具体问题推进，不要求每轮调用全部工具，也不要求每轮都生成代码。一次提交可完成多轮工具分析，直到处理目标完成、缺少继续条件或耗尽预算；仅改名、润色或回复评论不足以完成需要验证的逻辑调查。

知识或证据改变时，由 Agent 检查相关函数并标记待复查。复查标记与最佳代码发布互不阻塞，不要求所有调用者立即重新分析。

动态与验证能力按实际实验逐步接入，首先打通 ARM64 unidbg 可重跑 harness 和基本差分闭环，再按需要加入局部符号求解、强制执行及更广的验证，仍复用 unidbg 执行。当前不扩展运行后端，也不要求每个函数经过所有分析方法。

强制执行记录干预，不能据此断言自然可达。符号求得的输入尽可能具体重放。差分比较返回值、输出内存和声明的副作用，并保存输入及环境范围；没有可执行候选就保持未验证。有限测试通过不等于全函数已证明等价。

## Agent 生成与共享 unidbg harness

Harness 按实际兼容的一组 SO 共享，放在用户选择的 `workspace/harnesses/<name>/`，不放进 LightRE 工具仓库，也不按 SO 的哈希复制工程。同一应用或库的多个版本可以复用兼容的 JNI 与初始化代码；差异用当前 SO 的少量参数或普通 Java 分支处理，差异很大时才另建 harness。它是普通 Maven 工程，不是插件或继承体系；LightRE 通用代码只负责启动和收集输出。

```text
<用户选择的 workspace>/
  harnesses/example-lib/
    pom.xml                             # 固定 unidbg 及实际使用的依赖版本
    README.md                           # 运行接口、使用方法与逐版本兼容记录
    src/main/java/
      TargetHarness.java                # 建模拟器、加载 SO、初始化、分派实验入口
      TargetJni.java                    # 有 JNI 依赖时才添加
  libexample-a1b2/
    binary/original.so
    harness.json                        # 指向 ../harnesses/example-lib
    dependencies/                       # 该版本需要的依赖，按需添加
    runs/<run_id>/
      harness/                          # 实际执行的源码、pom 和配置副本
      request.json                      # 选定入口、参数、实验选项
      ...                               # 命令、工具版本、日志、trace 和结果
  libexample-c3d4/
    binary/original.so
    harness.json                        # 指向同一工程，参数可以不同
```

`harness.json` 是关联和版本参数的唯一来源，不另建 harness 注册库。例如：

```json
{
  "path": "../harnesses/example-lib",
  "parameters": {
    "api_level": 23,
    "process_name": "com.example.app",
    "entry_rva": "0x1c07c"
  }
}
```

字段随实际 harness 需要增加，不预定义完整 Android 环境模型，也不建立多层配置覆盖。原始分析目标默认是所选 SO 目录的 `binary/original.so`，由启动入口传给 harness，不在共享 Java 源码中写死。差分运行另外显式指定候选构建产物、入口映射和所用版本，不修改原始样本身份。RVA、依赖文件、初始化差异等按当前 SO 的参数解析；不能把一个版本的地址原样用于另一个版本。共同使用的 APK/资源可以保存一份并引用相同文件，无需每个 SO 目录都复制。

Harness 的创建和修复可以作为 Codex 任务：先读取已有关联；没有时检查可复用的 harness、导出签名和输入资料，适配或生成最小工程，再编译运行。有 JNI 依赖时才调查签名并按缺口补全。V0.31 先实现纯 C 固定测试库的明确导出调用，不建设任意 ABI/RVA 调用器。成功完成选定入口实验后再记录该 SO 的兼容情况；失败时保存缺口和下一步，不要求人工预先提供可运行工程，也不保证从 SO 自动恢复全部 Java 依赖。选择和适配交给 Agent，不开发自动匹配服务。

`TargetHarness` 负责建立 ARM64 Android 模拟环境，按样本依赖加载 SO、执行必要初始化，再调用选定入口。纯 C 目标不要求创建 Dalvik VM、实现 JNI 或调用 `JNI_OnLoad`；后续 DG 适配按实际依赖加入这些步骤。minilua 后续以薄 C 接口加载 `.lua` 并调用自身解析器，另行构建 Android SO，不能直接复用现有 Linux glibc ELF。初始化顺序是样本逻辑的一部分，不要求所有函数都能从任意状态独立调用。纯 C 导出按已知符号和签名调用；JNI 导出或动态注册的方法按类名和签名调用；内部函数支持后再按模块加载基址与 RVA 定位，显式准备 ABI 参数和所需状态。

`TargetJni` 集中实现这些版本所依赖的类、方法、字段和对象状态。例如签名 `android/content/Context->getPackageName()Ljava/lang/String;` 可从当前 SO 的参数返回包名；影响逻辑的 Java 方法需要相应实现或有来源的实验输入。存在 APK 时可以用于类信息、资源及包信息，但不代表 unidbg 会自动执行其中任意 Java/Dex 方法。

补 JNI 按具体运行缺口迭代：记录缺失的类/方法完整签名和调用位置，Codex 读取汇编、APK 或已有知识后补实现，再重跑同一个实验。未实现的方法默认明确失败，不统一返回零或空对象。由配置提供的环境值、简化实现、Hook 和强制修改都要记录；依赖假设的观察注明条件，不能把为了跑通的返回值当作真实设备证据。

不同版本及同一 SO 的函数可共用初始化与 JNI 代码，通过目标 binary、各自版本参数、选定入口和输入运行不同实验，不假定所有版本的初始化或 JNI 行为相同。代码可共享，内存状态不共享：每次实验默认新建模拟器；同一次有意连续调用则记录顺序。实验少时直接在 Harness 中写几个具名入口，复杂后再拆普通 Java 文件，无需一开始建立用例框架。

共享 harness 是 Codex 持续修改的唯一工作版本，同一工程的生成和修改先串行处理。Run 中的副本只用于复现历史，不作为第二份可编辑主版本。执行前保存实际源码、pom 和当前 SO 参数的小型副本，并从该副本构建运行；输入、命令和实际工具版本随 Run 保存，原始 SO 身份从该 SO 的 SQLite 元数据读取。依赖 SO、APK 和大型资源按路径与哈希引用，保留用过的原文件，内容变化则另存文件；不复制 Maven 依赖缓存或整个构建目录，也不为每个 SO 维护独立源码分支。

所有输入路径相对所选 SO 分析目录解析，执行入口显式传入该目录，不依赖 Java 进程的当前目录。重放旧 Run 使用保存的 harness、参数与输入，不能默默改用共享工程的当前版本。运行接口与使用方法记在 harness 的 README，具体 JNI 假设、运行缺口和函数前置状态记在该 SO 的知识中。一个版本的运行证据不自动成为另一个版本的证据，共享代码后仍需对目标版本验证。不另建 JNI 数据库、跨版本证据同步或代码继承系统。

## Web 评论到 Codex 执行

用户在函数页面发现问题后，填写评论并点击“提交并执行”，可选附上选中的伪代码片段。后端创建独立的 `tasks/<task_id>/task.md`，用 reviewed.c 保存用户实际正在查看的代码，再持久入队并立即返回任务 ID。队列中评论优先，同优先级 FIFO；执行时对照提交时版本与最新代码继续调查。暂停期间也可提交，保持排队直到继续。

任务保持为普通 Markdown，例如：

```markdown
---
function_rva: 0x1c07c
source_id: f001
viewed_version: v004
---

# 核查状态转换

## 用户评论
这里的分支似乎被错误合并了，请结合 unidbg 调查状态更新并修正。

## 选中片段（可选）
这里保留用户看到的伪代码原文，仅用于定位疑问。

## 处理结果
待执行。
```

最小流程：

```text
Web 评论 → 保存 task.md/state.json → 持久队列 → codex exec → 分析/实验/发布代码
                              ↓                    ↓
                         运行日志             任务处理结果
                              └──────── Web 展示 ──┘
```

非交互命令是 `codex exec`；`-p` / `--profile` 用于选择配置 profile，不是提示词参数。沿用本机登录、模型和 provider 配置。V0.2 已接入最小流程：分析阶段默认分批尝试全部未生成候选的函数，Web 评论优先入队，自动启动选定函数续做。

`src/recovery/` 使用 subprocess 参数列表和 stdin 调用 Codex，SO 目录作为 cwd；模型返回结构化 JSON，由 LightRE 校验并发布候选及上下文。容器默认使用当前执行权限，可配置 sandbox。每个 SO 一个调度器，同一时间执行一个任务，任务内有限批次并行；文件锁保护执行与入队，不增加队列服务。具体参数、目录及状态以 [V0.2 使用说明](milestones/v0.2/USAGE.md)为准。当前尚不执行下面描述的动态实验或完整版本发布。

参数依据为 OpenAI 官方[非交互运行](https://developers.openai.com/codex/noninteractive/)。

Agent 读取任务，确认样本、函数地址和评论对应版本，再调用 API 读取知识与证据，按疑问编写或调整调查脚本。如果当前最佳版本已经变化，同时对照被评论的旧版本和当前版本，避免把旧问题套用到新代码。评论表达调查目标或人工假设，不直接作为已验证证据。

Codex 执行静态分析或动态实验，按原流程保存证据与代码版本；在任务文件中保留原始评论，补充采用的 Run、Evidence、输出版本、结论及未解决问题。执行入口独占更新 state.json 的任务状态与检查点（queued / running / complete / partial / error / interrupted / cancelled）；模型通过结构化结果返回代码与理解，由 LightRE 发布，不能自行修改任务状态。退出码为零也需有任务处理结果，不能直接等同于问题解决或语义验证通过。中断续做资料保存在关联 Run。

对需要进一步验证的评论，Codex 在同一任务内继续多轮静态调查、unidbg 实验与差分，不以一次回复作为结束。暂时无法解决的问题写入所属知识文档的 Unknown，任务结果只引用该项及失败 Evidence，注明停止原因和继续条件；后续从 Web 再次提交或重试时读取已有尝试继续调查。

V0.2 使用工作区内的文件任务队列和独立后台执行进程，HTTP 不等待模型结果。忙时评论直接排队；批量分析在当前全部活跃批次结束后让位，反馈结束后根据 done_rvas 续跑。同一 SO 不并行执行两轮函数分析。队列支持去重、暂停、继续、取消和失败隔离，重启 Web 恢复已有未暂停的请求；队列清空后进程退出，不依赖 Redis、Celery 或常驻 Worker 服务。未来共享 harness 的写入仍需独立互斥，不能将不同版本的知识混用。

任务所属 SO 由其分析目录下的 `tasks/<task_id>/task.md` 位置确定，文件内记录原始函数 RVA、被评论版本和任务内容；查看还原代码时同时记录源码 ID，避免合并或拆分后评论定位不清。原始汇编尚无源码实体时可省略源码 ID，不重复保存原始 SO 的 SHA256。任务文件不复制完整函数或整个 Context，所需资料按身份和版本读取。任务正文维护在 task.md，状态与检查点只维护在 state.json；Run 保存进程退出、日志及产物，不另存一份可独立修改的任务状态。用户可在未运行时编辑任务要求；Web 查看任务时直接读文件。任务状态和日志按需轻量轮询，代码发布仍通过该 SO 的 revision 自动刷新。默认在 Web 看结论、证据及代码差异，原始 Codex 日志折叠显示，手动进入聊天会话仅作为可选排查方式。

## Web

本节保留现有浏览能力和可选反馈设计。长期自动化的完成标准以源码工程和验证结果为中心，不要求实现本节全部界面设想，也不为 Goal Loop 增加新的可视化前置。

Web 针对当前选中的 SO 版本查看和验收还原逻辑，使用该 SO 的 SQLite 和文件，不将多个版本的函数混在一个列表。界面保持 FastAPI 和简单 HTML/JavaScript：左侧函数列表支持名称/地址搜索，右侧从实际源码文件读取当前最佳还原代码或分析中伪代码，显示当前 SO、文件、原始地址关联、源码 ID 和版本，提供调用导航、工具参考及历史版本切换。函数合并或拆分后可按原始地址找到关联的源码声明，阅读同一份定义。

主视图明确区分“分析中伪代码”和“可执行还原源码”，简要显示验证范围与未解决问题。人工通过修改建议介入，不提供逐函数认可或待评价状态；没有建议时自动任务继续推进，源码正确性由构建、测试和行为对比判断。建议绑定实际显示的源码身份及版本，并沿用持久任务队列。

导入框填写 SO 路径后，显示所选 workspace、SO 分析名称和来源资源目录；名称可编辑，在所选位置创建名称加短 SHA 的 SO 目录。Workspace 路径来自本次用户选择或已有上下文，不硬编码。来源目录只是查找资源的起点，不意味着其中每个文件都参与本次实验。已有 SO 的显示名称也可在 Web 修改，目录路径保持稳定。

代码区域只读，另有一个简短的建议输入框和“提交修改建议”按钮。任务可在 Web 执行、重试并查看状态、结论和处理结果。人工反馈后，Agent 继续多轮工具分析与运行验证，证据和代码发布后页面自动更新，人工再审阅和反馈。Unknown 与失败记录沿用折叠的知识、依据和任务结果展示，不新增常驻面板。复制文件路径或提示词只是备用方式，不是日常操作的前置步骤。

默认折叠依据，展开查看证据摘要或 Markdown。未生成代码时显示待分析，已有函数仍可浏览。列表是“当前识别函数”，不要把它描述成已找到 binary 中所有函数。

页面约每 3 秒查询当前 SO 的轻量发布 revision 和进度；源码、路径、来源、知识或结果状态的发布变化均可触发重读，不依赖任务计数。按“原始 RVA → 当前源码 ID 集合 → 文件版本与字节范围”定位，确保索引和正文属于同一发布结果。草稿或读取失败不能消耗待刷新版本，迟到旧响应不得覆盖新结果。当前最佳视图保留阅读位置，历史视图保持所选版本；函数列表按变化重载，trace 不进入常规响应。具体协议及性能边界见 [源码定位设计](SOURCE_NAVIGATION.md)。

进度显示当前阶段、已处理函数数及停止原因，不显示“正确性百分比”。Agent 通过 API 更新 Run 进度，Web 读取同一持久数据。打开新 SO 可先用本地路径，上传流程不作为首版前置要求。

## 实现顺序

每次只交付一个能运行、能由用户直接验证的小增量，交付后由用户体验和反馈决定下一步。P0/P1/P2 是长期需求分组，不是一次完成的开发批次。具体步骤与验收例子以 [小步实现计划](IMPLEMENTATION_PLAN.md) 为准。

以下关于“第一版”“首次开发”的内容是 V0.1 的历史起步说明；当前版本范围以 [V0.2 计划](milestones/v0.2/PLAN.md) 为准，下一小步以 [V0.31 计划](milestones/v0.31/PLAN.md) 为准。

第一版只完成“Skill 聊天给出目录或 SO → 按用户上下文定位或创建可见的外部 workspace → Agent 启动当前 SO 的 Web → 列出已识别函数 → 搜索名称或 RVA → 点击查看原始汇编”。一份最小 Skill 说明、一个页面和最少读取接口即可；先不引入完整多版本管理、代码版本、自动刷新或动态分析。外部目录位置从首版就遵循约定，SQLite 与公共知识按需加入。底层启动命令由 Agent 执行，巨型函数分段读取，原始汇编本身就是首版的可用产物。

随后按反馈逐项加入单函数候选展示、持久化、知识、一次 unidbg 运行、Evidence、候选执行和差分。Web 评论和自动刷新也分别作为可验收的小增量，不把整套自动化作为首版门槛。不为未来能力预写空接口或完整数据库。

逐步形成一个函数的“读取 → unidbg 运行 → 保存证据 → 重写可执行代码 → 比较 → Web 人工审阅与反馈 → Agent 多轮分析/运行/比较 → 再审阅”闭环，满足选定范围的验收后交付源码。中途失败或无法解决时保留 Evidence、Unknown 和续做条件，并确认新会话能续做。

进入差分能力的开发时，先用一个小函数验证构建、状态准备、比较、反例保存和修复回归，再选择真实强混淆样本中的一个明确逻辑入口验证还原效果，随后扩大到调用链。每一步均单独交付，不等整个闭环写完才提供可运行例子。

## 首次开发任务与完成条件

首次只开发 V0.1。以 `dg-samples/dC6BDAE/libdC6BDAE49562F.so` 为示例验收输入；相对路径按 Skill 调用目录解析，也可传入实际绝对路径，不固定任何本机目录。

1. 用户通过 LightRE Skill 给出目录或 SO，Agent 识别目标，在用户指定或上下文确定的可见 workspace 中定位/创建该 SO 的分析目录，返回完整路径。
2. 由独立分析入口导出真实函数列表、名称、RVA 和完整汇编，持久保存到 workspace 的 SQLite；Web 查询只读这些结果。
3. 启动一页 Web：左侧函数列表和名称/RVA 搜索，右侧原始汇编；选择函数能切换内容，巨型函数能继续加载后续指令。
4. Agent 返回经过访问检查的实际 URL。提供聊天复现例子，验收搜索、短函数、巨型函数和停止后重新启动；读取失败能看见原因并继续选择其他函数。

这一增量只实现本次所需的目录、数据读取、最小 Skill 说明和页面。无需先建完整 SQLite、接入 Ghidra/unidbg、生成候选、做多版本管理或创建公共知识；已经确定的身份与目录约定在后续加入这些功能时继续沿用。

交付时说明本次行为、实际 workspace/SO 目录、聊天复现方式、URL、验证结果及限制，然后留给用户体验。完成 V0.1 不代表完成全部 P0；后续任务从反馈中选择，需求清单只对实际完成并经人工验收的条目勾选。
