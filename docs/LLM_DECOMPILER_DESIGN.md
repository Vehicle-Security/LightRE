# LightRE 极简设计

实现范围与验收依据见 [REQUIREMENTS.md](REQUIREMENTS.md)，小步交付顺序见 [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md)。本文是规划，不代表功能已经实现。

## 开发基线

以下约定作为开始开发时的统一依据，后文展开其细节；长期能力按需加入，不要求一次实现。

| 对象 | 当前约定 |
| --- | --- |
| LightRE | 工具代码、Skill 说明和工具依赖，与分析产物分开 |
| workspace | 用户可见、位置和名称动态决定的外部分析根目录，可组织同一类 VM 的多个 SO 版本 |
| SO 分析目录 | workspace 下的 `<名称>-<短SHA>/`，固定对应一份原始 SO，独立保存 SQLite、源码、知识、证据、运行和任务 |
| Web | 每次只读一个选定 SO 的持久分析结果；函数及汇编读取 workspace 的 SQLite，源码正文读取对应版本文件，不现场调用分析工具 |
| SQLite | 每 SO 一份，维护实体映射、版本选择及结构化状态；源码变化通过发布入口同步更新索引 |
| harness | workspace 内按兼容情况共享代码，各 SO 保存自己的参数、JNI 假设、运行证据与验证结论 |
| 公共知识 | 从多版本分析中有意提炼，保存在 workspace 顶层 Markdown，引用原始依据，指导新版本调查 |
| 开发节奏 | 每次交付一个可运行、可验证的小增量，用户体验后再确定下一步 |

“SO 版本”指内容不同的原始文件；“源码版本”指对同一 SO 的某个还原结果的多次修改。不同 SO 的同一 RVA、源码 ID 或验证状态不合并。下文的路径和名字均为示例，不要求预先创建整棵目录。

**当前提交基线为 V0.1，本轮人工验收反馈已落实。** 本版本先由分析入口调用 Rizin 保存函数和完整汇编，再让 Web 只读 workspace 和 SQLite；最终功能、界面与验证记录见 [V0.1 milestone](milestones/v0.1/DELIVERY.md)。后续范围见 [小步实现计划](IMPLEMENTATION_PLAN.md)，用法见 [V0.1 使用说明](milestones/v0.1/USAGE.md)。差分闭环是后续逐步达到的目标。

V0.1 每个 Web 进程固定浏览启动时指定的一份 SO 结果。更换目标由 Skill 重启服务，页面不提供工作区切换。

## 目标与边界

LightRE 配合 Codex 使用，提供简单的本地 Python API、功能说明、持久资料和一个轻量函数浏览器。核心目标是面向强混淆 ARM64 SO，以函数或明确的逻辑入口为单位，让 LLM 持续还原 VM/OLLVM 逻辑，借助 unidbg 运行原实现与候选实现并差分比较，逐步恢复原机器码语义。

最终产物是一份简单可读、可执行、可修改的等价源码，供后续二次开发。Web 帮助人工审阅恢复后的逻辑、查看验证依据和提交问题；反馈后 Agent 继续按问题调用 unidbg、Rizin 或 Ghidra，多轮调查、还原和差分验证，再更新 Web 供人工复查。函数伪代码、原 VM 的运行结果和 Evidence 支撑这个目标，最终需要把选定范围内被虚拟化的逻辑恢复成直接表达行为的代码。

最小闭环是：**读取知识、Evidence 与 Unknown → 分析并重写候选 → 构建候选 → unidbg 双边运行与比较 → 保存反例和新证据 → 修正并重跑累计用例。** Harness 尚不可运行时先补齐初始化与环境；暂时没有候选时仍可执行原实现收集观察。先围绕一个实际样本打通这个闭环，持续保留能支持下一轮调查的资料。

Codex 主导推理、实验和多轮优化，根据功能说明编写普通 Python 脚本组合调用 LightRE API。LightRE 负责执行基础操作、保存结果并让 Web 展示。Web 提交任务后直接调用非交互 Codex，无需人工逐个进入聊天会话。Agent 可以更换或退出，新会话能从工作区重建理解。内部允许分析 CFG 和基本块，Web 以函数与伪代码为主，支持提交分析评论作为本地任务；代码本身保持只读。

系统只维护持久数据。批次内缓存、临时状态、上下文裁剪和下一步决策由 Agent 处理。首版不做独立 Agent 平台、通用工具适配框架、MCP、任务队列服务、缓存层或 bundle 导入导出。

VM/OLLVM 的具体调查方法由 Agent 按问题选择，不预建通用 VM 解码器、去混淆流水线或策略引擎。需要的专用脚本随实验保存；先让观察和推断可积累、实验可重跑。能执行原 VM 只是运行观察，恢复其中被虚拟化的逻辑仍需进一步分析，结论保留验证范围。

通用性首先体现在可复用的实验、状态准备、比较和资料保存能力；不同保护方案的调查方法由 Agent 随样本积累。目标是逐步扩大已恢复范围，不承诺有限测试可证明任意 ARM64 SO 的全部行为。运行环境不支持、关键依赖缺失或路径尚未探索时保留 Unknown，不能据此宣布全部还原。

## 主要入口：目录 + Agent Skill

用户以目录和自然语言目标发起任务，例如：

> 用 LightRE 打开 ../dg-samples/dC6BDAE，展示函数和汇编。

LightRE 的产品入口设计为 Agent Skill，说明 API 能做什么、输入输出和持久化约定。Agent 根据任务理解目录、确定目标 SO，编写脚本调用 API 并开展调查；不要求用户手动枚举依赖或拼接完整参数。底层工具命令仍由 Python 函数直接调用，Web 的路径导入保留为辅助入口。

输入目录是相关材料的范围，不等于一个 binary。Agent 根据用户目标、文件格式、ELF 依赖和目录内容区分主要 SO、其他版本、依赖库及配套资源。目标唯一时直接选用；无法区分多个候选时才询问。同一类 VM 的多个版本可以放在同一个 workspace，每份 SO 有独立目录、SQLite 与全部版本知识；共享 harness，并逐步提炼有依据和适用范围的公共知识。

目录、分析目标和已识别资料足以启动调查，不强制用户先写输入配置。LightRE 根据 Agent 请求创建或恢复外部 workspace；用户可指定位置，也可把新版本加入已有 workspace。目标与来源位置按 binary 登记，输入角色及未知关系记入其知识文档，运行实际采用的文件按原规则固定并记录。后续发现新依赖时补充资料，不必重新导入整个目录或预建通用输入描述语言。

工作区创建或恢复后，启动或复用 Web，页面可访问就打开并返回地址；不等待全量分析完成。当前 Codex 直接执行 Skill，Web 评论才通过非交互 Codex 发起下一次任务，避免递归调用。浏览器无法在容器中启动时仍提供服务地址。

Skill 和 API 文档随实际功能一起完善。V0.1 即提供最小聊天入口：用户说“用 LightRE 打开这个目录，展示函数和汇编”，Agent 识别目标、调用读取能力、启动或复用 Web 并返回实际地址，用户无需填写 Python 启动命令、监听地址或端口。开发验证可让 Agent 显式读取项目内的 Skill 说明，不要求先做全局安装；完整工作区等能力按后续增量加入。本文只约定方案，不表示入口已经实现。

## 最小 API 职责

API 指可从项目源码直接导入的 Python 函数，开发测试不要求安装 Skill 或启动 HTTP 服务。功能说明只需给出参数、返回值、文件位置、失败含义和短示例，Agent 自行组合调用。

- 定位或创建外部 workspace，打开其中选定 SO 的分析目录，读取函数汇编、当前代码、知识和关联证据。
- 运行指定 harness 和输入，保存实际配置、源码及原始输出，返回 Run 和产物位置。
- 登记有用的 Evidence，并按函数或 Run 查询。
- 保存函数候选与更新最佳版本，启动或定位 Web。

调查脚本可以筛选数据、解码字节码或设置实验观测点，需要复现的脚本放入 runs。结构化数据更新通过 API 完成，沿用地址身份、版本和文件发布约定，避免每个脚本自行修改 SQLite 形成不同格式。Web 直接复用同一套函数；不维护另一套业务实现。具体函数随闭环需要实现，不先铺满所有分析工具的 API。

## 工作区与数据

**Workspace 是用户可见的分析根目录，可以研究同一类 VM 的多个 SO 版本。每份 SO 的分析目录仍独立保存 SQLite、源码、Knowledge、Evidence、Unknown、Run、任务和验收结论。** 保留原来每 SO 一套数据的结构，不新增统一数据库或 binary_id。Workspace 只在外层组织这些目录、共享 harness 和提炼出的公共知识。

LightRE 仓库只放工具源码、文档、Skill 说明及工具依赖；workspace 由 LightRE 按聊天请求动态创建或打开。**位置和目录名由用户或当前上下文决定。** 未指定时放在会话当前工作目录下，本环境为 `/work2`，不得混进 LightRE 或 dg-samples 等样本 Git 仓库。创建前说明拟用路径，创建后返回完整路径和 Web 地址；不要求用户再次确认常规目录创建，不写入隐藏缓存。扫描输入时跳过生成目录，避免再次导入原始副本或候选 SO。

例如用户可说“用 LightRE 分析这些 VM 版本，workspace 放在 `/work2/vm-analysis`”。该路径仅是例子。也可直接给出已有 workspace，加入新的 SO 版本；创建多个项目或放在其他仓库外位置均可。Web 改显示名称只改元数据，不移动目录。

每个 SO 分析目录内有自己的 `index.sqlite`，完整 SHA256 在该库元数据中保存一份权威值。选定该目录就确定原始 SO，实体不重复存哈希；同内容在本 workspace 内复用原分析目录，内容不同建立新目录，旧结果不覆盖。各数据库之间不联表，不把不同版本的同 RVA、源码 ID 或 Evidence ID 当成同一个实体。

每份 SO 使用 `<名称>-<短SHA>/` 作为可读分析目录。名称默认取样本来源目录名，可指定；无来源目录时用 SO 文件名去掉 `.so`。短 SHA 默认 4 位，重名且内容不同则延长新目录的前缀，已有目录不动，不能只凭短 SHA 判断身份。原始副本不变，候选和导出不改变 SO 身份。

来源资源目录按 binary 记录；例如 `bytecode/` 下的 `.bin` 是待调查输入，不能直接当作确定的 VM 结构或原生依赖。导入不递归复制整个输入目录，只保留目标 SO；实际使用的依赖按路径和内容哈希固定。共享资源可引用同一文件，避免重复复制。

```text
/work2/LightRE/                    # 工具代码及工具依赖

<用户选择的可见 workspace>/
  harnesses/default/               # 多版本兼容的运行代码
    pom.xml
    src/main/java/
    README.md                     # 运行接口、使用方法及逐版本兼容记录
  knowledge/overview.md           # 按需创建，逐步提炼出的公共 VM 知识
  dC6BDAE-d65f/
    binary/original.so
    index.sqlite                  # 只管理当前 SO
    harness.json                  # 共享 harness 引用与当前 SO 参数
    dependencies/
    ghidra/                       # 按需创建
    knowledge/overview.md         # 当前版本的理解、差异、假设与 Unknown
    knowledge/functions/0001640c.md
    knowledge/globals/0005a844.md
    versions/f001/v001.c
    exports/<export_id>/
    runs/<run_id>/
    tasks/<task_id>.md
  other-version-abcd/              # 独立一套目录和 SQLite，按需创建
    index.sqlite
    ...
```

目标是通过多个版本的逆向总结公共 VM 知识，加快后续版本分析。各 SO 的知识、证据和验证状态始终独立，公共知识是有意提炼的结果，不能直接把某个版本的全部知识当作其他版本事实。入口 RVA、opcode 对应、字节码布局、JNI 细节等具体结论仍归属实际版本；可共享的设计规律、识别方法和实验经验写入顶层知识，注明来源、适用条件及已知例外。共享 harness 只表示复用可兼容运行代码，不表示逻辑或验证结论相同。

只维护一份权威内容：

| 内容 | 保存位置 |
| --- | --- |
| 当前 SO 的 SHA256、显示名称、来源目录、格式版本、revision | 该 SO 的 SQLite 元数据 |
| 原始地址实体、源码实体索引、引用、当前最佳版本 | 该 SO 的 SQLite |
| 代码正文、声明名称、源码 ID 与来源注释 | versions 文件；SQLite 只索引身份、名称、路径、来源与检查状态 |
| 人工验收结论 | SQLite 对应代码版本上的状态及意见引用 |
| 用于二次开发的源码交付物 | exports 文件，从选定版本生成的独立快照 |
| 当前 SO 的知识正文 | 该 SO 分析目录中的 knowledge Markdown |
| 提炼出的公共 VM 知识 | workspace 顶层 knowledge Markdown，附来源与适用范围 |
| 证据摘要、条件、来源、地址关联、有效状态 | SQLite |
| 当前可编辑的共享 harness 与 JNI 实现 | workspace/harnesses/<name> 文件 |
| SO 使用的 harness 及版本差异参数 | 该 SO 分析目录的 harness.json，不在 SQLite 重复维护 |
| 依赖 SO、APK 和资源 | 按需保存的文件，按相对路径与内容哈希引用 |
| 原始 trace、当次 harness 副本、输入、运行输出与检查点 | 当前 SO 的 runs 文件；该库登记运行状态及路径 |
| Web 评论、任务要求、处理状态与结果 | 目标 tasks Markdown；不在 SQLite 复制正文或状态 |

SQLite 保存映射索引和少量结构化权威状态，不保存可独立修改的知识或代码正文。源码索引可从已登记文件重建，SO 元数据、版本选择、证据记录及人工验收结论仍由该库保存，不能把整个数据库当作可随意删除的缓存。各 SO 的配置与数据库文件引用相对其分析目录解析，`../harnesses/default` 可指向同一共享工程；运行入口显式传入 SO 分析目录，不依赖当前 shell 目录。备份时停止写入，整体复制外部 workspace 及其引用的固定资源，无需复制 LightRE 工具仓库。

不预建 Markdown 索引库、Context 快照库、跨版本数据库或任务数据库。SQLite 按实际操作增加必要表；公共知识直接读 Markdown，不额外同步到各 SO 的数据库。任务由轻量入口调用 Codex，不增加队列服务。Markdown 无需重新索引或文件监听，整理长知识前保留旧文件，原始 trace 不做 compact。

## 快速打开与按需分析

“Rizin 优先”不等于每次都做完整分析：

1. 已有所选 SO 的分析产物时，直接读取其函数列表和代码，打开页面不重新启动 Rizin 或 Ghidra。
2. 新样本先做轻量枚举，显示当前已识别的函数。stripped SO 的初始清单可能不完整，明确展示分析阶段，后续补充。
3. Agent 的分析任务读取目标函数汇编、引用、字符串和字节时优先用 Rizin，先保存所需结果。Web 只读取已保存结果；缺失时由 Agent 显式执行分析导出。
4. 只有深入分析需要时才做 `aaa` 等完整分析，保存结果；不把完整分析作为每次打开或查询的前置条件。
5. Ghidra Headless 按需提供参考伪代码、P-Code、类型分析，并保留项目。无需先反编译全部函数。

工具通过命令或脚本直接调用。需要的参数、工具版本、退出状态和持久产物记入 Run。耗时调用可设超时、可取消；单函数失败不阻断其他函数。Ghidra 对同一项目的写入先串行执行。

Agent 生成的脚本和 Web 使用同一组 Python API；Agent 可以直接导入项目源码调用，不必启动 Web 或通过 HTTP 写入。Web 负责展示结果、保存评论任务及触发 Codex 执行。CLI 如有需要只作薄包装，Rizin 和 Ghidra 各自只接入当前需要的命令。

## 地址、命名与函数版本

### RVA 是什么

RVA（Relative Virtual Address，相对虚拟地址）表示相对模块映像基准的偏移。本项目用它标识同一 SO 内的函数、全局变量和指令位置：

```text
运行时虚拟地址 VA = 对应模块基址 BASE + RVA

例如 BASE = 0x70000000，函数 RVA = 0x1c07c
则函数运行时地址为 0x7001c07c。
```

ASLR 或模拟器加载位置改变时，BASE 和 VA 可以变化，同一份 SO 的 RVA 不变。不同 SO 可能有相同 RVA，因此地址始终在所属 SO 分析目录内解释；跨 SO 或对外引用时附带原始 SO 的完整 SHA256。

RVA 不是文件中的字节偏移。对 ELF，以最低 `PT_LOAD` 的 `p_vaddr` 为本项目的静态映像基准，并记录工具的地址调整；BASE 指该静态基准在本次运行中的对应地址。常见 SO 的静态基准是 0，此时 ELF 虚拟地址通常与 RVA 相同；非零基准或工具重定位时先换算。Rizin/Ghidra 地址不能不加判断直接当 RVA，读取原始文件还需按 ELF 段布局转换文件偏移。

### 稳定身份与命名

选定 SO 分析目录就确定原始 binary，原始地址实体只用“类型 + RVA”唯一定位。它与还原后的源码声明分开：源码文件保存实际声明名称，当前 SO 的 SQLite 索引其名称与来源，便于查询和导航。例如：

```text
(function, 0x1640c) -> cleanup_tagged_slots
(global,   0x5a844) -> runtime_flags
```

API 调用、版本、证据关联和评论任务明确所属 SO 分析目录，不给每个实体增加 SHA256 字段，也不在每次查询时重新计算文件哈希。只有跨 SO 引用、导出或需要独立解释的源码文件头等资料，才从该 SO 的 SQLite 元数据附上 SHA256；这是来源标识，不是另一份可编辑的身份记录。

源码直接使用可读名称，尚未理解时可使用 `fn_0001640c` 等临时名称。稳定身份保存在声明注释中，不要求 C 标识符本身携带地址。SQLite 中的名称是所选源码版本的索引，不能脱离源码单独修改；重命名由 Agent 修改声明和相关引用，生成新版本并更新索引。历史版本保留其真实名称，Web 不用当前名称替换历史文本。先由 Agent 处理选定代码范围，不预建通用重构引擎。

直接调用按地址关联，函数内分支不算 callee。间接调用保存调用点及有证据的候选目标，未解析时保留间接表达式。动态目标根据所属模块和加载布局转换地址；模块外目标先保存模块/符号或目标记录，不要求建设多模块联合分析模型。TLS、GOT 及指向对象按需要区分，不提前建设完整类型系统。

LLM 可以重写整个函数。每次保存一个新版本，记录来源、输入依据、检查状态和未解决问题。最新候选与当前最佳版本分开。Agent 提交时明确是否替换最佳版本并给出理由，不建设自动评分框架；更短、更好看或功能相似不足以证明语义正确。

先完整写入不可变代码版本文件，再通过统一发布入口用 SQLite 事务登记版本、选择结果和更新索引及 revision；完整流程见下文“SQLite 索引与更新”。读取者只展示已登记的文件。中断留下未登记文件可以以后清理，不增加文件与数据库的分布式事务。

### 同一份源码与声明注释

**Web 的源码正文直接读取项目中保存的版本文件，编译也读取同一版本文件。** 页面只增加语法高亮、行号和可点击定位，去除这些展示标记后文本与文件一致，不替换名称、改写函数或维护页面专用代码。界面显示正在读取的文件和版本；工具原始伪代码与 Agent 还原代码分别标明来源，均展示各自实际保存的文本。

每个还原函数、全局变量有一个 SO 内稳定的源码 ID，例如 `f001`、`g001`，创建后不随改名、移动文件而改变。其全局身份是“原始 binary SHA256 + 源码 ID”；不同 SO 的同名源码 ID 不合并。原始地址身份仍用类型和 RVA，两者通过来源注释关联。无需给局部变量建立全局地址表。

文件头从当前 SO 的 SQLite 元数据写入 binary 文件名和完整 SHA256；声明上方写源码 ID 和来源。文件头是便携的来源说明，不是另一份可编辑的 binary 身份。完整哈希每个文件写一次，声明继承文件的 binary 上下文。例如：

```c
/* lightre-binary: libdC6BDAE49562F.so
 * sha256: d65fc4e408a87ab24c0f355096ceb8c406176379067657f409d6b51e24283472
 */

/* lightre-id: g001; origin: global@0x5a844 */
static unsigned runtime_flags;

/* lightre-id: f001; origin: function@0x1640c */
void cleanup_tagged_slots(void) {
    /* 可选局部定位：lightre-local: f001/l001; origin: unknown */
    unsigned count = 0;
    /* ... */
}
```

局部变量和参数需要单独引用时，用“源码函数 ID + 局部 ID”加注释；不要求名称跨函数统一，也不为编译器临时值、寄存器或栈槽虚构唯一原始地址。全局变量或派生函数没有直接地址来源时写明 `origin: derived` 并引用其相关源码 ID；尚不清楚的来源标为 unknown。局部 ID 只在仍表示同一逻辑变量时沿用，整函数重写后不假定局部变量必然一一对应。

声明注释是代码身份和来源映射的依据，SQLite 保存可重建的查询索引，不再维护另一份可独立修改的名称或来源正文。一个文件可以含多个声明，索引按源码 ID 定位文件与版本，行号仅作当前版本的阅读位置。注释声明来源关联，不代表已证明整段原始代码均被覆盖；详细证据与未解决项仍在 Evidence/Knowledge。

### VM 的逻辑边界

一个原生解释器函数可能执行多个字节码入口，一个恢复出的功能也可能跨越多个原生函数。因此原生 RVA 是追溯锚点，不强制对应一个最终源码函数。需要时在知识、版本关联和 Run 参数中补充字节码资源身份、入口偏移及影响含义的执行上下文，区分不同逻辑入口；字节码偏移不能冒充原生 RVA。

原始地址与还原源码之间按多对多来源关联处理，不把 RVA 作为还原函数的唯一主键：

| 情况 | 源码身份与来源 |
| --- | --- |
| 一对一还原 | 一个源码 ID 关联一个原始函数 RVA |
| 多函数合并 | 合并结果使用一个源码 ID，`origin` 列出多个原始函数 RVA |
| 一个函数拆分 | 各结果使用不同源码 ID，可以关联同一个原始函数 RVA，并按需注明指令范围或逻辑入口 |
| 抽取公共 helper | 分配独立源码 ID，注明 derived 及其来源源码实体，不虚构原生函数入口 |

例如合并可记录 `lightre-id: f003; origin: function@0x1640c, function@0x17000; replaces: f001, f002`；拆分结果 `f004`、`f005` 都可以来自 `function@0x1c07c`，但用各自已确定的字节码入口或指令范围进一步说明。以上关系限定同一 binary，派生 ID 在该 binary 内不复用；跨版本的相似性先记录在知识中，不直接合并代码身份。

改名或移动文件保留 ID；真正合并、拆分时为新逻辑声明分配新 ID，旧 ID 和历史版本继续可追溯，记录被替代关系，不把旧实体静默改成另一个含义。一次涉及多个声明的发布用已有 SQLite 事务和 revision 一起选择新结果，避免 Web 显示新调用者和旧 callee 的混合组合。一个原始函数在 Web 可定位多个还原结果，一个合并结果也可从多个原始地址进入，展示其完整定义，不重复生成源码副本。

最终导出保留原生地址、逻辑入口与还原函数的映射。内部仍可分析 handler、指令片段和基本块，Web 无需增加 CFG 或基本块面板，也不预建通用 VM 类型系统。这些能力随实际合并或拆分需求逐步加入，不扩展首版函数与汇编浏览的范围。

## SQLite 索引与更新

### 唯一身份约定

所有 API、注释、证据、调用关系和 Web 导航遵循同一套实体身份。每个 SO 的独立 SQLite 内统一使用带类型前缀的 `entity_id`，前缀区分原始实体和还原源码，不另发依赖数据库行号的业务 ID。选定 SO 后无需增加 binary_id 字段：

| 实体 | binary 内 entity_id 示例 | 身份依据 |
| --- | --- | --- |
| 原始函数 | `native:function:0x1640c` | 类型和规范化 RVA，名称不参与身份 |
| 原始全局变量 | `native:global:0x5a844` | 类型和规范化 RVA |
| 还原函数 | `source:f001` | 声明注释中的稳定源码 ID |
| 还原全局变量 | `source:g001` | 声明注释中的稳定源码 ID |

`source:f001` 与注释中的 `f001` 是同一身份的完整写法和简写，不是两个不同编号。跨 SO 使用“binary SHA256 + entity_id”；需要定位具体代码时再带版本 ID，行号和名称都不作唯一键。源码 ID 由发布入口在当前 SO 内分配并检查唯一性，不复用已登记过的 ID；索引重建不得重新编号。原始 RVA 按统一数值格式规范化，不能因大小写或补零生成重复实体。局部变量的可选身份继承源码函数及局部 ID，不进入全局函数/变量列表。

原始实体与源码实体间的来源映射是多对多关系，不能强行压成一个地址主键。合并只让旧源码结果退出当前选择，不删除原始 SO 中仍存在的函数实体。

### SQLite 具体保存什么

- **映射索引**：原始实体、当前源码实体、名称、文件路径、文件哈希、版本、声明位置、原始来源和实体间引用。Web 通过索引定位文件，再直接读正文，不逐次扫描所有源码。
- **版本与选择记录**：已登记的不可变文件、候选版本、当前选定版本集与 revision。最新候选不自动替换最佳结果。
- **结构化状态**：当前 SO 元数据、Run 登记、Evidence 及关联、验证范围和人工验收结论。代码、知识、trace 和任务正文继续放文件，不与其他 SO 的状态混合。

具体表按需加入，初期不预建完整 schema。唯一约束覆盖实体 ID、同一源码实体的版本和当前唯一选择，关系使用外键且每个连接启用 `PRAGMA foreign_keys = ON`；其他 SO 的实体不直接作为本库外键。历史名称与引用按其源码版本索引，不能用一个无版本的名称字段覆盖全部历史。

源码索引是派生数据，选择和验收是权威记录，两者在同一个数据库中也有清楚边界。重建前者不清空后者，索引修复不能改变最佳版本或把未验证代码变成已通过。

### 修改与发布：替换当前索引，不只追加

首个需要源码索引的版本使用简单方式：**每次改变当前 SO 的选定版本集，就从该版本集完整重建当前源码索引，在其独立 SQLite 的一个事务内替换。** 不触碰其他版本的目录和数据库。初期不做复杂增量失效判断，规模确有需要时再优化为相同语义的范围替换。

1. Agent 修改草稿，经同一发布入口写成新的不可变版本文件；多文件修改一起提交。现有已登记文件保持不变。
2. 解析声明注释、实际名称、来源和可确定的引用，计算文件哈希，准备登记结果。声明 ID 缺失、重复、binary 上下文不符等情况拒绝登记；不以一次不完整扫描清空正常索引。
3. 保存候选时只登记该版本及其索引，不改变当前最佳选择。选择新最佳版本时，发布入口串行读取当前 revision，构造完整的目标版本集，检查其中声明 ID、命名作用域和引用是否一致。尚不能解析的间接或外部引用保留为显式 unknown/外部目标，不能伪造绑定。
4. 开启 SQLite 事务，登记新版本、更新选择，删除旧的“当前源码索引及其派生来源/引用”，插入完整目标集合并递增当前 SO 的 revision，一次提交。任何校验或写入失败都回滚到旧选择与索引。每次 Web 读取在同一数据库读事务中取得 revision、索引和文件版本，再读取对应不可变文件。

这不是删除整个数据库重建。原始函数索引、候选和历史版本、证据、Run 与验收不随当前源码索引一起清空。原始静态清单需修正时，完整扫描结果替换其声明范围内的当前索引，片段分析仅更新明确范围；不能把尚未扫描到或尚未还原的函数误删。

例如删除或拆分一个声明时，旧声明及其旧名称、文件位置、来源和调用边会退出当前源码索引；新的集合完整写入，不依靠 Agent 记得逐条删旧行。仍在当前版本中调用已移除声明的代码必须一起修正，或明确保留未解析引用及未完成状态，不能静默丢掉这条调用。

### 历史、异常修改与恢复

保留的历史不是残余数据：被版本、Run、Evidence 或任务引用的旧实体和文件仍可回溯，但历史查询与当前查询分开，不能作为当前函数返回。未登记的临时文件或没有任何保留记录引用的孤立索引可在显式整理时清除；不为消除“旧数据”删除仍有验证价值的反例或历史来源。

支持的源码更新方式是“编辑草稿 → 发布新版本 → 同步索引”。发布中断时，数据库仍指向完整旧文件；先写好的未登记新文件不会被 Web 当作当前结果。无需文件系统与 SQLite 的分布式事务。

不依赖常驻文件监听保证一致性。启动、显式同步及 Web 读取目标源码时检查登记哈希；如果已登记文件被外部原地修改或删除，明确显示不同步/文件缺失，不继续展示该文件的旧名称索引、旧位置或通过结论。变动作为新版本重新发布，或恢复原文件后再读取；不能把新内容冒充原已验证版本。校验只读取实际需要的文件，不每次全量重新索引所有资料。

提供一个显式校验/重建源码索引的操作：从登记的选定版本集校验文件，重建派生表；失败时保留原选择并报告具体文件或引用问题。先用“改名、移除声明、合并、拆分、发布中断、外部改文件”这些小例子逐项验收，再考虑增加索引功能。

## 还原源码与二次开发

先选择一个函数或明确的功能范围，恢复其真实运算、分支、数据结构和副作用，逐步扩大覆盖范围。VM 还原应把已解析的虚拟指令行为组织成可读逻辑，消除仅为混淆服务的分派与状态跳转；必要的算法状态和数据仍须保留。单纯翻译原解释器、继续用原 SO 代算，或只复现少数输入的输出，都不足以完成该范围的源码还原。

分析中允许保存不完整伪代码；最终交付的范围需具备明确的函数接口、必要类型、全局状态及外部依赖，能按说明构建并独立调用。语言先根据二次开发需要选择一种，不建设多语言生成框架。JNI 和环境接口尽量与恢复出的核心逻辑分开；未还原调用或占位实现明确标出，依赖这些占位的路径保留未验证状态。

持续用 unidbg 执行原函数，并在相同输入、初始状态和可比环境下运行还原实现，比较返回值、输出内存及相关外部副作用。差异反馈给 Agent 继续调查。记录测试范围及未覆盖问题；人工阅读验收和运行验证分别保存，不能用“看起来合理”代替执行比较。

### 函数级差分的最小约定

首个可执行闭环采用 C/C++ 候选编译成 ARM64 SO，在两个独立 unidbg 实例中分别运行原始实现和候选实现。共享 harness 的状态准备规则，两边内存、对象和运行状态独立；不在同一份可变状态上先后调用。后续交付语言可按实际需求调整，不预建多语言运行框架。

```text
                         同一用例与状态构造规则
                          ↙               ↘
原始 SO → unidbg A → 原始观察         候选源码 → ARM64 SO → unidbg B → 候选观察
                          ↘               ↙
                       比较 → 保存差异 → Agent 修正
```

候选构建保存实际源码版本、构建命令、编译器版本与选项、生成物哈希。候选入口按其实际符号或入口映射调用，不能沿用原始 RVA；原始 RVA 只用于关联与追溯。候选须正确表达 ARM64 的整数宽度、符号、截断、移位、浮点和 ABI 等相关语义，避免 C/C++ 未定义行为使结果随编译选项改变。编译失败保留日志并标为未验证，不能跳过执行直接发布通过。

每个差分用例用普通文件和 harness 代码明确以下内容，不增加用例服务或完整环境描述语言：

| 约定 | 最小内容 |
| --- | --- |
| 调用输入 | 参数及类型、指针对象的内容与有效长度、必要的别名关系 |
| 前置状态 | 初始化和历史调用顺序、相关全局/TLS、JNI 对象状态 |
| 环境输入 | 实际使用的时间、随机数、文件与 JNI 响应；按需控制或记录重放 |
| 观察范围 | 返回值、有效输出内存、相关全局变化与声明的外部副作用 |
| 运行依据 | 两边实现及依赖版本、harness、输入、实际构建与运行配置 |

“同一初始状态”指含义一致，不能只依赖重建模拟器，也不要求两边物理地址和内部表示相同。指针、JNI handle 和分配地址按逻辑对象、对象内偏移及内容对应；不直接比较整份内存或原始地址。比较外部调用时记录相关参数、结果和必要顺序，不要求无关内部操作一致。恢复后的实现可以消除 VM 分派，不要求逐指令或逐分支对齐。

最初可由 Agent 在 harness 中为选定函数手写状态准备和比较规则。内部函数无法直接独立运行时，先从可执行入口走到该调用，观察并补齐所需状态；不要求自动捕获任意函数的完整快照。未知状态或不可对应的副作用写入 Unknown，并限制验证结论范围。

### 累计回归与组合验证

每个候选版本在声明的验证范围内重跑已保留用例，失败用例固定为反例。用例数据只保存一份，Run 引用所用用例及其内容哈希；修改用例后保留旧内容。用例可放在现有 `runs/<run_id>/` 中，后续 Run 按引用读取，SQLite 只登记关联，不增加缓存层或测试平台。

Agent 继续补充边界、变异及针对未探索路径的输入；仅反复运行同一小组输入不能扩大验证范围。新的静态、符号或强制执行观察可以指导生成用例，带干预的路径仍需在原始条件下具体重放。

单函数通过后逐步验证调用链、顶层 JNI 入口及连续调用序列。每次 Run 记录实际使用的候选与 callee 版本，并注明哪些调用仍由原实现执行；依赖变化后的旧结果不能自动视为新组合已经通过。分析阶段可以借助原实现处理尚未还原部分，最终声明完成的交付范围应独立执行，剩余依赖和占位明确标出。

“迭代停止”“用例范围内通过”“人工审阅通过”和“语义等价证明”分别表达。双边使用同一 JNI 简化实现时，比较结论也只适用于该环境假设。可维护性另由人工检查：真实运算、分支和数据结构应清楚，不能因复制解释器通过差分就判定已完成逻辑还原。

### 源码导出

交付时由 Agent 将选定代码版本组织成普通源码工程，放到新的 exports/<export_id>，提供最小构建/运行说明，并记录原函数地址、所用版本和验证依据。选中的源码文件按原文复制，保持 Web 审阅、实际构建和交付文件中的名称、代码及身份注释一致；额外构建文件和接口胶水单独提供，不在导出时暗中重写代码。跨函数引用和依赖一起处理，避免只有互相缺失的函数片段。单函数交付可以很小，无需重建整个 SO 才有可用成果。

导出物是独立交付快照，不与分析版本双向同步。每次导出写新目录，不覆盖已用于二次开发的代码。用户从该快照继续开发，LightRE 保留产生它的分析版本和 Evidence。先由普通脚本完成组织与导出，不预建发布平台。

## 证据、知识与可恢复 Context

三者是资料用途，不是三个服务：

- Evidence：工具观察到什么、在什么条件下观察到、原始产物在哪里。
- Knowledge：Agent 或人工的当前理解、假设、冲突和下一步，用 Markdown 表达。
- Context：当前任务需要读取的代码、知识和证据，由 API 读取返回，Agent 再选择使用。

### 证据

每份 SO 有独立证据库，一条记录可以关联该 SO 的多个函数、全局变量或调用点。例如“调用点 A 调用了函数 B”只保存一次，双方都能查到。公共知识引用其他版本证据时使用“SO 身份 + Evidence ID / Run 路径”，不复制成当前 SO 的观察，也不继承其验证结论。

最少字段为 `id、run_id、kind、summary、data、artifact_ref、status`。类型区分 static、concrete、symbolic、forced、differential。输入、环境、初始状态和干预记录可引用所属 Run，不重复复制。

只把需要继续使用的观察登记为证据，不把每条指令或每个 trace 事件写进 SQLite。大量事件保留在运行文件，用路径及行号、偏移或事件范围定位，需要时分段读取。不建设通用 trace 查询引擎。

原始产物保留。证据错误时更新其有效状态和更正说明，原始观察仍可追查；不做追加式事件账本。工具观察与 LLM 假设分开，支持和反驳当前结论的依据都保留。

有后续价值的失败实验也登记 Evidence，不能只保存成功结果。例如缺少 JNI 实现导致中断、间接调用未能解析、候选实现出现差分不一致。Run 保留实际输入、初始化与环境配置、脚本、错误和已有输出；Evidence 摘要指出观察到的失败及其条件。差分反例保留两边实现版本、可重放输入和输出差异，后续候选将其作为回归用例。工具执行失败只说明本次实验未完成，不能推断目标逻辑不存在或不可达。

### 知识与 Context

函数 Markdown 简要记录当前理解、证据 ID、假设与冲突、下一步、人工备注。人工直接用编辑器修改，Agent 更新时保留人工备注。仅在长文需要整理时归档，不给每次编辑建立版本或结论依赖图。

### 跨版本提炼公共知识

Workspace 顶层 `knowledge/overview.md` 是逐步积累的公共 VM 知识，不是各版本知识的合并副本。先在每份 SO 中保留具体观察，再由 Agent 对比多个版本，提炼可复用的设计规律、识别线索、实验方法和已知变体。一个版本产生的通用猜测也可保留，但必须标为假设，不能提前当作已确认共性。

公共条目最少记录结论或假设、适用条件、支持它的 SO 与 Evidence/Run 引用、已知反例或差异。公共条目引用相对 workspace 根目录，并注明原 SO 身份；原始证据仍在各自 SQLite 和 Run 中，不增加公共 SQLite、同步服务或知识继承机制。

分析新版本时，Agent 读取这些条目作为调查起点和待检查清单，优先验证可能复用的规律，从而减少重复摸索。该版本仍需生成自己的观察、知识与验证记录；确认适用、发现变体或推翻旧假设后，再更新公共条目的范围和依据。不能把旧版本地址、opcode、解码参数或“通过”状态直接复制为新版本事实。这样形成“逐版本逆向 → 对比总结 → 指导新版本 → 新证据修正总结”的积累过程。

### Unknown 与失败尝试

保留此前讨论其他工具时关注的“暂时无法处理也要留下记录”这一做法；具体失败案例必须有本项目的实验依据，不把对其他项目的讨论直接写成样本事实。

Unknown 是知识 Markdown 中的“未解决项”章节，不另建数据库、文件层或知识服务。函数问题写入该 SO 目录内的 `knowledge/functions/<rva>.md`，当前版本的环境与共性问题写入其 `knowledge/overview.md`。公共知识中可以保留跨版本规律的疑问及来源引用，但不替代每个 SO 的具体 Unknown；其他位置引用其文件路径和局部编号，不重复维护正文。

每项用稳定的局部编号记录：**问题、状态（open / blocked / resolved）、已尝试方法及 Run/Evidence 引用、当前缺口、下一步或重试条件**。`blocked` 表示有明确缺失条件，不等同于逻辑已还原。未经过实验的疑问也可登记，但保持假设性质。例如：

- JNI 依赖缺失：Evidence 保存缺失签名与调用位置，Unknown 说明还需什么行为或资源才能继续运行。
- 间接调用仍有未知目标：Evidence 保存已观察目标及对应输入，Unknown 保留未覆盖范围和后续探测方法。
- 还原实现差分失败：Evidence 保存反例，知识记录被反驳的假设，Unknown 指向尚未解释的差异。

解决后将原项标为 resolved，补充解决依据，不删除失败尝试。整理知识时保留开放项及关键失败路线的摘要和引用，详细日志仍在 Run。Agent 续做先检查这些记录；没有新输入、环境修正或分析方法时，不机械重复已失败的尝试。无法继续时留下明确缺口与续做条件，不能把失败或未知当成完成。

### Context 读取

提供按 SO 分析目录和函数地址读取 Context 的函数，返回：

1. 当前代码与知识、上次运行状态及续做笔记。
2. 所需汇编或工具参考结果。
3. 当前 SO 的直接调用关系、相关全局变量，以及注明来源和适用范围的公共知识摘要。
4. 关联证据摘要与原始文件引用，包括已知冲突。
5. 相关 Unknown、关键失败尝试及重试条件；长记录保留继续读取的引用。

原始地址关联多个还原声明时，Context 返回相关源码 ID 与版本清单，可再选择一个源码 ID 深入读取，不静默将一个原始 RVA 当成唯一源码函数。

用条数、文本长度和事件范围限制输出，保留继续读取的引用。Agent 决定 token 预算和临时裁剪；不要求系统计算精确 token 或保证跨版本构建完全相同的 Context。

发布代码时登记实际采用的代码版本、证据 ID 和产物引用，必要时保存在 Run 的输入清单中。无需截获外部 Agent 的完整聊天、系统提示词或模型配置。新会话从当前持久资料重建 Context，不依赖原 Agent 的内存。

## Agent 迭代与动态去混淆

```text
打开 SO → 建立/读取函数索引 → Agent 选择函数与问题
                              ↓
读取资料 → 提出假设 → 静态调查或执行实验 → 保存有用观察
    ↑                                           ↓
    └──────── 继续调查 ← 检查候选 ← 重写函数 ────┘
                              ↓
                     发布版本 → Web 自动更新
```

以控制流平坦化为例：Agent 根据汇编提出 dispatcher、状态变量、状态更新和不透明谓词假设，再用 unidbg/Qiling 实验记录状态转换、内存读写及外部调用，必要时结合符号求解或强制执行，恢复有效控制流和数据依赖后重写函数。

先围绕一个选定函数完成“分析—实验—保存—重新打开”的闭环，再扩大到批量。巨型混淆函数内部按问题、地址范围和执行片段调查，不要求一次将全函数汇编放入 LLM。

单次 `codex exec` 内可自主完成多轮调查、实验和函数重写。LightRE 只负责启动、查看进程和收集结果，不为每轮推理重新启动 Codex。进度、停止原因和续做笔记随 Run 保存，轮数或资源预算由调用方控制。中断后可从 Web 重试，由新 Codex 读取检查点继续；首版不做常驻调度器、失败自动重试或函数依赖级联重跑。

Web 评论发起的任务沿用同一迭代流程：Agent 读取评论、代码和已知失败项，优先用 Rizin 补充静态信息，按需用 Ghidra 深入分析，调整 unidbg harness 或输入进行实验，根据新证据重写并比较候选。每轮围绕具体问题推进，不要求每轮调用全部工具，也不要求每轮都生成代码。一次提交可完成多轮工具分析，直到处理目标完成、缺少继续条件或耗尽预算；仅改名、润色或回复评论不足以完成需要验证的逻辑调查。

知识或证据改变时，由 Agent 检查相关函数并标记待复查。复查标记与最佳代码发布互不阻塞，不要求所有调用者立即重新分析。

动态与验证能力按实际实验逐步接入，首先打通 unidbg 可重跑 harness 和基本差分闭环，再按需要加入 Qiling、符号执行、强制执行及更广的验证。不要求每个函数经过所有工具。

强制执行记录干预，不能据此断言自然可达。符号求得的输入尽可能具体重放。差分比较返回值、输出内存和声明的副作用，并保存输入及环境范围；没有可执行候选就保持未验证。有限测试通过不等于全函数已证明等价。

## Agent 生成与共享 unidbg harness

Harness 按实际兼容的一组 SO 共享，放在用户选择的 `workspace/harnesses/<name>/`，不放进 LightRE 工具仓库，也不按 SO 的哈希复制工程。同一应用或库的多个版本可以复用兼容的 JNI 与初始化代码；差异用当前 SO 的少量参数或普通 Java 分支处理，差异很大时才另建 harness。它是普通 Maven 工程，不是插件或继承体系；LightRE 通用代码只负责启动和收集输出。

```text
<用户选择的 workspace>/
  harnesses/example-lib/
    pom.xml                             # 固定 unidbg 及实际使用的依赖版本
    README.md                           # 运行接口、使用方法与逐版本兼容记录
    src/main/java/
      TargetHarness.java                # 建模拟器、加载 SO、初始化、分派实验入口
      TargetJni.java                    # 可兼容多个版本的 JNI 行为
  libexample-a1b2/
    binary/original.so
    harness.json                        # 指向 ../harnesses/example-lib
    dependencies/                       # 该版本需要的依赖，按需添加
    runs/<run_id>/
      harness/                          # 实际执行的源码、pom 和配置副本
      request.json                      # 选定入口、参数、实验选项
      ...                               # 命令、工具版本、日志、trace 和结果
  libexample-c3d4/
    binary/original.so
    harness.json                        # 指向同一工程，参数可以不同
```

`harness.json` 是关联和版本参数的唯一来源，不另建 harness 注册库。例如：

```json
{
  "path": "../harnesses/example-lib",
  "parameters": {
    "api_level": 23,
    "process_name": "com.example.app",
    "entry_rva": "0x1c07c"
  }
}
```

字段随实际 harness 需要增加，不预定义完整 Android 环境模型，也不建立多层配置覆盖。原始分析目标默认是所选 SO 目录的 `binary/original.so`，由启动入口传给 harness，不在共享 Java 源码中写死。差分运行另外显式指定候选构建产物、入口映射和所用版本，不修改原始样本身份。RVA、依赖文件、初始化差异等按当前 SO 的参数解析；不能把一个版本的地址原样用于另一个版本。共同使用的 APK/资源可以保存一份并引用相同文件，无需每个 SO 目录都复制。

Harness 的创建本身就是 Codex 任务：先读取已有关联；没有时检查可复用的 harness、JNI 签名和输入资料，适配或生成最小工程，编译运行，按缺失 JNI 逐步补全。成功完成选定入口实验后再记录该 SO 的兼容情况；失败时保存缺口和下一步，不要求人工预先提供可运行工程，也不保证从 SO 自动恢复全部 Java 依赖。选择和适配交给 Agent，不开发自动匹配服务。

`TargetHarness` 负责建立 Android 模拟环境和 VM，设置 JNI 实现，按样本需要加载依赖、执行初始化及 `JNI_OnLoad`，再调用选定入口。初始化顺序是样本逻辑的一部分，不要求所有函数都能从任意状态独立调用。JNI 导出或动态注册的方法按类名和签名调用，内部函数按模块加载基址与 RVA 定位，并显式准备 ABI 参数和所需状态。

`TargetJni` 集中实现这些版本所依赖的类、方法、字段和对象状态。例如签名 `android/content/Context->getPackageName()Ljava/lang/String;` 可从当前 SO 的参数返回包名；影响逻辑的 Java 方法需要相应实现或有来源的实验输入。存在 APK 时可以用于类信息、资源及包信息，但不代表 unidbg 会自动执行其中任意 Java/Dex 方法。

补 JNI 按具体运行缺口迭代：记录缺失的类/方法完整签名和调用位置，Codex 读取汇编、APK 或已有知识后补实现，再重跑同一个实验。未实现的方法默认明确失败，不统一返回零或空对象。由配置提供的环境值、简化实现、Hook 和强制修改都要记录；依赖假设的观察注明条件，不能把为了跑通的返回值当作真实设备证据。

不同版本及同一 SO 的函数可共用初始化与 JNI 代码，通过目标 binary、各自版本参数、选定入口和输入运行不同实验，不假定所有版本的初始化或 JNI 行为相同。代码可共享，内存状态不共享：每次实验默认新建模拟器；同一次有意连续调用则记录顺序。实验少时直接在 Harness 中写几个具名入口，复杂后再拆普通 Java 文件，无需一开始建立用例框架。

共享 harness 是 Codex 持续修改的唯一工作版本，同一工程的生成和修改先串行处理。Run 中的副本只用于复现历史，不作为第二份可编辑主版本。执行前保存实际源码、pom 和当前 SO 参数的小型副本，并从该副本构建运行；输入、命令和实际工具版本随 Run 保存，原始 SO 身份从该 SO 的 SQLite 元数据读取。依赖 SO、APK 和大型资源按路径与哈希引用，保留用过的原文件，内容变化则另存文件；不复制 Maven 依赖缓存或整个构建目录，也不为每个 SO 维护独立源码分支。

所有输入路径相对所选 SO 分析目录解析，执行入口显式传入该目录，不依赖 Java 进程的当前目录。重放旧 Run 使用保存的 harness、参数与输入，不能默默改用共享工程的当前版本。运行接口与使用方法记在 harness 的 README，具体 JNI 假设、运行缺口和函数前置状态记在该 SO 的知识中。一个版本的运行证据不自动成为另一个版本的证据，共享代码后仍需对目标版本验证。不另建 JNI 数据库、跨版本证据同步或代码继承系统。

## Web 评论到 Codex 执行

用户在函数页面发现问题后，填写评论并点击“提交并执行”，可选附上选中的伪代码片段。后端先创建独立的 `tasks/<task_id>.md`，保存用户实际正在查看的版本，再启动非交互 Codex 并立即返回任务信息。历史视图中的评论也绑定该历史版本。可选保留“仅保存”用于稍后执行。

任务保持为普通 Markdown，例如：

```markdown
---
function_rva: 0x1c07c
source_id: f001
viewed_version: v004
status: pending
---

# 核查状态转换

## 用户评论
这里的分支似乎被错误合并了，请结合 unidbg 调查状态更新并修正。

## 选中片段（可选）
这里保留用户看到的伪代码原文，仅用于定位疑问。

## 处理结果
待执行。
```

最小流程：

```text
Web 评论 → 保存 task.md → codex exec → 分析/实验/发布代码
                              ↓                    ↓
                         运行日志             任务处理结果
                              └──────── Web 展示 ──┘
```

非交互命令是 `codex exec`；`-p` / `--profile` 用于选择配置 profile，不是提示词参数。执行入口固定在项目目录启动，将任务文件的绝对路径与处理约定通过 stdin 交给 Codex。已有登录和模型配置沿用本机 Codex 配置，无需 LightRE 直接接入模型 API。

例如下面的命令形态，`<run_dir>` 由执行入口创建，`prompt.txt` 包含任务路径、读取项目规则、保存分析产物和回写任务结果的要求：

```bash
codex -a never exec -C /work2/LightRE --sandbox workspace-write \
  --json -o '<run_dir>/codex-final.md' - \
  < '<run_dir>/prompt.txt' \
  > '<run_dir>/codex-events.jsonl' 2> '<run_dir>/codex-stderr.log'
```

实际实现用 subprocess 参数列表及 stdin/stdout 文件调用，不把评论拼接成 shell 命令。项目目录从当前安装位置获取，不硬编码 `/work2/LightRE`。工作区在项目外时显式加入所需写入目录；权限由部署配置一次确定，执行时不等待终端交互，需要但无法执行的操作记录为失败或阻塞。

本机已核对 `codex-cli 0.162.1` 的帮助；参数依据为 OpenAI 官方[非交互运行](https://developers.openai.com/codex/noninteractive/)与 [CLI 参考](https://developers.openai.com/codex/cli/reference/)。这里是接入设计，不代表已经启动了任务。

Agent 读取任务，确认样本、函数地址和评论对应版本，再调用 API 读取知识与证据，按疑问编写或调整调查脚本。如果当前最佳版本已经变化，同时对照被评论的旧版本和当前版本，避免把旧问题套用到新代码。评论表达调查目标或人工假设，不直接作为已验证证据。

Codex 执行静态分析或动态实验，按原流程保存证据与代码版本；在任务文件中保留原始评论，补充采用的 Run、Evidence、输出版本、结论及未解决问题。执行入口在启动前和退出后更新任务状态（`pending / running / done / blocked / failed`），Codex 运行期间只更新结果正文，避免两个写入者同时修改状态。退出码为零也需有任务处理结果，不能直接等同于问题解决或语义验证通过。中断续做资料保存在关联 Run。

对需要进一步验证的评论，Codex 在同一任务内继续多轮静态调查、unidbg 实验与差分，不以一次回复作为结束。暂时无法解决的问题写入所属知识文档的 Unknown，任务结果只引用该项及失败 Evidence，注明停止原因和继续条件；后续从 Web 再次提交或重试时读取已有尝试继续调查。

接入 Web 任务执行的首个版本，同一 workspace 只运行一个 Codex 任务，避免并发修改共享 harness；忙时可保存新任务，空闲后从 Web 点击执行，不做自动排队。执行入口在现有 Web 后端进程中管理子进程，不能阻塞 HTTP 请求；不增加 Redis、Celery 或独立 Worker 服务。后端重启后将遗留运行标记为中断供用户重试，先确认旧进程已结束，避免重复执行。这是后续任务能力的约定，不纳入 V0.1。

任务所属 SO 由其分析目录下的 `tasks/<task_id>.md` 位置确定，文件内记录原始函数 RVA、被评论版本和任务内容；查看还原代码时同时记录源码 ID，避免合并或拆分后评论定位不清。原始汇编尚无源码实体时可省略源码 ID，不重复保存原始 SO 的 SHA256。任务文件不复制完整函数或整个 Context，所需资料按身份和版本读取。任务正文和业务状态只维护在 Markdown；Run 保存进程退出、日志及产物，不另存一份可独立修改的任务状态。用户可在未运行时编辑任务要求；Web 查看任务时直接读文件。任务状态和日志按需轻量轮询，代码发布仍通过该 SO 的 revision 自动刷新。默认在 Web 看结论、证据及代码差异，原始 Codex 日志折叠显示，手动进入聊天会话仅作为可选排查方式。

## Web

Web 针对当前选中的 SO 版本查看和验收还原逻辑，使用该 SO 的 SQLite 和文件，不将多个版本的函数混在一个列表。界面保持 FastAPI 和简单 HTML/JavaScript：左侧函数列表支持名称/地址搜索，右侧从实际源码文件读取当前最佳还原代码或分析中伪代码，显示当前 SO、文件、原始地址关联、源码 ID 和版本，提供调用导航、工具参考及历史版本切换。函数合并或拆分后可按原始地址找到关联的源码声明，阅读同一份定义。

主视图明确区分“分析中伪代码”和“可执行还原源码”，简要显示验证范围与未解决问题。人工可对正在查看的具体版本标记“通过”或“待改”，意见沿用评论任务。验收结果绑定版本，新版本不继承旧版本的人工通过状态；验收不阻止 Agent 继续实验和生成候选。

导入框填写 SO 路径后，显示所选 workspace、SO 分析名称和来源资源目录；名称可编辑，在所选位置创建名称加短 SHA 的 SO 目录。Workspace 路径来自本次用户选择或已有上下文，不硬编码。来源目录只是查找资源的起点，不意味着其中每个文件都参与本次实验。已有 SO 的显示名称也可在 Web 修改，目录路径保持稳定。

代码区域只读，另有一个简短的评论输入框和“提交并执行”按钮。任务可在 Web 执行、重试并查看状态、结论和处理结果。人工反馈后，Agent 继续多轮工具分析与运行验证，证据和代码发布后页面自动更新，人工再审阅和反馈。Unknown 与失败记录沿用折叠的知识、依据和任务结果展示，不新增常驻面板。复制文件路径或提示词只是备用方式，不是日常操作的前置步骤。

默认折叠依据，展开查看证据摘要或 Markdown。未生成代码时显示待分析，已有函数仍可浏览。列表是“当前识别函数”，不要把它描述成已找到 binary 中所有函数。

页面每隔约 2 秒查询当前 SO 的轻量 revision 和进度，有变化再读取当前需要的内容。当前最佳视图自动更新并保留位置，历史视图不被替换。切换 SO 后使用另一套索引和状态。函数列表无需每次轮询重载，较长代码按需读取，trace 不进入常规页面响应。

进度显示当前阶段、已处理函数数及停止原因，不显示“正确性百分比”。Agent 通过 API 更新 Run 进度，Web 读取同一持久数据。打开新 SO 可先用本地路径，上传流程不作为首版前置要求。

## 实现顺序

每次只交付一个能运行、能由用户直接验证的小增量，交付后由用户体验和反馈决定下一步。P0/P1/P2 是长期需求分组，不是一次完成的开发批次。具体步骤与验收例子以 [小步实现计划](IMPLEMENTATION_PLAN.md) 为准。

第一版只完成“Skill 聊天给出目录或 SO → 按用户上下文定位或创建可见的外部 workspace → Agent 启动当前 SO 的 Web → 列出已识别函数 → 搜索名称或 RVA → 点击查看原始汇编”。一份最小 Skill 说明、一个页面和最少读取接口即可；先不引入完整多版本管理、代码版本、自动刷新或动态分析。外部目录位置从首版就遵循约定，SQLite 与公共知识按需加入。底层启动命令由 Agent 执行，巨型函数分段读取，原始汇编本身就是首版的可用产物。

随后按反馈逐项加入单函数候选展示、持久化、知识、一次 unidbg 运行、Evidence、候选执行和差分。Web 评论和自动刷新也分别作为可验收的小增量，不把整套自动化作为首版门槛。不为未来能力预写空接口或完整数据库。

逐步形成一个函数的“读取 → unidbg 运行 → 保存证据 → 重写可执行代码 → 比较 → Web 人工审阅与反馈 → Agent 多轮分析/运行/比较 → 再审阅”闭环，满足选定范围的验收后交付源码。中途失败或无法解决时保留 Evidence、Unknown 和续做条件，并确认新会话能续做。

进入差分能力的开发时，先用一个小函数验证构建、状态准备、比较、反例保存和修复回归，再选择真实强混淆样本中的一个明确逻辑入口验证还原效果，随后扩大到调用链。每一步均单独交付，不等整个闭环写完才提供可运行例子。

## 首次开发任务与完成条件

首次只开发 V0.1。以 `/work2/dg-samples/dC6BDAE/libdC6BDAE49562F.so` 为实际验收输入，路径通过聊天请求解析，不写死在工具代码中。
