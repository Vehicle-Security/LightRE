# 逆向源码恢复与逐轮整理指令

接入状态：后续工程恢复模板，尚未被当前 V0.2 worker 加载。当前首轮、评论和汇编恢复提示分别由 src/recovery/prompts/ 下的 INITIAL.md、FEEDBACK.md 和 ASSEMBLY.md 提供，代码填入任务上下文，仍要求只读分析并返回逐函数 JSON；不能仅因本模板存在就直接改写已登记源码或启动工程 Goal Loop。

适用范围：明确包含 VM/业务源码恢复的后续工程任务。V0.31 的 harness 修复只使用本版窄范围任务指令，不整体加载本模板，不要求恢复 VM、编译候选、双边差分或自动提炼知识；实际范围以执行器提供的原始任务为准。

你负责恢复当前任务范围内 VM 混淆承载的真实业务逻辑，重点解决控制流平坦化与 MBA（混合布尔算术）混淆，并随着语义恢复整理文件、类型、接口及命名。目标是可编译、可独立运行、可维护的等价工程；仅让原 VM 可运行、翻译解释器或润色候选不算完成，不要求猜中原作者的名称。

当前运行范围仅为 ARM64，动态执行统一使用 unidbg。minilua 使用独立构建的 Android ARM64 SO 与纯 C 测试接口，保留原 Linux ELF；DG 按需准备 JNI。不要自行接入 Qiling、其他架构或多后端平台，不将现有 Linux glibc ELF 当作 Android SO。新构建与候选分别记录实际入口、哈希和工具依据，尚未跑通时如实保存缺口。

这是为 LightRE 后续 recovery 工程流程准备的指令。接入时由执行器拼入 `codex exec` 的单轮输入，并在其后提供当前任务说明与本轮上下文，至少明确目标 SO 分析目录、原始任务路径、可编辑源码目录、本轮结果目录和已有检查报告的位置。没有历史报告时明确标为首轮。原始任务应约定交付范围、构建与行为检查方式、允许修改的路径。若缺少影响正确执行的信息，先完成不依赖它的调查，并在结果中列明缺口；不能自行选择另一个 SO、扩大写入范围或假定验证已通过。

## 每轮开始

1. 读取项目适用的 AGENTS.md、原始任务、当前源码、相关知识和最新实际检查报告。确认本轮使用的 SO、源码及证据属于同一目标。读取上一轮完整返回与执行情况，不只依赖会话记忆或派生摘要。
2. 核对上一轮修改是否仍存在、检查报告是否对应当前内容。存在代码或报告变化时，以当前文件重新判断，过期的通过结果不能沿用。
3. 选择一个有具体产出的工作范围：功能入口及必要调用链、共享对象的一组操作，或检查报告指出的跨文件问题。说明这轮要解决什么，以及用什么检查判断结果。
4. 优先修复构建失败、行为反例、跨函数类型和引用冲突，再处理缺失语义及职责整理。已通过验证的部分不因轮次增加而反复换名、搬文件。
5. 读取调用方提供的上一轮结果、外层实际检查及相关旧失败。模型自评与实际观察冲突时先处理冲突，明确应修正的假设或方法；不要在相同条件下机械重复失败尝试。基础设施失败不作为语义假设被反驳的依据，条件改变后允许有理由地重试。

VM 任务按 LightRE 仓库中的 [语义恢复里程碑](../VM_RECOVERY.md) 选择本轮范围：M0 可重放入口与边界、M1 取指、M2 解码、M3 dispatch、M4 指令语义、M5 逻辑控制流、M6 业务源码。结合任务提供的工具仓库路径读取该文档，明确当前阶段、适用入口/状态、已有模型、证据和待检查差异。每阶段要能预测并核对新的实际行为，不能只标注旧 trace。取指与分派相互依赖时允许联合调查，反例出现时修正既有结论；不将阶段数量等同于轮次，不等待全部 opcode 恢复才开始短片段差分。

## 分析依据

汇编、工具导出、内存访问、实际运行和差分结果是依据；Ghidra 伪代码、现有候选和既有语义名称均可能有误。区分直接观察、推断和未知项，保留反例及冲突。

按需读取调用者与被调用者、参数流、全局状态、常量表、对象分配和释放、字段访问、字符串与导入 API。只读取当前问题需要的材料，不要求每轮扫描整个 SO。

混淆分派、解释器、handler 和原生函数边界可能不对应最终业务边界。允许依据实际行为合并、拆分和抽取 helper；保留原生 RVA、字节码入口或派生来源的追溯关系。不能把字节码偏移当作原生 RVA，也不能凭一次运行认定覆盖了所有路径。

## VM、控制流平坦化与 MBA

每轮优先解决阻碍业务语义恢复的具体问题。以下方法按可用工具和证据选用；缺少执行环境或求解器时说明缺口，不能虚构工具结果，也不能将多轮 LLM 推断写成验证通过。

先明确实验方式：合法字节码运行/差分、输入或字节码 fuzz、强制执行。区分虚拟程序 P、业务输入 I、初态 S 和环境 E，记录相关常量、元数据及解码上下文。解释器模型差分双方执行同一个 P；固定 P 的业务候选不能作为变异 P 的预期。没有完整合法字节码生成器时，可以从有效前缀到达局部边界后强制探索，记录干预与状态缺口；对应边界和干预均有依据时，可做受控局部状态比较，但不能宣称原程序自然可达或未干预等价。首批真实目标使用现有输入：DG 的 4 份 `.bin`；minilua 的 `.lua` 用例，由匹配解析器生成内部 Proto/字节码，不要求另造生成器或外部 luac 加载器。资源可用不代表 unidbg 已完成相应加载和状态适配。

差分粒度可选完整函数/逻辑入口，或双方已有语义映射的字节码进度分段。分段在一致阶段的检查点比较相关状态及段内副作用；记录调用实例、逻辑位置和事件序号，不能按 ARM64 指令数或 VPC 大小直接对齐。循环、递归、融合指令和潜在滚动解码状态需显式处理，后者仍作为待排查机制。候选没有对应 VM 边界时回到较粗业务边界；控制流分歧保存为差异，不跳过不同路径寻找相同 VPC。连续回归让候选沿自身状态推进，不每段注入原实现状态；局部前态驱动检查与完整入口回归分别报告。

- **VM 语义**：识别取指与解码、字节码位置、虚拟寄存器/栈、handler 及外部调用。按选定逻辑入口和实际上下文记录状态转换，区分原生控制流、虚拟指令控制流与业务控制流。共享 handler 在不同上下文的含义需分别核对，最终把虚拟行为组织成业务逻辑。
- **解码状态**：滚动密钥或历史相关解码是待排查的可能机制，不是已确认的样本事实。检查解码的真实数据依赖，有证据时恢复状态来源、更新顺序及分支/循环等位置的衔接，不预设 XOR、固定 key 或逐指令更新。使用有效前态连续预测多步并与原实现核对，不能每步注入 trace 的后续状态。没有相关依赖证据时保留简单模型及验证范围。存在状态依赖时，不仅按 VPC 缓存或合并节点；强制改变路径须核对相关状态及内存是否相容，不能只改 PC 便假定实验有效。
- **平坦化**：OLLVM 包含多种变换，不将其全部等同于平坦化。定位 dispatcher、状态存储及更新、条件和真实工作块，对后继目标与状态更新做反向切片，恢复工作块入口到真实后继及出口状态的局部关系，再用 unidbg 核对条件与转移。绕过分派时保留沿途的有效状态更新、内存和调用副作用，多层平坦化逐步处理。VM 正常分派不自动等于额外混淆；单条 trace 不等于完整 CFG，未走到的边不能当作死代码。
- **MBA**：优先提取影响分支、分派状态、内存地址和输出的表达式。保留实际位宽、W/X 零扩展、截断、溢出、移位及必要标志位语义，保留内存与调用副作用；结果等价不自动表示 NZCV 等标志等价。先常量传播、规则化简，再按需规范化、分解并用 SMT 位向量检查候选，不假定一次 simplify 自动恢复最简表达式。随机采样仅用于筛错；在明确前提下检查两式不等，SAT 保存反例，UNSAT 仅说明该模型与前提内等价，超时和 unknown 保持未验证。生成 C 时避免引入未定义行为。
- **动态与强制探索**：原实现实验优先通过输入和环境驱动；必要时在明确位置修改状态探索目标路径，并记录修改前后状态、前置条件和干预位置。强制结果不能证明自然可达，也不能充当未经干预的行为基准。求得的输入尽可能在原实现中具体重放；不假定 unidbg 自带符号执行或状态快照。
- **联合推进**：MBA 化简可能暴露真实后继，路径条件又可能帮助化简 MBA，按具体问题交替推进。每轮留下可追溯的状态转移、表达式候选与验证、反例或明确缺口，避免只反复改名。最终仍需对恢复源码进行构建与行为差分，局部表达式等价不能代替整体业务验证。

## 文件与接口

- 优先按职责、共享状态及对象生命周期形成模块，调用关系作为补充。namespace、调试信息和路径字符串可提供线索，需核对来源；内存段、地址邻近及固定函数数量只适合生成初稿。
- 公共分配器、日志、通用工具函数不能成为把所有调用者合并的依据；共用一个大上下文也不等于同属一个模块。
- 文件开始可以较粗，职责与依赖清楚后再拆。模块内部 helper 使用内部可见性；只有确实跨模块使用的接口进入头文件。内部类型尽量留在所属模块，避免创建无所不包的公共头文件。
- 移动文件时一并调整 include、声明、调用和构建清单。不能只改变目录或文件名便宣称模块化完成。

## 类型与结构体

先恢复可支持的布局，再确定语义名称。综合对象分配大小、字段偏移、访问宽度、读写用途、初始化、传参和释放关系，说明字段的来源及尚未确定的部分。

- 相同布局不自动合并成同一个类型。相同偏移必须先确认对象身份；注意指向对象内部的指针、嵌套结构、数组、union 和不同调用上下文。
- 未知字段保留 `field_18` 等中性名称或明确的未知区域；不透明对象按需保持不透明。不要为满足编译而猜测整套布局。
- 区分字节数、元素数、容量、标志和枚举；注意整数宽度、符号、指针宽度、对齐与别名约束。不能通过强制转换或 packed 属性掩盖尚未解决的布局冲突。
- 与原 SO、JNI 或 harness 交换内存的类型保持所需 ABI；独立源码内部类型在行为验证支持下可以重设计。单纯改名与改变布局、字段类型分别说明，后者需要相应行为验证。
- 公共类型和字段的变更要覆盖全部相关使用者。冲突无法解决时保留证据与缺口，不强行统一。

## 函数、变量与字段命名

名称表达已理解的职责、数据来源、用途及单位。先理解参数、返回值、对象和跨函数数据流，再处理函数内临时值。

- 同一寄存器或栈槽可以承载不同逻辑变量，先按定义与使用区分再命名；多个临时值也可能属于同一个逻辑变量。
- 名称具体程度不得超出证据：确认后使用 `remaining_bytes`、`write_cursor` 等名称；含义不足时使用 `buffer`、`flags`、`field_18` 或原临时名，并说明未知含义。
- 参数角色沿真实调用关系核对，不要求所有函数使用相同局部名称；跨文件公共接口、类型和字段必须一致。
- 同时修改声明和绑定到该声明的引用。不能全局字符串替换，不能误改日志文本、协议字符串或无关作用域中的同名变量。
- 改名或移动保留已有稳定源码 ID，原始 RVA 用于来源追溯，不强制进入最终名称。类型需要稳定引用时可沿用项目的类型身份约定；无需给每个局部变量建立全局身份。真正合并、拆分遵循现有身份与替代关系约定，不让旧 ID 静默变成另一个实体。

## 修改、验证与知识保存

在任务授权的源码范围内直接完成调查和修改，不只提出建议。涉及同一逻辑变更的定义、引用、类型和构建配置一起处理，不留下一半新接口、一半旧接口的结果。

原始 SO、固定验收依据、已有反例及用户工作不得被改写以换取通过。存在版本发布入口时遵循它；尚未接入工程发布时，只修改调用方明确提供的草稿或独立工程副本，不原地改写已登记的不可变版本，也不绕过当前逐 RVA 候选保存流程修改分析工作区。

对修改后的实际文件执行任务已有的构建及受影响行为检查，并重跑相关累计反例。跨文件共享类型变更扩大到所有受影响调用者。改名和搬文件优先复用现有检查，不为低影响整理新增镜像实现的测试。没有可运行的行为检查时，报告已执行的静态检查和验证缺口，不能声称等价。

任务包含候选编译、运行或差分时，结合 [构建与验证 workflow](BUILD_AND_VERIFY.md) 执行：固定输入、逐次保存构建、检查 ELF/ABI、unidbg 调用和行为回归。在一次 exec 内持续处理具体失败；本轮结束后由外层执行器独立核验并决定是否续跑。

对当前问题按需补充实验和可复现用例。保留有价值的失败和新反例；实验失败本身不证明目标逻辑不存在。通过只适用于实际检查范围，编译成功、命名更清楚和模型判断均不能代替行为验证。

有新增理解或假设变化时，更新现有知识位置，写明实体或字段定位、证据路径、当前解释、冲突和下一步。沿用当前 knowledge.md 约定，不另建一套名称或知识数据库；源码中的名称是事实，索引按现有流程派生。

修正旧结论时引用原尝试、反例和新证据，说明旧判断为何不再适用，并保留修正关系。知识正文保留能继续调查的具体观察、前提与失败做法，不只累积“已解决”主题摘要。当前代码、harness 或输入改变后重新检查旧结果是否适用，不把会话记忆当成当前文件的验证。

## 本轮结束

最终输出一份可独立理解的 Markdown 本轮报告，由调用方将完整最终正文原样保存为本轮 `result.md`；不要求额外提取摘要或记忆。报告应包含：

- **本轮问题与结果**：选择的范围、实际解决内容，VM 任务注明所推进的里程碑及依据，是否存在新反例。
- **修改产物**：实际文件路径、相关源码 ID/RVA，以及文件归属、名称、类型判断的依据；未修改源码时说明新增调查结果。
- **验证**：执行命令、结果、日志位置及所检查的源码版本或内容依据。未执行和失败的检查分别列明。
- **未解决项**：沿用已有问题引用，保留已尝试方法、冲突、缺失输入及验证范围。
- **结论修正**：本轮支持、反驳或仍待验证的旧假设，引用原记录与新证据；失败实验尚未运行到目标时明确说明，不据此否定语义。
- **建议下一轮**：依据当前缺口给出一个具体工作范围、所需材料和预期检查；范围已满足时说明完成依据，无需强行制造改动。

外层执行器负责核对产物、维护任务状态和决定是否续跑。不要替它写入 complete 或伪造通过报告，不启动另一层 Codex 循环。不存在阻塞且本轮范围内仍有可以直接完成的工作时继续处理，不以“建议下一轮”代替本轮必要修改。
