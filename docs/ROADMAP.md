## 完整闭环的用户结果

用户提交一次目标 SO、选定入口、相关输入和交付要求后，工具自主调查并运行原实现，整理和构建该范围的候选，在独立环境中执行双方；发现差异时保存反例并自动修复，最终交付有实际验证依据的源码与复现资料。

首个闭环以一个状态可准备、边界明确的函数或逻辑单元为目标，同时保留目标 VM 的原始运行记录；不要求一次还原整个 VM 或编译整个 SO。DG 使用匹配版本的现有 .bin，minilua 使用 .lua 并由自身解析器生成内部 Proto，不把生成器或外部 luac 加载器设为前置。

动态后端当前限定 ARM64 + unidbg。纯 C 与 JNI 的状态准备由目标 harness 承担，不增加 Qiling、其他架构、多后端平台或目标注册服务。minilua Android 源码适配继续维护在原 samples/minilua，保留 Linux 样本。

## 能力引入顺序

D1–D4 是工具能力顺序；[M0–M6](design/VM_RECOVERY.md) 是单个 VM 的分析进度，二者不一一对应，也不是产品版本号。

### D1：候选构建、函数差分与反例修复

由 [V0.3 第三阶段计划](milestones/v0.3/PLAN.md)承接：先完成原实现的可重放运行，再选择一个状态可准备的真实逻辑单元，接通候选构建、双边差分及反例反馈修复。具体开发拆分、产物和验收条件只在该计划维护，技术契约见[动态差分设计](design/DIFFERENTIAL_EXECUTION.md)。

原实现可重复运行后，可对普通参数、缓冲区及环境输入做初步变异，记录种子与新观察；没有对应候选时只称探索。系统化覆盖反馈、自动最小化和反例管理随具体需要加入。

### D2：VM 定点调查、强制探索与局部求解

围绕 M1–M3 的具体缺口采集取指、解码、dispatch、寄存器/内存和状态转移，不默认保存全程指令 trace。自然输入暂时无法触及目标分支时，在有依据的边界上干预条件、外部返回或虚拟状态，记录前态、修改和观察。

不要求完整合法字节码生成器或全部 handler 已恢复后才能做局部实验；无法说明前态相容性时，结果仅是带缺口的探索材料。强制覆盖与自然覆盖分开，修改后的原实现不能充当未干预业务基准。优先尝试自然可达输入，必要时做局部约束求解并具体重放。

控制流平坦化与 MBA 围绕关键切片处理，例如取指地址、分派目标或分支条件，保存机器位宽与前提。不先建设通用去混淆器或全程序符号执行；D1 遇到同类瓶颈时可提前使用局部方法。

### D3：结构化字节码 fuzz

对已理解的局部指令格式、长度、操作数和必要上下文生成变体，不等待全部 VM 恢复。原始随机字节变异与有效虚拟程序生成分别记录；滚动密钥、校验或状态编码存在时，保持已知约束，解码后注入明确标为干预。

语义差分双方必须运行同一变异程序，不能将变异后的 VM 与原始程序的固定业务候选比较。没有对应模型时用于探索新行为，不称语义通过。保存资源、种子、初态、编码规则和执行限制，优先反馈虚拟操作、逻辑边与反例，而非 native dispatcher 的无意义路径增长。

### D4：扩大语义恢复与工程交付

交替使用静态切片、自然运行、变异、受控干预和局部求解，逐步恢复状态模型、逻辑 CFG 与真实业务源码。尽早让一个短片段贯穿 M4–M6，再扩大调用链、共享状态、类型、命名和文件组织，不要求按工具清单机械执行。

逐步完善跨文件修改、组合验证、长时间续做和独立工程导出。完整交付须可构建、可执行和可维护，不能仅逐 handler 翻译解释器后就宣称已去虚拟化。

## 阶段验收

初步动态闭环按 [V0.3 整体验收](milestones/v0.3/PLAN.md#第三阶段验收)检查，V0.31 只按自己的 PLAN 验收原实现运行与 harness 循环。后续 D2–D4 的增量在确定范围后另立版本计划；路线图不重复维护验收清单。

## 交付原则

每次确定一个可运行、可复现、能由人工验收的小增量，只实现当前需要的接口和数据。无界面增量不补建 Web；不要求完整 P0 需求全部实现才交付。正常任务内持续推进已授权工作，不把内部每轮变成人工确认。

已实现的命令只在 [功能说明](USAGE.md) 更新，实际结果只在对应 DELIVERY 记录，范围和验收只在对应 PLAN 维护。源码导航、任务循环与 VM 方法分别引用专题，路线图不再复制协议或历史命令。当前人工验收完成前不自动宣布下一版本开始。
