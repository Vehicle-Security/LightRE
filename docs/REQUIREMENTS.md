# 需求清单（人工维护）

本文件是系统的产品范围与验收依据，实现方案见 [ARCHITECTURE.md](design/ARCHITECTURE.md)。首要目标是恢复 ARM64 SO 中 VM 混淆所承载的真实业务逻辑，重点处理其中的控制流平坦化与 MBA（混合布尔算术）混淆。LightRE 提供简单 API 和持久 Evidence，支持 Agent 结合静态分析、反复运行 unidbg、局部表达式化简与验证，积累观察并恢复函数语义。文件划分、类型和命名服务于这一目标；仅让原 VM 可运行、逐 handler 翻译解释器或生成未经验证的候选，不代表完成去虚拟化。

最终交付是供二次开发使用的简单可读、可编译、可执行且可维护的等价源码工程。长期自动化的支柱是 Python 外层 Goal Loop：用户提交一次目标，循环调用 `codex exec`，验证当前工程，未通过时自动反馈并继续，通过交付范围内的完成检查后才结束。方案见 [GOAL_LOOP.md](design/GOAL_LOOP.md)，尚未实现。

产品入口明确为 LightRE 常驻 Python 服务及指导聊天窗口，系统集成多个 Codex CLI 工作会话。指导会话面向用户理解目标、解释进度并通过系统接口组织任务，后台工作会话独立推进源码恢复、工程整理、构建和验证；内部 prompt/workflow 是操作资源。聊天窗口关闭或指导会话失败不停止已提交工作，实际并发、写入互斥与恢复由服务器管理。现有源码 Web 与评论能力保留，新服务/聊天尚待实现，范围和检查条件见 [V0.3 维护计划](milestones/v0.3/PLAN.md#维护与优化计划)。交付和验证范围须明确，失败尝试及暂时无法处理的问题须持久保留。

当前 V0.2 按最新用户反馈只验收 Ghidra 直接反编译、一轮 LLM 保守整理与 Web 审阅，允许保留混淆结构及已记录的反编译局限；新任务不自动追加深入分析。上面的去混淆、VM 业务语义恢复和等价工程交付为后续目标，本版不以完成这些能力为前置。2026-11-03 起，LLM 首轮主动改善函数与变量命名、类型、表达式及有依据的控制流；不要求破解虚拟机，仍保留未知路径及副作用。具体历史范围见 [V0.2 计划](milestones/v0.2/PLAN.md)，已于 2026-11-01 通过用户人工验收。

正在验收的 [V0.3](milestones/v0.3/PLAN.md) 已实现通用 Android ARM64 harness 运行、记录、重放与最小修复循环，并按后续授权适配 DG JNI 和 minilua Android SO 单边执行。核心不按目标名称分流，独立检查器和用例是固定基准。实际结果见 [DELIVERY](milestones/v0.3/DELIVERY.md)，仍待用户人工验收；不包含候选构建、双边差分或完整业务语义恢复。

动态执行限定 ARM64 + unidbg，Qiling 和多后端仍延期。DG 使用配套四份 .bin；minilua 使用 .lua 并由自身解析器生成内部 Proto，已另建 Android SO，保留原 Linux glibc 样本。当前用法只在 [功能说明](USAGE.md) 维护，后续比较协议见 [动态差分](design/DIFFERENTIAL_EXECUTION.md)，完整闭环顺序见 [路线图](ROADMAP.md)。

对已有工作区，用户可显式选择纯汇编 LLM 输入：跳过 Ghidra 参考伪代码和初稿生成，将全部已保存指令与地址一次性内嵌到同一初始提示词，并保存可核对的机器码快照，允许用原 ELF 与 objdump 补核。仍按一轮未经验证的候选处理，不要求去混淆；新二进制的无 Ghidra 导入器不在本次范围。

## 维护与使用

- 每个编号只对应一个可独立验收的行为；按职责分组，不按代码文件划分。
- 编号创建后不改名、不复用；废弃项保留编号并注明原因。
- 需求正文及验收口径由人工维护；未经人工指示，Agent 不自行删减需求或改变验收标准。
- `[ ]` 表示尚未人工验收；`[x]` 表示人工确认通过。勾选状态不等同于代码是否存在。
- Agent 根据需求 ID 开发和报告完成情况；报告须附实现位置、验证结果及未完成项。
- 恢复开发时读取适用的 AGENTS.md、本文件、设计文档和现有实现，不能依赖之前的聊天记录。
- P0：Ghidra 静态导出、可恢复函数浏览器与基础存储；P1：证据、知识、Context、Agent 迭代及 unidbg 实验；P2：扩展动态分析及验证。明确标为废弃的条目不再实现，其余阶段表示实现顺序。
- 实现细节可调整；若发现需求冲突，记录冲突及受影响 ID，由人工修订。
- 每次实现只选一个可运行、可人工验证的小增量，提供准确启动方式和真实样本例子后交付；后续范围根据用户反馈决定，不连续铺开整套系统。小版本顺序见 [ROADMAP.md](ROADMAP.md)，P0/P1/P2 不作为一次性交付包。

开发时的小步交付与工具运行时的目标生命周期分开：成熟工具接受一次已授权目标后，应自动贯穿调查、还原、整理与验证，不把每个内部步骤变成人工确认点。既有 Web 需求保留编号和验收状态，不作为 Goal Loop 的开发前置或扩大 UI 的依据。

持久化原则：系统只维护文件和 SQLite 中的持久数据，每类数据有唯一权威位置。批次内临时状态由 Agent 自行管理；知识读取可在进程内复用，批次完成后保存，不增加独立缓存存储层；文件正文不在 SQLite 中维护可独立修改的副本。

轻量原则：Agent 依据功能说明编写脚本，脚本和 Web 共用本地 Python API；Codex 负责推理、临时 Context 和多轮调查。核心闭环是读取证据、调整 harness、运行 unidbg、保存新证据并继续分析。Web 评论正文保存为本地 Markdown，任务状态与检查点使用同目录 state.json，不在 SQLite 重复维护；后端通过本地持久队列调用 Codex 子进程，不建设独立队列或调度服务。首版不建设独立 Agent 平台、知识索引服务、自动依赖传播或通用 VM/OLLVM 策略框架。废弃项集中留在文末，不计入有效验收范围。

首个可运行版本通过 Skill 聊天启动，Agent 根据目录或 SO 路径打开 Web，展示已识别函数、地址与原始汇编；用户无需手写启动命令和端口参数。随后按用户反馈小步加入还原和动态验证；既不要求首版完成全部 P0，也不能把完成全部浏览器或框架功能作为开始动态分析的前提。

以下 SKL 条目保留早期入口的编号及验收原文。目标产品改由系统内指导会话承接自然语言请求、识别目标并组织后台任务，外部 Skill 仅为旧方式兼容；新服务/聊天的具体范围以 V0.3 PLAN 为准，不能按旧条目的存在要求用户先进入外部 Codex。

- [ ] `SKL-001` · P0 — 用户可通过样本目录和自然语言目标发起分析。（验收：不填写完整依赖或工具参数清单，Skill 仍可开始识别目录内容。）
- [ ] `SKL-002` · P0 — Agent 区分目录中的目标 SO 和配套文件。（验收：当前样本的 SO 作为目标，bytecode 下的 .bin 保留为待调查输入，不默认作为原生依赖加载。）
- [ ] `SKL-003` · P0 — Skill 为已确定的目标自动创建或恢复分析目录。（验收：按用户指定或上下文动态选择可见 workspace，返回完整路径，唯一明确目标无需人工另行执行导入命令，相同 binary 在该 workspace 内复用已有 SO 目录。）
- [ ] `SKL-004` · P0 — Skill 启动或复用 Web 并定位到目标。（验收：聊天提供目录或 SO 后，Agent 处理启动参数，页面可访问后尝试打开浏览器并返回地址，不要求用户手写终端命令、host 或 port；无桌面浏览器时如实报告服务地址，完整工作区未实现时可直接定位单 SO。）
- [ ] `SKL-005` · P0 — Skill 保存已识别的输入关系与未知项。（验收：新会话读取工作区知识可得知选定目标、配套文件用途假设和下一步，无需恢复旧 Agent 内存。）

## 工作区

- [ ] `WS-003` · P0 — 内容不同的 SO 使用独立分析目录和 SQLite。（验收：同一 workspace 可容纳多个版本，各自知识、证据、源码、运行与验收独立保存，不覆盖旧分析，不建立统一多 binary 数据库。）
- [ ] `WS-004` · P0 — 工作区保留原始样本副本。（验收：移动输入文件后仍能读取原始样本。）

- [ ] `WS-006` · P0 — 工作区产物引用使用相对路径。（验收：迁移工作区及其引用的共享资源后能恢复既有结果。）

- [ ] `WS-009` · P0 — 默认分析产物与 LightRE 工具仓库分离。（验收：SO、副本、索引、trace、harness 和分析源码写入外部 workspace，LightRE 的 Git 待提交列表不出现分析结果；外部 workspace 是否纳入 Git 由用户决定。）
- [ ] `WS-010` · P0 — 结果直接保存在文件系统和 SQLite 中。（验收：保存成功后重启进程，直接打开工作区即可恢复结果。）

- [ ] `WS-013` · P0 — 本地导入保留来源资源目录位置。（验收：目录输入使用指定目录，单 SO 输入使用父目录，无需递归复制全部内容；运行实际使用的文件仍按 RUN-017 固定。）

## 地址实体与引用

- [ ] `ENT-001` · P0 — 所选 SO 的地址实体使用类型和 RVA 唯一定位。（验收：每 SO 独立 SQLite 内无需 binary_id 或重复 SHA256；不同 SO 的同 RVA 不合并，跨 SO 引用或导出从元数据附上 SHA256；RVA 与运行时 VA、文件偏移可区分。）
- [ ] `ENT-002` · P0 — SQLite 以原始函数入口 RVA 为键。（验收：函数表及相关汇编、任务和知识按 RVA 关联，允许不同 RVA 的原始函数同名；改源码名不改变原始身份，不要求另存字符串实体主键。）
- [ ] `ENT-003` · P1 — 普通全局变量具有地址实体记录。（验收：多处引用同一全局变量时返回同一实体 ID。）
- [ ] `ENT-004` · P0 — 每个源码实体的名称与所选源码版本一致。（验收：原始分析名与当前源码声明名分开，源码索引从实际文件派生，Web 显示和搜索当前名称；名称不作为身份键，不能只在数据库改名而让 Web 替换文本。）
- [ ] `ENT-005` · P1 — 同一源码命名作用域内的声明避免重名。（验收：冲突声明拒绝发布或显式改名；不同局部作用域允许合法同名，全局定位使用实体 ID，不依赖名称唯一。）
- [ ] `ENT-006` · P0 — 直接调用保存目标实体绑定。（验收：被调用函数改名后调用链接仍定位原地址。）
- [ ] `ENT-007` · P1 — 函数内跳转与 tail call 分别记录。（验收：普通函数内分支不会显示成 callee。）
- [ ] `ENT-008` · P1 — 间接调用以所属 SO 分析目录和指令 RVA 标识调用点。（验收：调用点不重复保存样本哈希，不同 SO 中的相同地址不会混为同一调用点。）
- [ ] `ENT-009` · P1 — 间接调用点允许关联多个候选目标。（验收：新增目标不会覆盖已有目标。）
- [ ] `ENT-010` · P1 — 未解析间接调用保留其未知性质。（验收：没有依据时不渲染成某个确定函数调用。）
- [ ] `ENT-011` · P1 — 导入符号保留模块/符号身份。（验收：尚无实现地址时仍能展示导入名称。）
- [ ] `ENT-012` · P1 — 动态地址根据所属模块的加载布局转换为静态身份。（验收：不同加载地址下同一目标关联同一实体。）
- [ ] `ENT-013` · P2 — TLS、GOT slot 和其指向对象具有可区分的引用类型。（验收：三者不会混写到普通全局变量映射。）
- [ ] `ENT-014` · P1 — VM 还原结果可关联独立的逻辑入口。（验收：同一解释器 RVA 下的不同字节码入口及必要上下文可区分，独立维护版本时不会相互覆盖；导出函数能追溯原生地址与逻辑入口，不强制一一对应。）
- [ ] `ENT-015` · P1 — 还原源码声明保留稳定注释 ID。（验收：当前一对一函数按原始 RVA 关联，默认注释 ID 由后端按 RVA 生成，已有 ID 在改名、移动和重建索引时不变；后续无原始入口的声明由后端分配不变 ID，不虚构地址；跨 SO 引用附上元数据 SHA256，工作目录内源码不重复 binary 或哈希；局部变量和参数不分配稳定 ID、不建映射表。）
- [ ] `ENT-016` · P1 — 源码与原始地址支持多对多来源关联。（验收：多原始函数合并后，点击任一原始 RVA 均定位同一份当前源码；连续合并、改名、搬文件和单原始函数拆分仍保留全部原始地址的可达关系；后端基于旧发布记录校验来源继承，不能只相信 LLM 注释，漏失旧映射拒绝发布；未知或派生来源不虚构 RVA，新实体可追溯被替代的旧实体。）

## 索引一致性

- [ ] `IDX-001` · P1 — 各功能使用统一的实体身份约定。（验收：在各 SO 的独立数据库内，原始实体按类型/RVA 定位，源码实体按稳定源码 ID 定位；native/source 前缀仅为带类型引用的表达，不强制替换现有整数 RVA 主键；改名、索引重建不重新编号，名称和数据库行号不作为跨文件业务身份。）
- [ ] `IDX-002` · P1 — SQLite 源码索引可定位真实文件与版本。（验收：能按实体查询名称、文件、内容哈希、版本、正文字节范围、来源及已知引用，正文直接从对应文件读取，历史字段不会覆盖当前字段。）
- [ ] `IDX-003` · P1 — 当前源码索引按选定版本集完整替换。（验收：改名、移除声明、合并或拆分后，旧名称、位置、来源和引用不残留在当前结果，候选尚未选用时不改变当前索引。）
- [ ] `IDX-004` · P1 — 当前选择与索引在同一事务发布。（验收：相关多文件更新和 revision 一起可见，失败或中断保留完整旧选择与索引，读请求不会混用不同 revision 的位置和文件版本。）

## 长期自动化目标循环

以下是已确认的长期支柱能力，尚未实现或人工验收；与现有单轮批量候选任务分别报告。具体设计见 [GOAL_LOOP.md](design/GOAL_LOOP.md)。

V0.3 先实现 harness 任务所需的结果保存、失败交接、实际核验和基本续做；不以完整工程恢复、知识自动提炼或 CLI 会话恢复为前置，也不因该子集通过自动勾选整项长期需求。

- [ ] `GOL-001` · P1 — 一次目标可在无 Web 的环境自动推进完整逆向任务。（验收：只提交一次目标及必要输入，内部自动开展调查、还原、工程整理与验证，无需逐函数指定或人工逐轮点击继续。）
- [ ] `GOL-002` · P1 — Python 外层循环由实际验证决定继续或完成。（验收：首轮 CLI 正常退出并声称完成、但当前源码检查失败时继续调用；只有完成条件全部通过且交付物保存成功才标记 complete。）
- [ ] `GOL-003` · P1 — 目标范围和固定验收依据保持可追溯。（验收：模型跳过失败检查、删除反例或降低原始预期不能取得通过；调用方修改范围时登记新依据并保留旧记录，新增实验和回归用例不覆盖原基准。）
- [ ] `GOL-004` · P1 — 验证结论绑定实际参与验证的内容。（验收：报告可定位目标、源码、构建物、检查器、harness 和用例依据；验证期间或之后源码变化、报告缺失或过期时，不能作为当前完成依据。）
- [ ] `GOL-005` · P1 — 自动续跑定位明确任务与轮次并携带真实失败。（验收：默认每轮独立 `codex exec --ephemeral`；逐轮原样保存完整 prompt、最终返回、事件、stderr、进程元数据及实际检查报告。下一轮可读取原始目标、上一轮完整返回与实际失败，并按需读取相关旧尝试；不要求先提取摘要或自动记忆。会话恢复仅为可选优化，采用时按明确 ID 恢复，不使用 `--last`。）
- [ ] `GOL-006` · P1 — 长任务可跨进程和会话中断恢复。（验收：持久文件是默认交接依据，不依赖 CLI 会话；执行器重启后先核对当前产物和检查点，从原始任务、结果与检查记录继续，不丢失源码、反例及未解决项；已有产物确实满足完成条件时不重复调用模型。）
- [ ] `GOL-007` · P1 — CLI 与检查器故障不会被当作目标完成。（验收：退出码为零但结果缺失、检查器崩溃或输出无效时，不据此标记完成；记录实际故障并核对当前文件，只有取得任务要求的有效检查依据与交付物才能完成，不编造缺失报告或沿用旧通过。）
- [ ] `GOL-008` · P1 — 基础设施故障采用有上限的恢复策略。（验收：网络、限流或 CLI 故障按配置退避重试，超过上限保留可恢复状态，不在同一故障下无上限调用模型。）
- [ ] `GOL-009` · P1 — 停止原因与完成结论独立保存。（验收：取消、调用方预算耗尽或已确认外部阻塞均保存检查点和继续条件，不标记 complete；模型自报阻塞需结合实际缺失条件核对。）
- [ ] `GOL-010` · P1 — 重复失败时利用持久资料调整后续调查。（验收：续跑识别已尝试方法并给出调整依据，不只重复“继续”；新证据、反例和排除的假设计入进展，不仅凭源码未变化宣布阻塞。）
- [ ] `GOL-011` · P1 — Goal Loop 与同一 SO 及共享 harness 的其他写入任务互斥。（验收：沿用现有任务目录及执行锁，共享 harness 同样保持单一写入者，模型不直接维护 state.json；取消或恢复时确认旧执行者及相关写入结束，不与批量任务、评论任务或其他 SO 的任务并发覆盖同一工程。）

本轮轻量审查进一步取消完整对话归档、命名历史、知识重索引、严格 token 预算与确定性 Context；迭代调度和复查选择交给 Agent/脚本，进度与检查点归入 Run。Ghidra 移至 P1，P0 先快速打开和浏览。新增轻量发现、超时/取消、汇编片段读取和单函数迭代约束，避免快速入口被全量分析阻塞。

Harness 由 Agent 生成与适配，当前源码放在用户选择的 workspace/harnesses/<name>，兼容的多个 SO 版本共享一套。每份 SO 保留独立目录和 SQLite，harness.json 仅维护共享路径与本版本参数；Run 保存实际执行的小型源码副本和输入。原始依赖按路径和哈希引用，不引入 JNI 数据库、自动匹配服务或 harness 插件体系。

Workspace 路径和名称动态决定、保持可见，不固定在 LightRE 工具仓库。其内各 SO 分析目录采用名称加默认 4 位短 SHA，完整 SHA256 在各自数据库记录；名称冲突时延长前缀，同内容改名不重复建分析目录。Web 导入默认用 SO 父目录名作为分析名称，后续改显示名称不搬目录。参与实验的输入仍需固定保存。

主要入口调整为 LightRE Agent Skill 与功能说明：用户给出样本目录与目标，Agent 识别 SO 和配套资料，编写代码调用本地 Python API、创建或恢复工作区并启动 Web。CLI 仅按需作薄包装，Web 路径导入作为辅助能力；不要求用户预先枚举完整输入参数。

核心仍保持简单：保留 Evidence，让 Agent 不断调整并调用 unidbg，依据新观察继续调查 VM/OLLVM 混淆。参考其他项目仅用于能力与推理的分工，不扩展为多格式工具平台或预定义去混淆引擎。

最终目标明确为用于二次开发的可读等价源码；Web 增加版本级人工验收，源码交付采用独立目录。基本差分比较提前到 P1，先在一个函数上打通运行、还原、比较和源码交付，不以仅能运行原 VM 或浏览伪代码作为最终完成。

Web 人工反馈后，Agent 按问题继续多轮 Rizin/Ghidra 静态分析、unidbg 实验与差分验证，再发布结果供人工复查。失败实验和差分反例保留在 Run/Evidence；Unknown、已尝试方法及继续条件保存在所属知识 Markdown，续做时读取，解决后保留处理依据。不增加 Unknown 数据库、独立调度器或常驻 Web 面板。

明确 RVA 与 ELF 地址的换算、VM 原生函数与逻辑入口的区别，以及 ARM64 候选双边执行、状态准备、环境控制、逻辑观察比较、累计回归和组合验证。动态地址转换、验证范围与未验证状态随基本差分一起放在 P1；持久化继续使用现有文件和 SQLite，不增加比较或用例服务。

实现方式调整为小步交付：首版只提供真实函数列表、名称/RVA 搜索和原始汇编阅读，不以完整持久化、自动刷新或动态闭环为前置条件。每次交付可运行例子后先供人工体验，后续功能按反馈选择；长期需求保留但不要求一次实现。

首版启动方式明确为 Skill 聊天：用户给目录或 SO，Agent 负责启动或复用 Web 并返回实际 URL。底层命令只作 Agent 执行与开发排查资料；首版包含最小 Skill 说明，但不要求全局安装或完整工作区功能。

Workspace 可以组织多个 VM 版本，各 SO 分析目录固定对应一份原始 SO，其独立 SQLite 内只保存一次完整 SHA256。选定 SO 后按类型和 RVA 定位实体，版本、Run 和评论任务沿用该 SO 身份；跨 SO 引用或导出时才附带原始哈希，不增加统一多 binary 数据库。

源码展示调整为直接读取实际文件，取消 Web 按名称映射改写文本。源码名称、稳定 ID 与来源注释保存在文件，各 SO 的 SQLite 保存查询索引；本地源码不重复写原始 SO 身份，各声明标明原始或派生来源，跨 SO 引用和独立导出另附来源说明。Web 隐藏机器注释但保留普通注释与代码正文。还原源码身份独立于原始 RVA，按需支持函数合并、拆分和公共 helper；此扩展不提前到首版汇编浏览。

明确 SQLite 保存派生映射与少量结构化权威状态的边界。统一实体 ID，源码变更经单一入口登记不可变版本，选定结果时事务替换完整当前源码索引；历史保留但不混入当前结果，文件异常变化须显式报告。索引更新和重建不删除验收、证据或仍被引用的历史，也不改变首版汇编浏览的范围。

每个 SO 的知识、证据、Unknown 和可视化状态独立；workspace 可共享 harness，并通过逐版本逆向与比较提炼公共 VM 知识。公共条目记录来源、适用条件和例外，帮助后续版本确定调查起点；新版本仍需独立验证，不直接继承旧版本的具体结论或通过状态。公共知识直接用顶层 Markdown，不增加公共 SQLite 或自动同步层。
