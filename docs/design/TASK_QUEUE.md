# 静态候选与评论队列

目的：分析和用户评论都由 LightRE 自动调度。评论不因全量分析正在运行而丢失，不需要回聊天窗口推动。

本文维护当前静态批量分析与评论队列的实现协议（由 V0.2 引入）。该队列恢复的是 LightRE 任务；后续可编辑工程的多轮修复与结果交接见 [Goal Loop](GOAL_LOOP.md)，操作入口见 [功能说明](../USAGE.md)，版本人工验收记录另见 milestones。

## 存储

每个 SO 自己维护 `tasks/<id>/`，与其他版本隔离：

- `reviewed.c`：评论对应的代码快照；只供分析上下文使用，当前源码仍只有 `source/src/` 一份。
- `state.json`：目标、评论及提交时摘要、任务状态、优先级、创建/开始/完成时间、RVA、done_rvas、计数、未知项、批次记录、失败次数与有效并发；首轮的 auto_refine、followup_id 和续做的 parent_task 记录自动续做关系。
- `batch-*.input.json`：每批精确源码输入快照，只用于按原文应用模型修改和中断恢复；不是第二份当前源码。
- `batch-*.before.json`：每批执行前的源码展示正文、摘要、路径和知识，用于准确记录本轮改动及中断后重放，不以提交建议时的旧 reviewed.c 冒充实际执行输入。
- `feedback-result.json`：评论任务的独立回复、实际发布结果及执行前后源码快照；仅为任务记录，不是可编辑的当前源码。区分 updated、unchanged、unresolved、conflict；没有可靠执行前快照时为 unrecorded，不伪造差异。
- `batch-*`：每批的提示、模型输出及日志；续跑使用新编号，保留旧日志。
- `cancel`：存在时取消该任务。
- `tasks/.dismissed.json`：已清理展示的结束任务 ID。任务目录及日志留档，源码、Knowledge、函数结果状态和引用关系继续有效；此操作不回收日志占用的磁盘空间。

队列直接读取这些任务文件，不另建数据库副本或消息服务。JSON 原子替换；`.queue.lock` 串行化入队与调度退出握手，防止并发提交丢失或请求滞留。`.dispatcher.lock` 保证一个调度器，`.lock` 保证一个执行进程；额外的调度器锁用于安全等待旧版执行者退出。该进程交替推进多个任务，外部只读 CLI 并行运行，源码和知识发布仍在同一执行进程中依次完成。

任务的 input_mode 默认 reference，assembly 为纯汇编模型输入；两种请求分别去重。assembly 跳过 Ghidra 参考与初稿准备，保存全部已导出指令及知识快照（`batch-0000-0x0001c07c.asm` / `.knowledge.md`），全部地址、指令和知识直接内嵌到同一初始提示词，文件用于留档与按需补核；每批 600 秒，不使用 low/禁用 shell 的快速首轮配置。函数目录和汇编复用已有导出，未形成候选时仍记未解决。两种模式共用并发额度、RVA 占用、优先级、取消和恢复。

默认 reference 首轮对既无参考初稿也无已有候选的函数，自动在当前任务内选择 assembly 批次，不再以首尾摘录为唯一输入。不同输入模式分别合批，仍遵循多函数最多 4,000 条指令、32 个函数及上下文限制，超大单函数不拆分。任务级 input_mode 表示请求模式，批次记录的 input_mode / timeout 表示实际输入与限时：有初稿的首轮为 reference / 600，无初稿的汇编批次为 assembly / 600。失败重试保留批次模式，恢复时按当前材料重新分流，不自动追加新任务。

完整提示词在启动 CLI 前检查 1,048,576 字符上限。超限属于不可重试的输入错误：保留完整 prompt 文件并记录执行失败，不启动模型、不截断指令，也不消耗一次自动重试。可重试的执行错误仍沿用后面的有限重试规则。

Prompt 只有两类：`RECOVER.md` 处理 initial/targeted，`FEEDBACK.md` 处理 comment，assembly 为各自的输入条件分支；共用一个内部 Skill。新任务不再生成 `task.md`，完整指令以每批 `.prompt.md` 留档。资源映射见 [Recovery Prompt](RECOVERY_PROMPTS.md)。

## 调度规则

1. 评论优先级为 0，初次/定向分析为 10；数值越小越优先，同级按创建时间 FIFO。
2. 同一 SO 的全部任务共享 `LIGHTRE_CODEX_WORKERS` 个 Codex 批次名额（默认 8）；每个任务还受自身 workers/effective_workers 上限约束。不同函数的评论和后台批次可并行。批次从启动到发布结束占用其全部 RVA，同一 RVA 不会被两个批次同时处理；混合批次可先发不冲突的函数，冲突部分等待。
3. 调度器按优先级及 FIFO 为可执行任务分配空位；评论不再等待后台所有活跃批次结束。名额已满时，评论优先取得下一个可用名额；同一函数正在处理时等待其发布完成。不会强杀健康批次来抢占，也不永久保留空闲名额。Ghidra/初稿准备与发布仍串行，外部模型等待期间交替推进其他任务。
4. 同一函数的不同评论分别保留并依次执行，后续评论读取前一条发布后的源码；不同函数可同时执行。活动请求的模式、RVA 集合、评论、提交版本均相同时复用原任务 ID。全量分析重复启动复用原活动任务。
5. 提交评论时校验页面对应的候选摘要；排队后源码可以继续变化。执行时读取最新候选，同时保留原快照理解用户意见，不将新代码回滚到旧版本。
6. 每个任务处理指定范围一轮。首轮、汇编及评论/定向批次时限均为 600 秒。CLI 错误、超时及无效输出只影响当前批次，每函数额外重试最多 1 次，等待 5 秒；有效子集先发布，剩余函数才重试。非限流失败拆小重试批次，429 则将后续有效并发减半（最低 1），不终止正在运行的健康批次。耗尽重试后单独记录 failed_rvas 和 failed_count，不能算作模型未解决结论。存储或来源校验失败仍进入 error。
7. 新建任务设置 auto_refine=false，只执行一轮 Ghidra 初稿与 LLM 命名、类型及控制流改进，不自动追加深入去混淆任务。旧任务已保存 auto_refine=true 时仍兼容原策略：为 unresolved 中排除 failed_rvas 的函数安排一次 targeted 任务，父任务保存 followup_id，子任务保存 parent_task，不递归续做。执行失败仍与模型未解决分开，父任务的历史结果不由子任务改写。
8. 队列清空后后台进程退出；新请求自动启动调度器。无需常驻 Web 或聊天 Agent。

`processed` 和 done_rvas 同时包含模型结果、最终执行失败及已有候选跳过项，不等于新生成代码数量；失败详情以 failed_rvas / failed_count 区分。任务 unresolved 中可能包含同一批执行失败；计算模型未解决数量应先排除 failed_rvas，不重复计数。run_duration_seconds 是最近一次执行段耗时，不累计多次暂停续跑。验收应核对 batch 输出及复用范围。新建任务的 workers 可用 --jobs 配置，重复打开复用已有任务不会修改其并发设置；它是任务上限，SO 的共享上限由执行进程的 LIGHTRE_CODEX_WORKERS 设置。`GET /api/recovery` 的 concurrency 返回共享上限与实际占用，Web 顶部据此显示总并发，并汇总所有正在运行任务的函数。

检查一轮自动分析时跟踪首轮，旧任务如有 followup_id 也跟踪对应任务。报告同时保留各任务计数和最终按 RVA 去重的当前结果，不累加父子任务的 generated 作为函数总数。已知截断初稿被保留时，即使被标为 LLM 候选，仍属于需要解决的逻辑缺口。有限续做既不保证全部函数可恢复，也不代替后续构建、运行与差分闭环。

## 状态与控制

| 状态 | 含义 |
| --- | --- |
| queued | 等待并发名额、同一 RVA 的前序任务或调度准备 |
| running | 正在调用工具/模型 |
| complete | 本任务所有入口已有候选或已由其他任务完成，不代表等价验证 |
| partial | 本轮范围已处理完，仍有模型未解决或耗尽重试的执行失败 |
| error | 存储、来源校验等导致任务无法继续的错误 |
| interrupted | 暂停后保留进度，继续时重新入队 |
| cancelled | 用户取消，不再调度 |

“暂停”创建 `tasks/.paused` 并停止全部活跃任务的批次，保留已发布结果与所有等待任务；“继续还原”先恢复队列；没有活动任务时才创建一次针对尚无 LLM 候选函数的任务（包括此前未解决或失败者）。关闭 Web 不会暂停队列。用户明确要求只浏览、不运行任务时，启动 Web 前用 `recovery.queue.pause(reader)` 暂停。暂停期间仍可提交评论，评论保持等待。取消只影响选中任务，其他任务继续。

异常退出后，重新启动调度器会恢复遗留 running 任务；done_rvas 跳过已记录的处理结果，初次任务也跳过已有 LLM 候选。续跑先读取状态为 running 的批次已保存结果，按原候选摘要校验并发布；已发布相同结果可重复确认。执行采用至少一次语义：没有保存完整输出的未确认批次可能再次执行；不宣称外部 CLI 严格只运行一次。发布前仍校验当前函数摘要，防止覆盖外部修改。

Web 启动时恢复已存在且未暂停的队列，不自动创建新分析任务。页面每 3 秒读取队列与进度；队列面板显示等待、执行、完成/失败状态，支持取消；函数列表可筛选有排队任务的函数。任务标题和状态均可按 RVA 跳转，单个目标直接打开，多个目标展开地址列表且轮询保留展开状态。状态优先使用 API 队列项 issues 中的失败/未解决 RVA，不按函数名或任意首项猜测；跳转问题函数时展开已有分析记录。标题仍可查看任务的全部入口。

HTTP 沿用 `GET/POST /api/recovery`、`POST /api/recovery/stop` 和评论接口，增加 `POST /api/tasks/{id}/cancel`。内部 API 位于 `src/recovery/queue.py`，批量执行位于 `jobs.py`。

顶部“清除已结束任务”调用 `POST /api/tasks/clear`，同时清除相关临时回复的展示；当前函数“清除已结束回复”调用 `POST /api/functions/{rva}/feedback/clear`，只影响该 RVA 的评论任务。两者均仅处理 complete、partial、error、cancelled；保留 queued、running 和可继续的 interrupted。清理标记在队列锁下原子保存，刷新或重开 Web 后生效；任务实体仍留档供状态推导和排查使用，不删除源码、Knowledge、用户草稿或其他函数的评论。重复清理返回 cleared=0。

## 建议进度、回复与源码差异

`GET /api/functions/{rva}/feedback?limit=5` 返回当前函数最近的建议、每条任务的状态、排队原因、耗时、独立回复及源码差异；只读取当前 SO 的任务文件。queued 项的 wait_reason 区分 same_function、capacity 与 dispatch；保留的 ahead 是队列排序计数，不能当作必须完成的任务数。同时返回独立的 `progress`，从全部任务中按该 RVA 的 current、done_rvas、unresolved 和 failed_rvas 计算本函数状态，供后端查询使用；源码区不常驻展示初次/定向任务的状态。未开始的建议没有回复，执行失败显示具体错误，运行锁已释放的遗留任务显示中断。实际修改以执行前与保存后的源码正文比较，不以 generated 计数或模型声称“已修改”判断。

差异来自本次任务保存的快照，包含文件路径和增删行；后续任务再次修改源码时，原建议的回复与差异保持原样，并标明当前源码已更新。源码摘要沿用原始片段摘要，比较展示正文时排除机器定位及生产者注释。旧任务可以从保存的 batch 输出读取原始模型回复，但没有发布快照时明确显示“历史回复，未记录改动快照”，不把今天的源码变化归因于旧任务。

源码区底部仅在当前函数有人工建议排队或执行时显示局部进度条，每 3 秒刷新，不依赖顶部全局任务计数变化。排队时显示等待状态，执行中使用不表示百分比的动态进度条；处理结束、失败、取消、暂停或尚无建议时隐藏进度条，不留占位，不常驻“本轮已处理”等文字。完成后的回复及源码差异继续保留。顶部折叠队列保留，用于查看全部任务及取消；顶部分析区标签使用 WORKSPACE。最近建议默认展开，其他建议可折叠，源码差异按需展开。队列中的建议可点击进入所属函数。Enter 发送、Shift+Enter 换行，中文输入法确认候选时的 Enter 不提交；发送期间防止重复提交，失败保留草稿。存在未提交草稿时不自动替换正在评论的源码，进度与回复仍继续更新。

局部处理栏提供“取消”按钮，按当前显示的建议任务 ID 调用取消接口；排队与执行中均可取消，请求期间显示“取消中…”并禁止重复点击。取消仅影响这条任务，不暂停其他队列任务；失败显示错误并可重试。

普通评论使用专用提示词：直接提供该 RVA 的最新源码、既有知识、用户意见和必要时的旧 reviewed.c；不调用 Ghidra、不重新准备全量初稿。源码优先返回精确 edits；独立 reply 简短说明本次建议的处理结果，仅存入任务回复，不追加到 Knowledge。后端保留不可变源码和 Knowledge 快照，按输入应用补丁、校验源码摘要及知识是否变化后发布。需要核对证据时保留只读工具，不自动降低模型配置或限制复杂建议。显式 assembly 评论继续使用完整汇编流程，返回完整 notes 和独立 reply，edits、knowledge_edits 均为 null。减少重复读取和整份源码/知识输出不保证固定响应秒数，模型与服务端等待仍会影响耗时。

Knowledge 是当前分析文档，每次修改都应整合进去，不能累积“建议处理 / 本次修改”日志。名称、类型或逻辑变化时，模型须同步调整代码中的相关解释及 Knowledge 的相关段落，修正过时结论、合并重复说明，保留仍有效的证据地址、依据、假设及未知项。更新有两种互斥形式：完整 notes（knowledge_edits=null），或精确段落 knowledge_edits（notes=null）。后者按顺序应用 old/new，每条 old 必须非空且在当时正文中恰好出现一次；无法唯一匹配、整合后为空或 Markdown 边界损坏均不发布源码及知识。knowledge_edits=[] 表示既有说明已准确；没有既有知识时必须返回完整 notes。已有逐轮记录可在下次处理该函数时由完整 notes 整合，不启动模型批量改写历史知识。

源码下方“函数说明 / 分析上下文”直接读取该 RVA 的 `knowledge.md` 内容，没有第二份说明存储；页面同时比较 notes 和源码摘要，只有说明变化也会刷新。清空临时任务回复后，这份当前说明继续保留。自动刷新仍遵循草稿保护，不把新说明与正在评论的旧代码版本混在一起。处理中源码或 Knowledge 发生冲突时保留当前内容，提案只进入标明未采用的临时回复；执行失败也不向评论任务的 Knowledge 追加错误日志。旧任务没有 Knowledge 快照时继续按旧输出协议恢复，不把新协议的完整说明当作增量追加。校验保证结构、精确补丁与冲突检查，语义整合质量仍依赖模型；源码与知识尚不构成跨文件原子事务。

建议 API 的 `items[].activity` 从当前函数所属批次的真实 `events.jsonl` 派生模型运行、工具命令、处理工具结果及返回后检查保存等阶段；只读取日志末尾至多 256 KiB，忽略正在追加的不完整记录，不向页面复制命令输出或模型回复正文。页面以 CSS 活动动画展示运行状态，悬停可见最近命令摘要，同时显示本轮耗时；15 秒以上没有日志输出时说明静默时长。CLI 不提供生成百分比或剩余时间，静默也不等于任务卡死。

快速验收使用 `tools/venv/bin/python -m unittest discover -s tests -p 'test_source_api.py' -v`：走真实建议 API、任务调度、发布与存储，仅替换外部 CLI/格式化器，覆盖 8 个共享名额、同 RVA 串行、后台首个空位让给评论、全局暂停恢复、连续修改后的知识整合、精确知识补丁、仅说明刷新、无效补丁不发布、源码与知识冲突保护、清理与重开保留分析，以及状态变化、作用域隔离、已修改/未修改/未解决/冲突、后续源码变化不改写历史差异、旧任务与损坏回复记录。不依赖浏览器或真实模型。
