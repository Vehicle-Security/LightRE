## 通用能力的边界

当前通用差分指 ARM64 unidbg 任务之间复用用例、状态和环境约定、结果比较、证据及反例反馈。公共流程是：读取同一逻辑用例 → 为原实现和候选分别准备环境与状态 → unidbg 执行 → 提取约定观察 → 规范化比较 → 保存结果、差异和复现资料 → 反馈修复。

初版只需 Python 执行与比较、目标相关的普通 Java unidbg harness，以及持久用例和报告。Python 以普通进程调用 harness，读取明确的观察结果文件；纯 C 目标与 JNI 目标使用同样的任务和比较流程，初始化与参数准备按目标编写。不建设插件注册、多后端运行平台或通用环境模型；这些边界尚未实现为 API。

“通用”不等于给任意 RVA 和几个整数就能自动运行和证明等价。函数签名、调用约定、对象布局、初始化及依赖仍需调查；Agent 为具体目标编写可重放的状态构造与结果提取代码。对不明状态保存缺口，不猜测后宣布通过。

## 候选 SO 与构建记录的位置

编译产物放在当前 SO 的外部分析目录中，按构建 Run 保存：

```text
<workspace>/<SO分析目录>/
  binary/original.so                  # 导入的原始目标，保持不变
  source/src/                         # 当前候选源码；构建时固定实际输入依据
  runs/<build_run_id>/
    build/libcandidate.so             # 本次构建的 ARM64 候选产物
    build.log                         # 实际编译输出
    build.json                        # 源码/版本引用、命令、工具链与选项、产物哈希
```

同一产物用于多个差分用例时，后续运行引用这个构建 Run 的实际路径与哈希，不重复复制或覆盖它。unidbg 显式加载原始 SO 和所选候选产物，不通过可被覆盖的 `latest.so` 决定验证对象。构建输入采用已固定的源码版本或小型快照，构建期间输入变化则不能把结果登记为同一输入的产物。

不把候选放进 `binary/`、LightRE 工具源码仓库或样本原始目录；新的构建使用新的 Run，失败保留日志但不沿用旧产物报成功。最后交付的二进制如需随源码提供，放入独立 `exports/<export_id>/`，引用已验证的产物及其内容依据。

这是待实现的保存约定。当前 V0.2 只保存候选源码，尚未提供候选 SO 编译与动态执行功能，不能把现有 `binary/original.so` 当作恢复源码编译结果。

Agent 的具体操作使用 [构建与验证 workflow](../../src/recovery/prompts/BUILD_AND_VERIFY.md)，覆盖固定输入、工具链、编译修复、产物检查、unidbg 调用及差分回归。外层执行器按 [Goal Loop](GOAL_LOOP.md) 核验实际结果并续跑；方法文档已经提供，编译与执行闭环尚未接入。

候选须正确表达 ARM64 的整数宽度、符号、截断、移位、浮点和 ABI 等相关语义，避免 C/C++ 未定义行为使结果随编译选项改变。编译失败保留日志并标为未验证，不能跳过执行直接发布通过。候选入口按实际符号或入口映射调用，原始 RVA 只用于关联与追溯。

## 用例与比较契约

每个目标先由普通 JSON/数据文件和 harness 代码表达下列内容，格式按首个实验需要确定，不预建完整配置语言：

| 内容 | 约定 |
| --- | --- |
| 调用与范围 | 两边实际入口、签名与 ABI、相关调用序列、待验证逻辑与已知依赖 |
| 逻辑输入 | 标量类型与宽度、缓冲区内容和长度、结构化对象、指针的对象归属与偏移、必要别名 |
| 前置状态 | 初始化、相关全局/TLS、对象关系、历史调用；VM 步骤按实际依赖包含 VPC、解码状态及字节码版本 |
| 环境 | 相关文件、JNI 响应、时间、随机源等的固定值或明确重放规则 |
| 观察 | 返回值、有效输出范围、相关对象/全局变化、声明的外部副作用与结果规则 |
| 运行依据 | 原始目标、候选源码和产物、用例、harness、依赖与 Android 环境配置、工具版本及内容依据 |

前置状态的含义应独立于被验证候选，不能为了接受候选而修改输入、固定预期或比较规则。Agent 可以新增用例及实验，改变原有契约须记录原因与目标依据；不能静默删除差异。

## VM 实验：字节码、业务输入与三种运行方式

VM 用例应区分虚拟程序 P、业务输入 I、初始状态 S 和环境 E。字节码还可能依赖常量池、子函数、元数据及解码上下文，不能仅保存一段指令字节。解释器/虚拟步骤模型差分让双方执行相同的 P、I 和含义对应的 S、E；若候选是固定程序 P 的去虚拟化业务实现，则只需提供 I 及必要状态，但来源必须绑定 P，不能变异 P 后继续拿旧候选作预期。

用户已确认优先使用现成资源作为固定种子：DG 为配套样本中的 4 份 `.bin`，minilua 为仓库内的 `.lua` 用例及已有预期，后者由自身解析器生成内部字节码。先适配一份的加载与运行，再重放其余资源，不要求开发新字节码生成器或外部 luac 加载器。文件存在不等于已具备可运行前态；仍需核对目标 SO、实际加载入口、初始化、附带业务参数及结果提取。输入路径与内容依据随 Run 保存，大段字节无需内嵌进每轮 prompt。

| 实验方式 | 输入与操作 | 用途及比较边界 |
| --- | --- | --- |
| 合法字节码基线与差分 | 从目标配套资料、合法调用或匹配的编译/生成流程取得可运行 P，记录 I、S、E | 建立可重放基线；有对应可执行候选后比较结果；尚无候选时仍可观测原 VM |
| fuzz | 变异 I，或变异/生成 P、相关常量、指令序列及必要状态 | 寻找新行为与反例；有对应模型时做差分，无对应模型时做探索；非法编码、上下文不相容与环境失败分开记录 |
| 强制执行 | 从有依据的前态修改条件、虚拟状态、解码结果、分派选择或目标寄存器/内存 | 调查 handler、分支和局部转换；无需已有完整可运行字节码生成器或完整候选，但必须说明当前操作依赖的状态及已知缺口 |

三种方式使用同一 unidbg 运行与记录底座，按调查问题选用。强制探索不必等整套合法字节码、完整取指/dispatch 模型全部恢复后才开始：可以从一次有效前缀走到边界，再对局部状态或解码结果干预。完全合成前态也可用于局部实验，但结论受其状态约束；无法说明前态是否相容时只保留探索观察。

强制实验若双方有对应局部边界和相同含义的干预，可比较该受控条件下的前后态；这只验证局部模型，不作为原程序自然可达或未干预业务等价的证据。干预点分别映射到两边实际代码，不能按同一原生 PC 盲目修改。

字节码 fuzz 分原始字节变异与结构化变异。后者先在部分已理解格式内进行，保持寄存器、常量索引、栈、分支边界及终止等必要约束；若确有滚动密钥或完整性机制，按其实际规则处理，或在解码后注入并标明干预。采用时间/步骤限制，记录资源版本、种子、前态及变异/干预记录，优先保留新的虚拟行为和首次差异；不把 native dispatcher 的路径增多等同于业务覆盖增加。

从开发顺序看，先交付一份合法种子及原始运行，再形成双边差分。底座同时保存字节码来源、实验方式及变异/干预事实；初步 fuzz 和定点强制实验可在有相应运行边界时开展，完整自动化生成、覆盖反馈和约束求解继续按后续阶段扩展。

## 比较粒度：函数级与字节码进度分段

两种粒度互相补充：函数级检查完整调用的业务行为，分段检查在存在对应逻辑边界时定位差异。每个用例明确所选粒度与观察契约；不要求所有目标都逐虚拟指令同步。

### 函数级差分

“函数”可以是原生函数调用，也可以是一个 VM 字节码函数/逻辑入口。原生大解释器函数执行整个虚拟程序时，函数级检查可能覆盖整次 VM 调用；不能假定它与单个字节码函数一一对应。

从含义一致的输入与前态启动两边，执行至正常返回、约定异常或明确的范围终点，比较返回值、输出、相关对象/全局变化及声明副作用。递归或嵌套调用记录调用实例和返回边界。复杂内部函数优先经正常初始化到达，不依赖复制任意栈或自动快照。

该方式适用于布局变化或已经去除 VM 分派的业务候选，不要求双方内部寄存器、VPC 或路径逐步相同。首个闭环以这种方式取得整体回归；返回结果一致仍只说明用例及观察范围内一致。

### 字节码执行进度分段

解释器模型、handler 模型或带来源检查点的候选，可以按已提交的虚拟步骤、逻辑基本块、虚拟调用/返回或选定字节码位置分段。比如每完成 32 个虚拟步骤检查一次，只是可调诊断策略，不是固定要求；不能按执行了相同数量的 ARM64 指令对齐。

1. **先定义步骤边界。** 选定一次虚拟操作已经提交、下一次取指尚未开始等明确时点，识别原生 Hook 位置及候选对应位置。记录当前/下一 VPC 的含义；不能一边在解码前、一边在 handler 更新后比较。
2. **再定义进度身份。** 保存虚拟程序与代码版本、逻辑函数/调用实例、逻辑位置、事件序号或出现次数、执行阶段及必要上下文。循环会重复 VPC，递归会重复逻辑函数；VPC 数值大小和字节偏移不是累计进度，变长指令也不能用固定字节数代替步骤数。
3. **映射两边边界。** 原实现和候选分别到对应的语义检查点后提取状态，不要求物理地址一致。只有双方逻辑步骤可对应时才按相同虚拟步骤数同步；融合指令、不同内部实现或已消除解释器的候选需使用来源映射与较粗的业务边界，映射缺失时回到函数级检查。
4. **比较检查点状态及段内副作用。** 按实际模型比较虚拟寄存器/栈、有效标志、相关对象与内存、下一逻辑位置，以及后续解码需要的状态；按对象归属、偏移与关系规范化。内存提取结合声明观察区与双方相关写入范围，候选额外写入同样需要调查。外部调用和文件等段内副作用不能只因段末内存恢复一致而被忽略。
5. **定位差异。** 例如第一个检查点相符、下一个不符，则保存该区间的前态依据、双方检查点及相关 trace。通过重放原始有效前缀和增加区间内检查点缩小问题，直至能定位某个虚拟操作或状态更新。只有已记录足够状态或完整快照可重放时才直接从中途恢复；不假定 unidbg 自动提供完整状态恢复。

概念示例：`入口 → 完成 32 步的 C1 → 完成 64 步的 C2 → 返回`。C1 相符而 C2 不符时，在这段重放中增加检查点，寻找最早可观察分歧。差异可能暂时出现后又消失，不假设分歧随执行步数单调，也不以两个端点一致证明段内所有行为一致。

若潜在滚动密钥已确认为解码依赖，其值应进入对应模型的检查，而不是为了对齐而丢弃不同值或只按 VPC 匹配。控制流已经分歧时记录双方实际到达位置、前一已匹配边界和停止原因，不能跳过不同分支直到再次遇到同一 VPC 才继续报通过。

连续回归应让候选使用自身输出状态执行下一段，不能每段自动注入原实现正确状态掩盖误差传播。单独从原实现前态驱动候选片段是另一种局部实验，明确标记范围；它不能替代连续函数回归。

V0.31 先验证单边 harness 及其修复循环，按固定测试 SO 的已知预期检查，不包含原实现/候选双边差分。后续完整闭环以函数级差分为基本交付方式；分段诊断先对首个样本中已识别、可映射的边界实现简单采集和比较，不承诺自动对齐任意重构后的代码。随 M1–M4 的取指、dispatch 和指令语义模型完善，扩展按字节码进度分段和自动缩小差异。最终业务源码仍保留完整入口回归，避免局部模型各自通过但组合错误。

## unidbg 双边执行

1. 从同一逻辑输入为原实现与候选分别分配对象和内存，重建别名关系；执行必要初始化和历史调用。默认使用独立模拟器，不共享指针或可变内存。
2. 原实现按真实导出、JNI 签名或规范化 RVA 调用；候选按其实际导出或入口映射调用，不能复用原始 RVA。整数、浮点、聚合返回及隐含参数依照实际 ARM64 ABI 准备，不能一律视作 X0 返回整数。
3. 在声明边界提取结果。函数返回指针时，提取其指向的对象、有效内容、偏移及必要身份关系；JNI 对象按逻辑字段或内容提取，不能比较 handle 数值。
4. 记录相关外部响应。可以先采用固定时间、固定文件与独立初始化的随机源；需要重放时按实际调用语义与对象对应，不把所有 API 混成一条按全局序号消耗的返回值队列。不匹配或缺失响应保持明确失败或未知。
5. 两边各自保存执行结果与原始日志，交由公共比较函数处理。简单参数和字节数组可直接序列化；Lua 状态、JNI 对象图等复杂对象由目标专用代码提取语义，不依赖自动序列化任意内存。

内部函数依赖复杂状态时，先从正常入口运行到对应调用边界进行观测，再确定可重建的前态或改在较大的入口边界验证。不能只恢复寄存器或复制一段栈就宣称得到可用快照。

## 比较结果如何解释

- 整数按声明位宽和符号比较；字节数组比较有效长度与内容。浮点、NaN、负零及容差按目标明确约定，不能为隐藏差异默认放宽精度。
- 对象与指针按内容、归属、偏移和必要别名关系比较；结构体只比较定义的语义字段，保留未解析布局，不对填充字节作无意义的全内存比较。
- 外部事件只比较声明属于业务行为的参数、结果与必要顺序，不要求分配次数、内部 helper 调用或指令轨迹一致。恢复实现可以消除 VM 分派。
- 明确区分当前用例范围内相符、语义差异、执行/环境失败和未验证。双方都崩溃、超时或缺少报告不能变成普通通过；原实现有预期错误行为时另行约定可观察结果。
- 差异至少定位用例和输出字段，例如 `result.table["count"]: original=3, candidate=4`，附双方运行及产物依据；不要只返回一个相似度分数。失败固定成后续回归用例。

## 累计回归与组合验证

每个候选版本在声明的验证范围内重跑已保留用例，失败用例固定为反例。用例数据只保存一份，Run 引用所用用例及其内容哈希；修改用例后保留旧内容。用例可放在现有 `runs/<run_id>/` 中，后续 Run 按引用读取，SQLite 只登记关联，不增加缓存层或测试平台。

Agent 继续补充边界、变异及针对未探索路径的输入；仅反复运行同一小组输入不能扩大验证范围。新的静态、符号或强制执行观察可以指导生成用例，带干预的路径仍需在原始条件下具体重放。

单函数通过后逐步验证调用链、顶层 JNI 入口及连续调用序列。每次 Run 记录实际使用的候选与 callee 版本，并注明哪些调用仍由原实现执行；依赖变化后的旧结果不能自动视为新组合已经通过。分析阶段可以借助原实现处理尚未还原部分，最终声明完成的交付范围应独立执行，剩余依赖和占位明确标出。

“迭代停止”“用例范围内通过”“人工审阅通过”和“语义等价证明”分别表达。双边使用同一 JNI 简化实现时，比较结论也只适用于该环境假设。可维护性需要对照源码与证据审查：真实运算、分支和数据结构应清楚，不能因复制解释器通过差分就判定已完成逻辑还原。

## minilua 状态准备与差分边界

Android SO 源码适配和单边 unidbg 运行已经实现；构建步骤、ABI 和原始样本的保留规则只在 [源码项目](../../samples/minilua/ANDROID.md) 与 [Java 适配说明](../../examples/minilua/ADAPTATION.md) 维护，真实结果见 [交付记录](../milestones/v0.31/DELIVERY.md)。现有 Linux glibc ELF 仍不能当作 Android Bionic SO 加载，旧 RVA、源码身份与通过状态不套用于新构建。

尚待实现的候选差分先在同一 Lua 输入上比较返回、完整输出、错误和声明副作用，再按调查需要进入内部函数边界。lua_State、TValue、table、闭包及 Proto 不能作为普通字节数组跨模拟器复制，应按逻辑内容和别名关系重建，或在较大的正常入口比较。例如 luaH_get 比较值、类型和必要对象关系，不比较地址。

已核对本份 minilua 的 lua_load → luaD_protectedparser → f_parser 路径，直接进入 luaY_parser，没有标准 Lua 二进制块加载分支。因此继续使用 .lua 生成 Proto；后续可对已理解的指令、常量和元数据做受控变异，但独立 Proto 重建/加载协议仍需实现，不假设现成 luac 加载器，也不直接保存指针。

## VM 调查与版本范围

程序级、函数级和虚拟步骤级差分使用相同的用例/观察原则，状态准备与提取代码分别按目标编写。虚拟步骤模型与原 VM 可以比较 VPC、虚拟状态及相关写入，去虚拟化业务源码则按业务边界比较，不要求它保留已消除的解释器内部状态。

已有可重放运行后可开展输入变异；有可执行候选后开展差分。强制执行与变异字节码按 [开发路线](../ROADMAP.md) 引入，仍保留干预性质、有效前态和相同变异程序的比较约束。

总体闭环按小版本实现：V0.31 已建立通用 harness、原文交接的最小修复循环，并完成 DG/minilua 单边适配；后续接候选构建、双边运行与公共比较。当前不接入 Qiling、其他架构或多后端抽象；Android minilua SO 构建与单边 unidbg 运行已按后续授权实现和实测，见 [目标 harness](../USAGE.md#样本入口)；本节其他差分能力仍为设计。
