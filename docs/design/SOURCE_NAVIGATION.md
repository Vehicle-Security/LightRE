# 函数身份、命名、源码定位与调用导航

状态：结构化标记、词法扫描、Web 隐藏机器注释，以及受支持 C 调用和 ARM64 直接调用的点击跳转已实现；多对多索引与统一发布 revision 仍为后续设计。整体约定见 [总体架构](ARCHITECTURE.md)，需求见 [REQUIREMENTS.md](../REQUIREMENTS.md)。

本文维护源码身份、定位和导航协议及其实现边界；任务循环与行为验证分别见相关专题，文件职责与阅读入口见 [文档入口](../README.md)。

当前 `source_index(function_rva, path)` 仍是一对一映射，每段源码必须对应一个原始 RVA；合并、拆分和无独立来源的 helper 暂不接入当前索引，读取时明确报错。新建候选默认分配 `f<RVA至少八位小写十六进制>`，已有 ID 在改名、移动和保存正文时保留；索引重建检查当前文件集合中的重复 ID。下文的多对多、字节范围及发布版本协议尚未实现。

当前读取会核对模块内容指纹，避免同长度修改且时间戳未变时漏掉索引变化。词法解析结果按原文和 SO 身份在进程内有限复用；文件变化会使用新的解析结果。这仍需要读取模块文件，不代表下文按发布文件版本仅查询目标文件的方案已经完成。

## 身份与存储

目标读取链路是 Web 用原始函数 RVA 查找当前还原结果，再用稳定源码 ID 定位实际文件。当前一对一实现仍由 RVA 查询文件路径并扫描来源标记，尚未独立索引源码 ID。源码、Knowledge、Evidence 和任务正文各自保存为文件；SQLite 保存原始分析数据及可重建的源码查询索引，不复制源码正文。

SO 身份由所属分析目录及其 SQLite 元数据确定。工作目录内的源码注释不重复保存 binary 文件名或原始 SO 的 SHA256；跨 SO 引用和独立导出时统一附带来源说明。原始 SO 哈希、源码文件内容哈希和源码 ID 分别用于样本身份、内容校验和声明身份，不能混用。

函数名、文件名、行号都允许变化。后端分配的源码 ID 在重命名、移动和同一声明的改写中保持不变，不根据名称、位置或内容哈希重新生成。源码注释是身份及来源的依据，SQLite 索引从文件生成；索引重建不得重新编号。

### 实现前确认的身份规则

同一 SO 内，有原始地址的对象直接按 RVA 关联。函数使用入口 RVA；全局变量使用其地址 RVA，并由表或显式类型区分实体。RVA 不是 SO 文件的字节偏移，也不是运行时 VA；不得为新增源码虚构地址，或用某条来源指令的 RVA 冒充新增函数入口。

| 对象 | 关联依据 | 改名时的处理 |
| --- | --- | --- |
| 原始函数、其汇编及原始调用关系 | 原始函数入口 RVA；调用点另带指令 RVA | 保持地址关联，原始分析名称不被源码名称覆盖 |
| 原始全局变量 | 类型与 RVA | 保持地址关联，源码使用当前声明名 |
| 当前一对一还原函数 | 原始 RVA 查来源标记，保留已有源码 ID | 改名、移动不换 RVA 或 ID |
| 后续合并、拆分或新增 helper | 稳定源码 ID，加真实来源关系 | 按需引入，不强行要求存在唯一原始入口 |
| 局部变量、参数 | 函数内部普通源码 | Agent 可直接修改，保持内部引用一致；不分配稳定 ID，不建变量映射表 |

现阶段继续使用 `functions.rva` 和 `source_index.function_rva`，不为原始函数额外存储一套 `entity_id` 或数据库行号身份。初次生成一对一候选时，后端以 `f<RVA至少八位小写十六进制>` 生成默认源码 ID；已有合法 ID 原样保留，包括外部编辑后读回的 ID，不能因它不符合默认命名形式而重新编号。ID 只是注释中的不变标识，不是 C 函数名。

确实引入无原始入口的声明时，由后端创建/发布入口分配并检查新的源码 ID，LLM 保留后端提供的 ID；未来可使用带实体前缀的 UUID，不依赖函数名、文件名、代码摘要或任意地址。该分配能力随 helper/合并拆分功能一起实现，当前不增加独立 ID 服务。删除后的 ID 不重新分配给另一个声明。

原始 RVA 对原始 SO 稳定，不意味着分析器第一次识别的函数边界永远正确。若后续分析纠正入口或边界，必须显式保存旧新关系并核对候选；不能因为同名或相近地址就自动迁移。源码搬动和源码重命名不属于原始边界修正。

### 名称与重命名

原始分析名称和当前源码声明名分别保存：现有 `functions.name` 保持原始分析名称的含义，源码名称从当前实际文件派生，不能靠更新 `functions.name` 代替修改源码。API 应明确提供 `native_name`、`source_name` 和 `source_id`；名称只供展示、搜索及在作用域内解析符号，不承担主键、外键或导航目标。允许不同 RVA 的原始函数同名，也允许不同文件作用域的合法同名声明。

一对一列表优先显示当前 `source_name`，尚无源码或声明不能可靠解析时回退到原始名称或 RVA，不能把回退名伪装成已解析的源码名。搜索同时覆盖当前源码名、原始名与 RVA；选中状态、草稿及历史导航继续绑定稳定身份。后续一对多结果返回声明列表，不随意挑一个名称代表整个原始函数。

局部变量无需身份管理，但任意改名仍应保持代码内部引用一致。`edits` 的 old/new 是普通文本补丁，不是变量重命名协议；不得用 `param_1` 的全局文本替换冒充安全改名，因为它会影响 `param_10`、字符串和注释。Agent 可返回完整修改后的函数，或带足够上下文的精确补丁；不为此建设局部变量数据库或通用重构引擎。

跨函数或全局变量改名时，Agent 修改定义、声明、调用及取地址等相关引用；修改文件作为一个发布结果一起校验。来源标记与稳定 ID 不变，旧源码版本保留旧名称。发布入口检查声明身份、作用域冲突及已知引用的目标；未修复的已知引用不能被删除或伪装成外部符号。已有 Ghidra 类型等原因使候选暂不可编译时，保留其明确的未验证状态；可构建范围运行编译/链接检查，编译通过也不等于行为等价。

当前逐 RVA 返回/保存 JSON 的接口不能覆盖跨函数改名。接通多文件发布前，不把单函数改名结果宣称为已完成工程级重命名；批量整理保留已有跨函数符号，需改名时记录待办，后续工程任务自动处理，无需人工逐轮认可。提示词中的 `fcn_<RVA>` 仅作为未知函数的临时名字，不能再称为稳定身份或要求有意义的名字回退。

### 调用关系与点击导航

原始调用图在分析导出阶段记录调用方入口 RVA、调用点指令 RVA、目标入口 RVA 和调用类型。直接调用、尾调用、函数内分支分开；间接调用保存候选或未知状态，导入且无本地地址的符号保留模块/符号身份。后续源码重命名不改写原始调用图。

源码调用关系由后端在索引/发布阶段重新解析：先在实际文件与作用域中解析调用指向的声明，再将声明关联到稳定源码 ID 及其原始来源。原始汇编调用图可作证据，不能直接充当重构后源码的全部调用关系；也不能按调用文本提取 `fcn_` 后缀，或仅用全局 `name -> RVA` 字典猜目标。语义解析与 begin/end 定位扫描分开，结构化标记只解决身份和范围，不能自行解析 C/C++ 的名称绑定。

首批只为能够可靠解析的声明和调用提供绑定，优先复用编译器的解析结果，不为导航自行建设完整 C/C++ 解析器。宏、函数指针、同名歧义或不完整伪代码无法确认目标时保留明确未解析状态，不生成看似确定的链接。名称用于本次解析，持久关系的目标使用 RVA 或源码 ID，重新发布后重新派生。

Web 接收后端给出的引用范围、目标稳定身份和对应内容版本，只负责渲染与导航。源码中新增的 helper 按源码 ID 定位；原始地址导航按 RVA 查询当前还原声明。代码正文隐藏机器注释、处理开头空行和高亮后，引用范围须映射到展示文本；后端原始 UTF-8 字节偏移不能直接作为浏览器字符串下标。过期引用范围不能套用到新正文，同名或不确定调用不自动选择第一个匹配项。

### 当前已实现的调用跳转

`src/recovery/navigation.py` 使用 tree-sitter C 语法树解析当前 `source/src/*.c` 与头文件。标记片段内只有一个受支持函数定义时，将实际声明名关联到片段的稳定源码 ID 和原始 RVA。`static` 定义按文件区分，普通定义必须唯一；参数和局部变量的遮蔽、函数指针、宏、同名歧义、条件编译和含语法错误的函数均保守处理，无法确认的调用不生成链接。此处是受限的 C 语法解析，不是编译器的完整类型、预处理或 C++ 语义分析。尚无源码的原始函数，仅在原始符号唯一且未被当前源码声明占用时使用原始名称绑定；不从 `fcn_` 后缀猜地址。

候选 API 在同一源码快照上返回 `source_name`、`source_id`、`references`、`unresolved_references` 与 `reference_offset_encoding: "utf-16"`。每条有效引用包含相对 `display_code` 的 `start/end`、调用名、`target_rva` 和可用时的 `target_source_id`。正文摘要和路径需与快照一致；检测到读取期间变化时重新读取，仍冲突则返回 409。绑定按实际文件内容在进程内有限缓存，目前没有独立持久化引用表或发布 revision。调用方正文未变但被调函数改名时，也会重新派生引用。

汇编 API 从 ARM64 小端指令字节计算 `BL` 和 `B` 的 PC 相对目标，只给已知原始函数入口附加 `target_rva`；函数内部的 `B` 分支不作为尾调用。`BLR` 等间接调用不猜测目标，不依赖反汇编展示名称或运行时 VA，也不重新运行分析器。

前端在完整高亮后按后端范围装饰调用文本，并映射省略的开头空行和展示时归一的 CRLF/CR 换行；中文和非 BMP 字符使用浏览器相同的 UTF-16 下标。点击源码调用名或汇编直接调用操作数后按 RVA 选择目标，浏览器后退、前进恢复地址。页面轮询时会重新读取可见源码及引用，没有建议草稿才刷新。新增 helper、合并/拆分和多文件一致发布仍未接通，不能把当前链接当作这些能力已完成。

## 结构化标记

函数使用独占一行的固定标记和 JSON 对象，begin/end 必须成对：

```c
// @lightre.begin {"v":1,"id":"f001","origins":["0x1000","0x1020"]}
int process_request(void) {
    return read_request();
}
// @lightre.end {"id":"f001"}
```

| 字段 | 约定 |
| --- | --- |
| `v` | begin 中必填的整数格式版本，首版为 1；它不是源码修改版本或工作区 revision |
| `id` | begin/end 中必填的非空源码 ID，在同一 SO 的当前源码集合中唯一 |
| `origins` | begin 中必填的原始函数 RVA 字符串数组；允许空数组，不虚构来源 |
| `derived_from` | 可选的来源源码 ID 数组，用于抽取 helper 等派生关系 |
| `replaces` | 可选的被替代源码 ID 数组，用于追溯合并、拆分前的声明 |

end 只携带对应的 `id`。上述 `origins` 专指原始函数入口，不把全局变量地址、指令地址或字节码偏移放入其中。全局声明沿用稳定源码 ID 原则，其地址来源须采用显式实体类型的结构化扩展，按实际需要另行约定，不从裸 RVA 猜测类型。

写出时使用 UTF-8、单行 JSON、规范化的小写十六进制 RVA。读取支持 LF/CRLF、行首空格或制表符，以及 JSON 内合法空白和不同字段顺序；标记不能被格式化器拆成多行。JSON 类型、必填字段、重复键、非法常量、支持的格式版本和重复来源均须校验，不能只以 `json.loads()` 成功作为有效依据。无标记的共享类型、头文件和构建文件可以保留，不强制把所有文本伪装成函数。

标记不保存实际函数名、文件路径、行号、内容哈希或验证通过状态。这些信息随修改变化，由源码、索引及与版本绑定的验证记录提供。具体解释、证据、逻辑入口和未解决问题保存在 Knowledge/Evidence，避免注释承担完整分析报告。

### 当前读写与旧格式迁移

`save_candidate` 写出 JSON 标记，编辑已有函数时保留 ID 和来源；旧格式函数在保存时转换，其他函数和共享声明不改写。旧来源头仍校验原始 SO 身份，旧模块和新旧混合模块均可读取。本地新标记不携带 SO 哈希，因此不能依靠它检测手工从其他 SO 目录复制的源码，跨 SO 导入应单独核对来源。

Web 使用读取接口返回的 `display_code`，只隐藏函数定位头及开头的 Ghidra 生产者注释，保留普通注释和代码正文。接口中的 `code` 仍是文件原始片段，`sha256` 仍覆盖该片段；提交建议的冲突检查和任务快照使用原文，不改用展示文本。结束标记位于片段边界之外，不显示在 Web 正文中。状态和文件路径在代码上方单独展示。

前端使用随工具提供的 highlight.js 11.11.1（BSD-3-Clause）进行 C/C++ 高亮，深浅主题分别配色，无需在线 CDN。高亮前仅省略开头空白行，保留首个非空行的缩进、中间空行和其他正文；这是展示处理，不写回文件或改变接口中的原文与摘要。源码先安全转义再生成高亮标签，资源加载失败时仍显示纯文本。

已有整个源码目录可在任务空闲时调用 `from recovery import migrate_source_markers`，然后执行 `migrate_source_markers(reader)`。工具先校验当前索引，核对转换前后每段正文与来源完全一致，再逐文件原子替换；共享文本、普通注释和正文换行保留。重复执行不改文件。迁移只改机器元数据，原始片段摘要会改变，旧页面需刷新后再提交建议；不在读取请求或任务恢复期间自动批量改写源码。旧单函数文件仍通过 `migrate_candidates` 先打包并核对正文后移除。

## 为什么容易解析

格式将两件事分开：固定前缀负责找到记录，标准 JSON 负责解释字段。解析器使用顺序扫描和一个“区域外/区域内”的状态，不需要用跨函数正则猜测整段代码的边界，也不需要自行实现分号字段、数组、引号和转义规则。

1. 识别真实的 C/C++ 行注释，检查该注释是否独占一行并带 `@lightre.begin` 或 `@lightre.end` 前缀。
2. 将前缀后的文本交给标准 JSON 解码器，并按上述格式校验。
3. begin 建立当前区域，end 必须匹配当前 ID；记录原文件中的边界字节位置，不靠计算花括号数量结束函数。
4. 文件结束时不得有未关闭区域；同一当前源码集合中 ID 不得重复。嵌套、孤立 end、ID 不匹配和损坏的保留标记都报告具体文件和位置，拒绝发布。

扫描器必须跳过字符串、字符字面量、块注释、C++ 原始字符串及续行等词法上下文，防止源码里的示例文本被识别为标记。单纯对每一物理行调用 `startswith()` 不足以保证这一点。可以复用合适的词法器或实现受支持 C/C++ 源码范围内的小型扫描器；无需为定位功能构建完整语义 AST。遇到无法可靠处理的词法结构时报告解析失败，不猜测位置。

begin/end 的显式配对让格式错误可检测；JSON 使字段顺序与空白不影响含义，并提供明确的数组和字段类型。JSON 本身不会保证 Agent 写出的来源关系在语义上正确，后端仍需检查目标实体存在，具体覆盖范围仍依靠证据和验证。

## 重命名、移动、合并与拆分

| 修改 | 关系维护 |
| --- | --- |
| 重命名、移动、同一逻辑声明的改写 | 保留 ID，重新派生文件路径和字节范围 |
| 多个函数真正合并成新声明 | 分配新 ID，`origins` 列出相关原始 RVA，`replaces` 记录旧源码 ID |
| 一个函数拆成多个声明 | 各新声明分配新 ID，可关联同一原始 RVA，记录被替代 ID |
| 抽取辅助函数 | 分配新 ID，以 `derived_from` 引用来源源码实体；没有独立原始函数入口时 `origins` 为空 |

例如，合并后的 begin 可写为：

```c
// @lightre.begin {"v":1,"id":"f003","origins":["0x1000","0x1020"],"replaces":["f001","f002"]}
```

原始 RVA 与源码 ID 是多对多关系，不再使用 `function_rva` 单列主键来代表一个源码片段。Web 点击原始 RVA，先查询全部当前源码 ID；一个结果直接显示，多个结果提供简单选择或依次查看，不任意截取第一个。通过多个原始 RVA 进入同一个合并结果时读取同一份源码，不制造副本。

### 地址定位必须保持的约束

定位保证覆盖合法发布的重命名、移动、合并及拆分，不依赖 LLM 遵守提示词。后端以已发布的身份和来源关系为校验基准；LLM 提交的注释是待校验输入，不能覆盖唯一的既有记录。任意改名不影响地址关联，但来源漏写、身份被改或文件损坏必须拒绝发布，保留上一份完整结果；不能声称可以从任意破坏后的代码自动推回正确来源。

例如两个函数合并，当前来源索引应为：

| 原始函数 RVA | 当前源码 ID | 当前文件与声明 |
| --- | --- | --- |
| `0x1000` | `f003` | `src/parser.c` 中的 `parse_request` |
| `0x1020` | `f003` | 同一份 `parse_request` |

此时点击任意一个地址都打开 `f003` 的当前正文。再次改名或搬文件仅更新派生名称与位置；再次合并为 `f004` 时，新声明承接全部来源，两个原始地址都转向 `f004`。原始 `functions`、汇编及按原始 RVA 保存的知识、证据、任务继续保留，不因源码合并而删除。源码名称、文件位置和引用等派生索引必须更新，不能把“原始身份不失效”误解为 SQLite 的所有字段都不变。

发布入口必须检查：

1. 普通重命名、移动和正文改写保留既有源码 ID 及来源；ID 改变只能通过显式新建/替代声明处理，不能当作一次普通改名。
2. 合并声明的来源至少包含所有被替代声明的原始来源；拆分后的当前结果来源并集覆盖旧来源。后端从旧发布记录计算应继承集合并与本次提交核对，不只检查提交的 RVA 是否存在。连续多次合并或拆分也遵循该规则。
3. 本次发布前已有源码映射的每个原始 RVA，发布后仍至少关联一个可读取的当前源码声明。旧声明退出当前选择时，替代结果必须在同次发布中接上，不能先删除旧映射再等下一轮生成。尚未还原的原始函数可以明确没有源码，但不能把本次丢失的映射悄悄降级成“尚未还原”。
4. 每条当前来源关系都指向存在的原始函数与已登记源码；其标记、文件版本、内容摘要和字节范围一致。范围失效、文件缺失或读取失败时显示明确错误，不按名称或相近地址跳到别处。
5. 上述检查与完整扫描成功后才切换当前关系和 revision；失败保留旧发布及其文件。已发布文件被外部直接破坏且无法读取时必须报错，不能保证读取被删除的内容；正常 Agent 工作使用草稿和统一发布入口，避免破坏当前可读结果。

多对多可分步开发，但它是“函数合并后仍能按全部原始地址定位”的必要交付条件，不能用当前一对一实现通过这项验收。定位准确只保证代码身份及来源关系连续，不证明 LLM 合并后的代码在行为上等价。

## 索引、发布与 Web 读取

SQLite 至少派生以下信息，具体表名在实现时确定：

- 文件记录：相对路径、文件内容哈希、发布版本。
- 源码实体位置：源码 ID、所属文件版本、标记及正文的字节范围；行号仅供阅读。
- 来源关联：原始函数 RVA 与源码 ID 的多对多映射。

字节范围依据原文件记录，不能用解码后的字符下标当作 UTF-8 文件偏移。保留文件原有换行和正文；Web 展示与编译读取同一版本，不重新拼接或改写正文。

```text
Agent 修改当前工程或草稿
  → 发布入口扫描标记、校验 ID 与来源、固定文件内容版本
  → 在同一事务更新当前索引及发布 revision
  → Web 按 revision / 原始 RVA 查询当前源码 ID
  → 按源码 ID 找到文件版本与字节范围
  → 读取并展示实际源码
```

多文件改动作为同一发布结果可见。沿用整体设计中的文件版本和 SQLite 发布事务：先写完整版本文件，校验成功后再登记并切换当前选择；扫描不完整或发布失败时保留完整旧发布结果。没有完成定位校验的新文本不能冒充已发布结果。

Agent 直接修改可编辑工程时也必须经过同步发布入口。启动、显式同步和请求目标文件时检测外部变化；检测到文件已改变或缺失，先同步成功再展示最新结果，或明确报告不同步。不能把旧字节范围用于新文件，不能把旧版本验证结论套到新内容。

Web 约每 3 秒查询轻量发布 revision 和进度，源码、路径、来源、Knowledge 或结果状态的发布变化均应反映到 revision，不以任务计数变化代替源码变更检测。版本变化后只重取当前需要的源码、笔记和发生变化的列表信息。响应返回对应 revision 和文件版本，迟到的旧响应不得覆盖新结果；历史视图保持所选版本。

前端分别记录“已观察版本”和“已成功显示版本”。有建议草稿或读取失败时，待刷新版本仍保留；清空/提交草稿后或下次重试时继续加载，不能提前把该版本记为已经显示。建议提交携带实际显示的源码 ID、版本和内容摘要；内容过期时提示并保留草稿。

## 性能边界与实现顺序

不用正则不等于一定更快。首次构建索引仍需线性扫描源码，复杂度为 O(文件总字节数)；JSON 解码也有开销。性能收益主要来自解析结果可复用，以及 Web 不重复扫描整个工程。

先保持当前索引完整事务替换的简单语义。相同文件内容哈希的解析结果可在进程内复用，变动文件重新解析；缓存不可用时允许重新扫描，不增加独立缓存服务。读取时只处理目标文件：缓存未命中时读取该文件并校验登记哈希，再按字节范围切片；已校验内容可按文件版本复用，检测到外部替换、修改或删除时必须失效并重新检查。重启后可从文件与索引恢复，不依赖常驻监听或会话内存。

推荐实现顺序：先在现有一对一 RVA 链路补齐当前名称读取与提示词约定，再补原始调用的地址绑定；工程级改名接通多文件一致发布和源码引用检查后再启用。多对多、无来源 helper 和完整历史版本按真实需要引入，不要求为了名称展示先实现全部长期能力。标记迁移核对代码正文不变；禁止直接移除旧格式导致已有候选丢失。当前 `history/` 是已有函数目录重新发布前的备份，不承担每轮源码版本管理，本方案也不把现有备份当作源码发布版本。

验收使用临时小文件覆盖：重命名、移动、合并、拆分、新增 helper、中文与 CRLF、JSON 字段顺序变化、字符串中的伪标记、损坏或重复标记、外部修改、发布中断，以及有草稿或请求失败后仍能加载待刷新版本。保持 Web 为预览和修改建议入口，无需增加复杂面板或要求逐函数认可。

## 实现前检查结果与交付边界

以下为当前代码检查结果，不代表上述设计已实现：

| 检查项 | 当前结果 | 实施要求 |
| --- | --- | --- |
| 原始函数及汇编身份 | `functions.rva` 为主键，汇编按 `function_rva` 关联 | 保留；不迁移成名称键 |
| 源码改名、移动后定位 | JSON 标记、ID 保留和内容指纹已实现 | 继续按 RVA 查来源，不从函数名取地址 |
| 当前名称 | candidate 已返回 source_name/source_id，详情标题显示当前名；catalog 仍取原始清单 | 后续更新列表和搜索 |
| Agent 身份约定 | 多处提示词仍称 `fcn_<RVA>` 为稳定标识 | 改为 RVA/已有注释 ID；可读名称允许修改 |
| 局部改名 | 普通文本 edits 会替换全部匹配项 | 不建立变量身份表；使用完整函数或精确补丁，核对无关文本 |
| 跨函数改名 | 单 RVA 发布不会同步其他调用方 | 先支持相关文件一致发布和引用检查，再开放工程级改名 |
| 函数内点击调用 | 已实现后端派生 C 调用范围、ARM64 直接调用目标及前端按 RVA 跳转 | 尚无持久化引用表、完整编译器语义或多对多来源支持 |
| 合并、拆分和 helper | 当前 source_index 明确拒绝一对多/多来源 | 后续扩展来源关联，不给新声明虚构 RVA |

最小实施检查使用临时数据完成：不同 RVA 同名仍独立；改名、搬文件后 ID、RVA、知识、评论与选中目标不变；列表及搜索读取新声明名；`param_1` 改名不误改 `param_10` 或字符串；已有调用方/声明/取地址引用一起修正，漏改不能报告重命名完成；同名 static 函数按文件作用域绑定；未解析或过期引用不跳转。多文件发布加入后，再验证发布失败仍读取完整旧结果。

完整地址定位验收另须覆盖：两个原始函数合并后分别点击两个地址均打开同一份当前正文；合并后再次重命名、搬文件及再次合并仍可从所有原始 RVA 进入；拆分后可枚举全部关联声明；LLM 漏写一个旧来源、删除身份标记或引用不存在的被替代声明时发布失败且旧结果仍可读取；重建索引和重启后关系保持一致。多对多是这项完整保证的必要条件；无原始入口 helper 的分配检查随对应功能加入。

## 快速后端 API 测试

测试文件为 [test_source_api.py](../../tests/test_source_api.py)，使用 unittest + FastAPI TestClient 在进程内发出 HTTP 请求；不启动 Uvicorn、浏览器或真实监听端口。每个用例创建独立临时目录，只有两条函数、两条汇编及少量 C 源码，不需要原始 SO、Ghidra、clang-format 或 LLM。调用真实路由、WorkspaceReader、源码索引和任务持久化；只屏蔽评论任务的后台执行与 Codex 路径发现，意外启动任何子进程均使测试失败。

首次安装开发依赖，之后只运行第二条命令；命令均从工具仓库根目录执行：

```bash
uv sync --locked
tools/venv/bin/python -m unittest discover -s tests -p 'test_source_api.py' -v
```

当前快速测试覆盖：

| 场景 | 通过 API 检查的结果 |
| --- | --- |
| 不同 RVA 使用同一原始函数名 | 列表保留两个对象，各地址返回正确源码及汇编 |
| 同一个函数连续多次改名 | 正文更新，既有注释 ID、来源、知识及邻接函数保持正确，原始数据不变 |
| 等长改名、保留时间戳并搬动模块 | 相同客户端请求同一 RVA，读到新正文和路径，无需重启 |
| 删除派生索引后重新创建 reader/app | 从实际文件重建，源码、知识和原始数据保持一致 |
| 不同 SO 使用同一 RVA 和默认源码 ID | 请求只返回各自目录的结果，不跨 SO 串联 |
| 改名前后提交评论 | RVA 与旧 reviewed.c 快照保留；重复提交已有活动任务返回原任务，不创建副本；新评论绑定旧摘要返回 409，新摘要可提交 |
| 源文件标记损坏 | 源码 API 返回 409，原始表和先前有效索引不被清空；修复文件后可重新读取。此项不冒充已实现不可变版本回退 |
| 没有源码、未知 RVA、非法地址 | 分别明确返回 missing、404、400，不按名称误匹配 |
| 源码调用、中文、emoji 与 CRLF | 引用只覆盖实际调用，UTF-16 范围截取正确，按 target_rva 读取目标源码 |
| 被调函数改名、搬文件，调用方正文不变 | 旧符号链接失效；调用方同步修改后仍指向相同 RVA 与源码 ID |
| 不同文件同名 static、局部回调与宏 | static 按文件绑定；参数/局部函数指针遮蔽、宏、注释和字符串不误跳 |
| 同名全局与类似地址的名字 | 歧义不生成链接，不按函数名后缀推断 RVA |
| ARM64 BL/B/BLR | 从字节验证正负偏移、递归和尾调用，内部 B/未知地址/间接调用不生成目标 |

测试读取 GET `/api/functions`、GET `/api/functions/{rva}/candidate`、GET `/api/functions/{rva}/assembly`，并实际提交 POST `/api/functions/{rva}/feedback`。源码准备直接调用真实保存函数，不为测试增加发布 HTTP 端点。测试不仅断言 HTTP 200，还核对正文、来源标记、路径、摘要、知识及持久化任务；通过读取原始表确认派生索引更新未破坏函数与汇编。

下列场景必须随功能实现增加真实 API 验收，目前不计为已通过，也不以 expectedFailure/skip 或 mock 映射替代：

- 合并发布后分别 GET 两个原始 RVA，返回的当前源码 ID、文件及正文一致；再次改名、移动和连续合并后重测全部原始 RVA。
- 拆分发布后按原始 RVA 枚举全部当前声明，不任意返回第一项；清除派生索引并重开应用后结果一致。
- 新结果漏写已有来源或中途发布失败，发布入口拒绝切换；同一客户端继续 GET 全部旧地址，仍返回完整旧发布。故障注入只作用于写文件/提交边界，不伪造查询结果。
- 当前源码名称进入列表和搜索；完整编译器语义下的引用与多文件改名一致发布。当前仅支持上述受限 C 调用绑定。

未来合并测试同样调用真实后端发布函数准备结果，再由 HTTP 读取验证；不得直接手写 source_index 关系让查询看似正确。优先验证后端身份、来源继承与发布一致性，前端点击只负责使用已测过的接口，不把 Playwright 作为验收前置。
