# V0.31：通用 harness 执行与修复

状态：开发实现及真实运行已有记录，仍待用户人工验收。本版是 [V0.3 第三阶段](../v0.3/PLAN.md)的首个增量，负责原 SO 运行、记录、重放与 harness 修复。本文维护该增量的最终范围和验收条件；当前功能及命令统一见 [功能说明](../../USAGE.md)，实际结果见 [DELIVERY](DELIVERY.md)。候选构建、双边差分和语义反馈修复由 V0.3 总体计划后续小步承接，不纳入 V0.31 验收。

## 用户结果

2026-11-02 用户修正本版实现方式：新增 [rehost](../../USAGE.md#rehost-从零生成)，使用代码与 Markdown workflow 从空目标工程调查入口、生成 unidbg harness，并按真实运行补环境；移除 examples 中预制目标 harness 与复制分流。原有运行、快照、重放和固定契约检查继续复用。无独立预期时只报告 observed，不自动通过固定行为验证；从零链路的真实模型/unidbg 验证单列，不能沿用旧模板运行结果。

用户可为 Android ARM64 SO 关联目标专用 Maven/Java harness、固定输入、独立检查器和产物列表。工具构建并运行，从真实输出进行外部核验，保存足够的源码、输入、规则和依赖依据供重放；harness 未满足契约时，最小循环携带完整失败记录调用 Codex 修复，再实际检查。

本版包含原先的纯 native 开发 smoke，以及用户后续授权的 DG JNI、minilua Android SO 单边适配。两者已有真实运行，不再列为“后移”。V0.2 静态候选流程保持独立，单边运行通过不表示恢复候选已验证。

## 维护与优化计划

状态：2026-11-02 按用户确认纳入 V0.31 收尾，以下均为待实施工作。本轮补充无用代码清理、目标目录、实施依赖及验收依据；只更新开发计划，不据此宣称重构已完成。目标是职责清楚、减少重复实现、保留现有可恢复行为，不以文件数或代码行数作为完成指标。清理清单和实施结果分别在本文及 DELIVERY 维护，不另建同职责文档。

### 已确定的约束

- LightRE 是容器内运行的独立工具，业务模块保持在 src/agents、src/analyzers、src/recovery、src/execution、src/rehost、src/webui 等目录，不统一搬入 src/lightre。仓库入口能直接启动，不要求先安装 LightRE 自身；已有包入口、资源位置及后台启动代码在整理时一起核对。pyproject、锁文件如保留，用于统一依赖及开发工具配置，不维护重复依赖清单。
- 产品入口是常驻 Python 服务：main.py 启动 Web/API 与主循环，由系统接收目标、恢复任务、管理多个 Codex CLI 工作会话、组织上下文和检查结果。空闲时等待请求/任务事件，不反复调用模型；会话按需建立，活跃 CLI 受并发额度与 SO/harness 写锁约束。LightRE 集成 Codex CLI，项目不以外部 Codex 加载 Skill 作为产品入口。
- 系统提供一个面向用户的持久指导会话及聊天窗口，负责理解目标、解释进度和通过系统接口提交/控制任务；后台工作会话独立执行。指导会话与工作会话共用 agents，分别记录上下文及 session/run 关联。关闭窗口、断线或指导会话失败不取消已提交任务；服务重启先核对持久记录与进程租约，不重复启动仍在途的写入者。
- Skill/prompt/workflow 只作为内部模型操作指令，优先复用现有资源；记录每轮实际指令、任务、返回和检查依据，不建立同职责副本。根 SKILL.md 暂作旧调用方式兼容，服务启动不依赖它；待入口收敛后清理其中的重复指导。V0.31 先接通服务、指导窗口与 harness/rehost 的窄范围编排；静态恢复仍是一轮处理及有限失败重试，完整候选差分循环按 V0.3 后续计划实施。
- agents 继续使用标准库 sqlite3，保留会话、FIFO、请求去重、执行状态和取消标记的事务管理，不引入 TinyDB 或另写 JSON 数据库。数据库访问集中，事务短，不在执行模型或编译器的长过程中持有写事务；进程租约与 SO/harness 锁继续约束实际写入者。
- prompt、完整返回、事件流、源码、知识、输入、构建日志和 SO 等继续保存为文件，数据库保存必要状态、关联及内容依据。每类可变状态只有一个权威来源；agent 的执行完成与业务检查通过分别表达，业务任务引用 session/run ID，不复制维护同一执行状态。
- 既有静态队列和 harness 的 JSON 状态格式在本次整理中保持兼容，不为格式统一额外迁移进 SQLite。现有 Agent 数据库也不并入每个 SO 的静态索引；未来统一任务调度时再单独设计迁移。
- 保留有效的旧 workspace 迁移、恢复和历史重放支持。用户样本、外部分析目录及历史 Run 不属于无用文件清理范围。尚未接入的候选构建/差分 workflow 核对后归入设计资料，避免被当作当前运行入口。

### 目标项目结构

以下是整理目标，不是当前目录已完成的描述。优先复用既有模块，不为每个概念增加目录；文件仅在存在明确职责或多个实际调用方时拆出。

```text
main.py                         # 常驻服务入口；参数解析后启动同一服务实现
src/
  service.py                    # 生命周期、任务协调、并发准入与启动恢复
  paths.py                      # 仓库、工具及资源定位；不依赖调用 cwd 或安装元数据
  agents/                       # Codex 会话、SQLite 状态、消息执行与进程归属
  analyzers/                    # 静态工具适配及必要迁移
  recovery/                     # 静态批次、模型业务协议、候选/知识发布
  execution/                    # 原生工具运行、固定契约、快照与重放
  rehost/                       # 目标工程准备及正在使用的 workflow
  webui/                        # FastAPI 路由、指导聊天与静态资源
  workspace.py                  # 目标身份、导入及工作区读取
scripts/                        # install_deps.sh 与确有独立用途的开发命令
tests/                          # 按模块/行为组织的轻量回归和人工验收说明
examples/                       # 独立检查器、用例和开发 smoke
samples/                        # 原始样本及 minilua 源码适配
docs/                           # 沿用当前文档分层；未来 workflow 归入对应设计资料
```

`service.py` 只做协调，不接管业务提示词、源码发布或工具检查。`webui` 调用服务接口，不在创建应用时启动恢复 worker；不要求已有导出完成的 SO 才能启动服务。服务生命周期内统一恢复和接纳任务，路由按请求绑定 workspace/目标。必要的通用进程与文件操作可抽为 src 下的小模块，只有确认多个调用方及相同语义后才提取，不建立通用框架。

`src/lightre/` 中现有 CLI、paths 和资源先迁移调用方，再删除失去用途的包装；不直接整目录删除。运行时 prompt/workflow 留在所属功能目录，Web 静态资源留在 webui，Ghidra Java 脚本留在 analyzers；clang-format 风格保留一个权威文件并修正快照来源，不保留仅为打包而存在的资源副本或悬空符号链接。

### 实施顺序

| 顺序 | 工作 | 可检查产物 |
| --- | --- | --- |
| 1. 建立基线及确认删除项 | 核对入口、导入、动态调用、资源、依赖、文档和测试引用，记录现有行为及未提交改动；完善上表的保留/合并/删除结论 | 基线轻量回归结果及已知缺口有记录；可独立删除的叶子残留先清理；不误删用户数据或开发中代码 |
| 2. 统一模型执行与基础操作 | 将 recovery/jobs.py 和 execution/loop.py 的 Codex 启动收敛到 agents；共用必要的进程清理、JSON 原子写入与哈希，删除替代实现 | 统一层支持现有静态/修复协议、独立轮次和持久会话；首轮工具限制、批次并发、评论优先、互斥及完整输出保持正确；调用方只保存执行引用和业务状态 |
| 3. 优化 agents 持久化访问 | 普通状态读取与失效 owner 恢复分开，初始化/迁移集中；历史查询分页，减少高频取消轮询；核对 request/prompt 重复正文 | 高频查询不逐次申请写锁或加载全量历史；启动/owner 交接仍核对在途进程；FIFO、请求去重、取消和旧记录一致性有回归依据 |
| 4. 接通服务生命周期与调度 | main.py 启动现有 FastAPI 和主循环，将 worker 启动从应用构造移入服务生命周期；集中并发准入、项目锁和重启恢复；harness 反馈/停止由协调层组织 | 未选择 SO 时服务也可启动；各类工作共享活跃进程额度，指导会话有保留容量/明确优先级；不重复启动在途写入者；空闲不调用模型；不建立第三套持久队列 |
| 5. 接通指导窗口与任务接口 | 使用同一 agents 层提供指导会话、任务提交/查询/控制及事件展示；兼容入口委托同一业务实现 | next_turn 排队语义明确；工作不阻塞 API，窗口断开或指导会话失败不取消后台任务；重连可读历史；重复控制请求不重复创建工作 |
| 6. 收敛目录、入口与业务接口 | 按目标结构迁移 paths/CLI/资源及后台启动方式，清理打包专用分支；明确 rehost/execution/recovery 边界，消除跨模块私有调用；按清单删除已替代代码和未接入资源的运行时假入口 | 仓库直接运行且不依赖 cwd；Python 依赖一个维护来源；核心无样本分支；删除项无失效引用，必要兼容保留；旧路径不再有第二套执行逻辑 |
| 7. 整理复杂文件并收尾验证 | 按职责拆分仍复杂的源码及测试，按需拆静态资源；核对无用导入/函数/配置/依赖及文档入口；汇总删除与迁移结果 | 完整轻量回归通过；未解决失败列为阻塞项，不标记相应工作完成；DELIVERY 逐项记录实际处置和证据；真实集成缺口与人工验收状态独立保留 |

步骤 2 中各业务保留批次选择、上下文、结果发布及独立检查规则；步骤 4 主循环消费检查结论组织反馈与停止，agents 只判断模型单轮协议是否完成。静态业务队列负责函数范围、评论优先与本业务并发上限，agents 会话队列只保证同一会话的消息顺序；服务负责跨任务的总活跃额度，各层不重复拥有业务任务状态。接入时须保留 SO/harness 锁与子进程租约，取消或异常后等待实际写入者退出再检查或续做。不能因增加主循环或接入 agents 就改变一轮静态恢复策略、自动追加语义任务，或将模型正常退出当成 harness 验证通过。

步骤 3 不能直接删掉查询时的失效 owner 核对而留下无人恢复的状态，需先接好明确的恢复责任方，再使普通查询只读；SQLite WAL 按并发读写需要评估，不用它代替缩短事务。Agent request 与 prompt 的重复正文在此步核对权威内容及必要快照；若精简数据库中的重复正文，以固定路径及内容哈希保留请求去重依据，执行前校验真实内容，兼容旧记录，不削弱请求一致性检查。步骤 6 仅凭没有内部导入不能删除已声明的可用 API；例如可选 Rizin 包装须连同文档和实际用途核对后决定。

### 收尾验证条件

1. 从仓库和其他调用目录均能启动指向本仓库的命令，前台与后台使用同一依赖环境；资源定位正确，没有第二套同职责入口实现。
2. agents 的并发提交、同会话 FIFO、请求去重、不同会话并发、取消、超时、进程异常及恢复行为均有轻量回归；SQLite 继续作为其状态权威来源。
3. 静态批次并发、评论优先、暂停/恢复、无效输出有限重试、内容冲突及源码/知识发布检查继续通过，既有 workspace 和任务记录可读取。
4. harness 的固定契约、输入/检查器保护、互斥、快照、重放和 observed/passed 区分继续通过；失败或旧报告不能被误判为当前通过。
5. 删除和移动的文件已修正全部引用，现有必要的迁移与测试没有因精简丢失；功能说明、设计边界和实际代码一致。
6. 常驻服务通过 agents 管理指导会话与后台工作会话，实际任务上下文及内部指令可追溯，完整结果进入业务核验；模型仅声明完成或检查失败时不能完成业务目标。兼容入口使用同一编排；暂停/取消不绕过锁，不另起竞争主循环，静态一轮任务不变成无限续做。
7. 指导窗口可以发送消息、接收事件与完整回复、读取真实任务进度，并通过系统接口提交和控制工作。忙时消息按当前 next_turn 能力明确排队；窗口关闭、重连或指导会话失败不丢失会话引用、不停止其他工作任务。常驻服务重启后先核对在途写入者和检查点，空闲期间不产生无任务的模型调用；任务控制去重，重复请求不创建重复工作。
8. 上述清理清单逐项有明确结论；已确认无用途的模板、包装、死分支、导入及配置已删除，合并实现的旧路径已移除。必要保留项注明当前调用方或兼容依据，不用“可能以后需要”保留无执行用途的代码；未来方案保存为设计资料。
9. 总活跃额度覆盖指导与后台模型调用，同会话仍串行；状态读取不会每次进入写事务或返回无限增长的全量历史。恢复和取消保持正确，不能以减少查询为由跳过在途进程核对。
10. 目录整理后的 main、开发命令、生成给模型的命令、后台 worker 与测试使用同一内部导入/资源规则；无悬空符号链接、失效模块路径或仅依靠已安装旧包才能通过的检查。现有测试按行为保留，新增检查只覆盖真实迁移风险，不为删文件编写镜像测试。

各步完成后运行受影响的轻量检查，最终运行一次完整轻量回归。模型、Ghidra、真实 unidbg 和浏览器不作为目录整理的日常回归；本版尚缺的新 rehost 真实集成验证仍独立记录，不能由轻量回归替代。结果归入 DELIVERY，人工验收状态由用户决定。

## 人工验收

1. 对 smoke 的普通输入、不同参数、整数边界/空输入及容量不足实际调用 SO，观察与独立预期一致；失败返回明确非通过记录。
2. 查看新目标关联配置，确认通用执行器无需增加目标名称分支，可使用自定义入口、参数和多个产物。
3. 查看 DG 真实注册、有效 handle、init/ss 两阶段核心命中、非空实际返回、close 完成及无未知 JNI/模拟错误；结论只适用于声明的 headless fixture。
4. minilua Android small/large 各自运行八个固定用例，核对完整 stdout/stderr、状态、执行入口及 Proto；Linux 样本与 C 源码归属保持正确。
5. 修改当前可编辑 harness 后，从新格式 Run 的旧源码/输入/检查器副本重放；原始输入已删除仍可读取快照。SO、依赖、历史规则或产物被改变时不得通过。
6. 从一个有实际错误的 harness 开始，外层先捕获失败，模型修复后实际通过；模型仅声称完成时继续反馈，不以 CLI 退出码或旧报告代替检查。
7. 每轮有完整返回、事件、退出状态和检查引用；空返回、检查器故障、超时、取消、中断、上限及共享写入冲突均保留真实状态，恢复时重新核对当前文件。
8. 按说明能准备依赖与工程，入口无需 Web、浏览器或 Ghidra；普通开发回归使用轻量临时数据，真实工具/模型验证另留记录。
9. 通过常驻服务的指导窗口提出目标并提交任务，查看后台执行状态和完整回复；关闭窗口后工作继续，重连可恢复历史及进度。聊天与长任务不会相互阻塞，暂停/取消明确作用于所选会话或业务任务。
10. 启动、重启与恢复时服务能核对 SQLite、业务记录和实际进程，避免重复模型调用及竞争写入；指导与工作会话有独立身份，数量增加仍受并发和项目锁控制。新增服务/聊天链路的真实验证另记，不沿用旧 Web 或 CLI 测试宣称通过。

人工验收不因开发测试通过而自动勾选。DG/minilua 的单边适配已有实测；二者由模型自动修复的效果尚未实测，不能把 smoke 的真实修复结果外推。
