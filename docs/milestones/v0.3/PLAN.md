# V0.3 总体方案：单函数动态差分与自动修复

状态：后续能力总体方案，尚未实现或验收；V0.2 已于 2026-11-01 单独通过用户人工验收。按用户反馈，先拆出 [V0.31：最小 unidbg harness 与任务循环](../v0.31/PLAN.md)，用简单 Android ARM64 测试 SO 跑通纯 native 调用、结果保存和重放，并接入按轮保存原文、反馈真实失败的 harness 修复 loop。本文完整闭环不再作为下一个小版本一次性交付的范围。

本文落实 [后续路线](../../IMPLEMENTATION_PLAN.md) 的 D1，采用 [Goal Loop](../../GOAL_LOOP.md) 的执行与验证闭环。最小 harness 任务循环从 V0.31 开始；DG 的 JNI 适配、minilua 的 Android SO 改造、候选构建、双边差分及语义自动修复分别后移，按实际进展再定小版本，不将两种目标适配同时设为前置。

## 用户结果

用户提交一次目标 SO、选定入口和相关材料后，LightRE 运行原实现、整理并构建该范围的候选、双边比较；发现差异时保存反例并自动继续修复，最终返回实际检查结果、源码和复现资料。遇到无法补齐的前态或环境时保存具体缺口，不能将生成候选、模型声称完成或 CLI 正常退出当作验证通过。

本总体方案从“静态候选生成”进入“行为反馈驱动还原”。完整闭环的交付重点是一个真实、边界明确的函数或逻辑单元，并具备针对目标 VM 的原实现运行记录；不要求全 SO 可编译或一次还原整个 VM。V0.31 的交付边界仍以其独立计划为准。

当前已确定的运行范围为 ARM64 + unidbg，minilua 也使用这条路线。minilua 另建 Android ARM64 SO 测试版本，纯 C 接口直接调用；DG 按目标需要接入 JNI。Qiling、其他架构及多后端框架不属于当前开发范围。

## 范围

1. **原实现可重放。** Codex 为选定 SO 复用、适配或创建最小 unidbg harness，准备依赖、初始化、参数和相关状态，JNI 只在目标依赖时加入。DG 使用已有 `.bin`，minilua 按用户确认使用 `.lua` 并由自身解析器生成内部字节码；优先选择一份并核对其目标版本、加载方式和所需上下文，跑通后重放其余种子，不以开发生成器或外部 luac 加载器为前置。区分虚拟程序与业务输入。每次实验保存实际使用的 harness、输入、环境假设、目标与资源来源、命令和原始结果。缺失 JNI 明确报出签名，不统一返回零或空值。
2. **候选可构建和运行。** 从 V0.2 的静态候选出发，整理选定函数所需类型、声明和必要依赖，构建 ARM64 候选 SO；用独立 unidbg 实例及候选实际入口执行。待验证逻辑不能回调原 SO 代算，原实现参与其他依赖时必须明确记录，不能宣称候选已经独立覆盖该部分。
3. **可解释的差分。** 用例明确参数、相关内存与别名、对象/全局状态、必要历史调用及观察范围；两边状态按含义对应。控制或记录时间、随机数及相关 JNI 响应，比较返回值、输出及声明副作用，不比较裸指针数值或整份无关内存。基本粒度为完整函数/逻辑入口；需要定位差异且双方已有可对应边界时，增加虚拟执行进度检查点，先针对具体样本采集和比较，不以自动对齐任意重构代码作为本版前置。
4. **反例驱动自动修复。** 在 V0.31 最小任务循环上加入候选构建和差分检查，将具体失败与累计反例反馈给下一轮。默认每轮独立调用 Codex，由程序保存实际 prompt、完整返回、事件和日志并组织 context，不依赖会话恢复。沿用已有知识与任务记录；模型修改授权草稿及必要 harness/构建文件，任务状态与通过结论由执行器核对后维护。
5. **复现与基本续做。** 结果绑定实际源码、构建产物、harness 和用例内容。源码变化后旧通过结论不再适用于当前内容。支持取消、检查点恢复、检查器失败及有上限的基础设施重试；复用同一 SO 的执行互斥，与现有批量候选任务协调，不并发覆盖同一工作。

成熟任务由工具自动推进以上步骤，用户不逐轮批准运行、选择文件或手动传递失败日志。现有 V0.2 只读分析并返回函数 JSON 的批量流程继续保留；动态工程任务采用单独的可编辑草稿与验证流程，不能直接取消原批量提示中的边界便视为接入完成。

## 开发顺序及可检查产物

| 小步 | 实际产物 | 检查 |
| --- | --- | --- |
| V0.31 基础任务循环 | 简单测试 SO 的 harness、每轮完整结果和实际检查记录 | 失败反馈到下一轮；固定用例实际运行通过后才报告 harness 任务完成 |
| 0.3-A 原始运行 | 一个真实入口的 harness、可运行虚拟程序种子与 Run | 新会话可以按保存材料重放相关输出或状态变化，确认字节码实际进入目标 VM |
| 0.3-B 双边比较 | 一个可执行候选、构建记录和差分报告 | 能定位实际输出差异，而不只是双方均正常退出 |
| 0.3-C 差分驱动修复 | 接入语义差异的任务循环、反例及修复后的候选 | 差异自动反馈；修复后重跑原用例及累计反例 |
| 0.3-D 续做与交付 | 可恢复任务、最终源码及复现说明 | 中断后核对当前文件继续；只有当前内容通过才报告范围内通过 |

这些是总体闭环的能力检查点，不强制对应版本编号。V0.31 先建立纯 native harness 及最小任务循环，不要求达到 0.3-A 的真实 VM 运行条件；后续再安排目标适配与双边验证。成熟工具执行任务时，不把内部步骤变成人工逐轮确认节点。

V0.31 使用小型纯 C 测试 SO 验证 harness。后续目标适配时评估已有 DG unidbg runner 的复用可能，或单独推进 minilua Android SO，先选一个。完整闭环的真实交付仍应包含目标 VM 的运行证据，以及一个与目标调查相关、输入和状态可明确准备的逻辑单元的差分修复；简单测试 SO 的通过不能代替该项。具体入口依据实际样本与可重放条件选择，不预先写死 RVA。

minilua 的运行环境需单独区分：仓库现有 small/large 交付物是依赖 glibc 的 Linux AArch64 PIE 可执行文件，使用 `/lib/ld-linux-aarch64.so.1`、`libc.so.6` 与 `libm.so.6`，不能仅凭同为 ARM64 就视作可直接在 unidbg Android 环境运行的 SO。当前采用独立构建 Android ARM64 SO 并导出薄 C 测试接口的方案，无需 JNI；先跑通基础加载调用，再复用兼容的混淆构建和还原差分流程。新构建是独立分析目标，单独记录工具链、混淆配置、哈希、地址与检查结果，不沿用原 ELF 的 RVA 或运行结论。保留原 Linux 样本；Android 版本构建和 unidbg 运行尚未实现或实测。

统一的 ARM64 unidbg 用例、观察和比较方式，以及 minilua SO 适配步骤见 [动态差分设计](../../DIFFERENTIAL_EXECUTION.md)。公共比较逻辑通过普通函数在目标间复用，harness 按目标准备状态，不为暂未需要的运行器预建抽象。

候选构建产物保存为当前 SO 分析目录下的 `runs/<build_run_id>/build/libcandidate.so`，同一 Run 保存固定源码输入依据、命令、工具链、选项、日志与产物哈希；差分任务显式引用该产物。每次新构建独立保存，原始 `binary/original.so` 保持不变。该构建保存流程尚未实现。

构建与修复采用功能模块内的 [构建与验证 workflow](../../../src/recovery/prompts/BUILD_AND_VERIFY.md)：一次 Codex exec 内可以持续修改、编译、加载调用和修复；外层 Python 按真实产物与差分结果决定是否续跑。V0.31 先实现 harness 任务的续跑与原文交接，0.3-B 接入候选构建、ELF/ABI 与双边运行检查，0.3-C 扩展为差分失败反馈和累计反例回归。workflow 已提供，执行器及实际运行能力仍待实现，不能以模型说“编译成功”作为验收。

运行记录从本版开始区分合法字节码基线、输入/字节码变异及强制实验，并保存虚拟程序、业务输入、前态和干预依据。底座供三类实验复用；具备具体运行边界后可以开展定点强制实验，不要求先恢复完整字节码生成器。系统性的 fuzz/强制探索自动化按后续阶段展开，不能把它们误解为差分的必经前置或必须等待全 VM 恢复的最后一步。

## 完整闭环验收场景

以下用于后续完整差分闭环；V0.31 只按本版计划验收固定测试 SO 的 harness 与最小 loop，不要求完成下列真实目标场景。

1. 一次提交目标与入口，工具保存原实现运行及候选构建、执行资料；使用说明能从保存材料重放。
2. 在选定真实函数上提供实际错误候选，或在实验草稿中引入一个明确的语义错误，差分检查能发现真实差异。原 SO、固定预期和检查器不因此改变。
3. 同一任务自动把差异交给 Codex，修改候选并重新构建；当前版本通过对应用例，原反例留作回归。未解决时报告具体差异，不把重试或失败算作完成。
4. 修改候选后不继续显示旧内容的通过结论；构建失败、超时、报告缺失、检查器故障和模型空结果均保持非通过状态。
5. 取消和恢复保留源码、知识、用例及执行依据；恢复不重复启动旧执行者或并发修改同一 SO。CLI 会话不可恢复时能从工作区记录继续。
6. 提交结果明确已检查入口、用例、环境和副作用范围，以及剩余未知；交付的源码与实际验证内容一致。有限用例通过不宣称全输入等价或全 VM 恢复完成。

自动化只保留关键数据和故障行为的快速测试；真实样本检查单独记录，不要求浏览器、Web 改版或全套端到端服务测试。此计划本身不构成上述检查已通过。

## 本版边界与后续能力

- 固定用例、边界输入和可重复的少量参数变异属于本版差分用例；不以建设覆盖引导 fuzz 引擎作为验收前置。
- 首个 VM 入口需要的最小状态和调用观测可以随 harness 加入；系统性的取指/解码/dispatch 建模、受控强制执行和局部 MBA 求解归入后续 D2。实际调查遇到阻碍时可使用有记录的局部实验，但不据此承诺通用探索能力已完成。
- 结构化字节码 fuzz 归入 D3，在部分指令边界、编码和必要状态已理解后实施；滚动密钥只作为待排查机制，不认定样本必然具备。
- 完整去虚拟化、跨入口恢复与全工程整理归入 D4；本版先取得相关小范围的真实行为反馈闭环。
- Web 复用现有浏览和任务反馈能力，结果首先以持久报告提供，不扩充 trace、CFG 或 fuzz 面板。

本版涉及现有 `RUN-001/002/008/009/010/011/014–020/024–028`、`EVI-017` 及 Goal Loop 所需最小子集。具体实现仍按既有需求与来源/索引约定；本版通过不自动勾选更大范围的长期需求，也不提前推进后续版本。
