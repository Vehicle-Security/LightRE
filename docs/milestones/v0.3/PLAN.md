# V0.3 第三阶段计划：unidbg 运行与初步差分闭环

状态：第三阶段总体计划，按小步开发和验收，尚未整体交付。沿用仓库的 V0.3 命名；[V0.31](../v0.31/PLAN.md) 是其中的首个增量，仍待用户人工验收。V0.2 静态候选流程已单独验收，不因本计划变更其范围。

本文维护第三阶段的交付目标、拆分与验收条件。长期能力顺序见[路线图](../../ROADMAP.md)，执行与比较协议见[差分设计](../../design/DIFFERENTIAL_EXECUTION.md)，循环与交接见[Goal Loop](../../design/GOAL_LOOP.md)。当前功能和命令只在[功能说明](../../USAGE.md)维护。

## 阶段目标

产品由 LightRE 常驻服务集成多个 Codex CLI 工作会话，并提供一个面向用户的指导聊天窗口；内部 prompt/workflow 指导工作实例，服务器负责后台编排、实际检查及恢复。服务与现有功能的接通先由 [V0.31 维护收尾](../v0.31/PLAN.md#维护与优化计划)承接，不要求用户在外部 Codex 加载项目 Skill。

把静态候选接入真实行为反馈：用户给定目标、相关输入和待恢复范围后，工具调查并运行原 SO，整理该范围的 C/C++ 候选并构建为 Android ARM64 SO，在独立 unidbg 环境中执行双方，比较实际结果。发现差异时保存反例，自动反馈、修改候选、重新构建并回归，最终交付与实际验证内容一致的源码及复现资料。

初步闭环以一个边界明确、状态可准备的真实函数或逻辑入口为交付单位。可以先验证短函数，再扩展到调用链；不要求本阶段一次还原整个 SO 或完成 DG 巨函数的业务语义恢复。

## A：原实现运行与重放

运行后端限定 Android ARM64 + unidbg。工具通过代码和 Markdown workflow 调查真实入口、ABI、初始化及资源，从空工程生成目标 Java harness，并据实际运行失败逐项补环境；执行核心保持通用，不按样本名称分流或复制预制目标 Java 实现。

DG 使用匹配版本的现有 .bin，经实际 JNI 注册及初始化执行；minilua 在原 samples/minilua 源码项目构建 Android SO，通过薄 C 接口运行 .lua，由自身解析器生成 Proto，无需 JNI。保留原 Linux 样本，两者复用各自原 workspace。每个新 SO 独立核对身份、入口、参数和环境，不能套用另一版本的 RVA 或通过结论。

固定实际使用的输入、工程、依赖与环境假设，保存原始日志和运行观察；未知 JNI 或其他依赖明确报告，不用统一零/null 返回或跳过初始化消除缺口。必要环境替身须注明依据和限制。新生成链路的真实验证须重新取得，不能由旧模板时期的 Run 替代。

没有独立已知预期时可取得 observed、passed=false，说明该条件下已有执行观察。固定检查通过只适用于声明的输入和环境；两者都不构成候选差分通过。

## B：候选构建与运行

从当前静态候选和调查结果整理选定逻辑，补足最少类型、声明及必要依赖，明确调用 ABI、整数位宽与实际候选入口。候选按自己的符号或入口映射调用，原始 RVA 只作来源关联。

每次构建固定源码输入、命令、工具链、编译选项、日志和产物哈希；候选保存在当前 SO 的 `runs/<build_run_id>/build/libcandidate.so`，差分显式引用该构建。原始 `binary/original.so` 保持不变，构建失败不能复用旧产物报告成功。源码在构建或验证期间发生变化时，结果不能绑定到变化后的内容。

待验证逻辑由候选实际执行，不能回调原实现代算。调查期间仍由原 SO 提供的其他依赖须列明；最终声称已恢复的范围须由交付源码承担。minilua 的原源码构建只可作样本基准，不能冒充恢复候选构建。

## C：双边执行与差分

为原实现和候选分别创建独立模拟器，重建同一逻辑输入、必要初始化和调用历史。缓冲区、对象、别名、全局状态按含义对应，不直接复制另一模拟器的裸指针或复杂运行时对象。时间、随机数、文件及 JNI 响应中影响结果的部分需要固定或记录重放规则。

优先按完整函数或逻辑入口比较返回值、有效输出内容、相关对象/全局变化及声明副作用；JNI handle 和地址按对象内容及关系规范化。首版不要求指令轨迹一致或自动对齐所有内部状态。双方已有可对应边界时，可以增加局部检查点定位差异，具体规则沿用差分设计。

差分不要求事先人工知道全部正确输出：在输入、环境和观察契约固定后，实际原实现可作为行为基准。原始观察必须绑定真实运行及内容依据；环境仍不稳定或前态未知时，先记录缺口。双方都失败、都缺少报告或都未执行目标逻辑不能判定相符。

每份报告列出原 SO、候选源码及产物、harness、用例和环境依据，保存双方原始结果及字段差异。结果区分用例范围内相符、语义差异、执行/环境失败和未验证。比较规则及基准不由模型为取得通过而放宽。

## D：反例驱动修复与续做

复用已有最小循环，加入候选构建和差分检查：实际失败 → 保存完整记录与反例 → 独立调用模型修改授权源码及必要适配 → 外层重新构建、执行并检查。模型声称完成或 CLI 退出码为零不决定停止；未通过时持续反馈，达到调用方上限、取消或基础设施故障停止时保留真实状态。

原 SO、固定输入基准、独立预期及检查器位于模型可编辑范围之外。新增反例进入累计回归，每个新候选在声明范围内重跑；不能删除旧失败或改预期取得通过。恢复先核对当前源码、关联工程和写入者，避免并发覆盖；每轮完整 prompt、返回、事件、日志及实际检查依据可追溯。

## 第三阶段验收

以下用于 V0.3 整体完成检查，V0.31 仍按其独立 PLAN 验收，不提前勾选长期需求。

1. 从零生成链路在真实纯 native 与 JNI 目标上完成必要调查和运行；所选输入实际进入目标逻辑，环境假设明确，保存记录可重放。
2. 在至少一个与真实目标调查相关、边界明确的函数或逻辑入口上，由恢复源码构建候选 SO，并在独立模拟器中实际执行。开发 smoke 或原样本源码重建不替代这项验证。
3. 用实际错误候选或在候选草稿中引入明确语义错误，差分能够发现并定位真实差异；同一任务自动修复、重建，当前内容通过原用例和累计反例。
4. 提供固定种子、适用边界输入及选定的错误路径，报告实际执行用例和比较范围。执行失败、超时、环境缺口、检查器故障及空回复均不算普通通过。
5. 修改源码、产物或基准后，旧通过结论不再适用于当前内容；历史 Run 仍可核对。取消和恢复保留工作成果及失败经验，不重复启动在途写入者。
6. 交付源码、构建和复现说明与验证内容一致，列明剩余原实现依赖及未知项。有限用例相符只说明其观察范围内一致，不宣称全输入等价或整个 VM 已恢复。

开发回归使用轻量临时数据；真实模型、unidbg 和目标集成检查单独记录。本文只是计划，本次文档补充没有执行以上验收，也不改变 V0.31 的人工验收状态。

## 本阶段之外

完整 VM 指令语义建模、系统化去平坦化/MBA 求解、覆盖引导 fuzz、通用强制探索、全 SO 独立工程恢复及跨版本知识自动积累继续按路线图 D2–D4 推进。局部调查需要时可以使用并记录相关实验，不把全部去混淆或全 VM 恢复设为初步差分的前置。

本阶段不新增其他架构或运行后端，不扩建 trace/CFG/fuzz Web 面板。DG 0x1c07c 无完整 C 的缺口保留为后续调查目标，不能用单边运行结果宣称已解决，也不把一次性完整恢复该巨函数作为首个差分闭环的必要条件。
