# V0.4：差分闭环与分支触发

状态：草案，待 V0.3 验收后确认范围。

V0.3.5 实战（DG 真实字节码，2026-11-03）证实框架机制已就位：轮次按时完成、
诚实失败、缺口门禁、失败证据反馈闭环。剩余瓶颈是**缺基准真值**（Java 侧业务
回调如 `DroidGuard->g([F)V` 无法凭补环境宣称正确）和**路径覆盖靠单条输入**。
二者分别由本版本的差分闭环与分支触发解决。

## 前置（V0.3 收官 + V0.3.5 收尾）

1. **V0.3 验收口径修订**（重要，来自实测）：
   - 环境类缺口（system-service / field 等 OS 提供）必须清零
   - **应用类缺口**（APK 内业务回调，如 DroidGuard.g）允许以"记录在案的
     条件假设"保留——它是应用的一部分而非 OS 环境；没有 APK 时不可能
     诚实地补全。验收 = 环境类清零 + 应用类逐条记录假设与来源
2. 4 字节码验收跑（在途任务终态后执行）
3. V0.3.5 小收尾（约一天，见下）

## V0.3.5 收尾清单（并入本版本开工前）

- **模式协议对齐**：agent 实测自造 `conditional_environment` 而非模板的
  `probe`。runner 门禁不依赖模式名（missing_environment 兜底）所以没出事，
  但协议要改宽松：TASK.md 改为"非自然运行须标记非空 mode 并在观察中保留
  missing_environment"；runner 同步接受任意非空 mode 为探索标记
- **ProbeJni 采纳摩擦**：agent 没用模板探针类（自造等价物）。调查原因
  （复制路径不顺眼/不知存在），让 ENVIRONMENT.md 的指引更直接
- OPTIMIZATION.md 中"现在可做"与 shim 删除（1.3+3.2）顺手完成

## 版本目标

### 1. 候选构建与双边差分（D1 主体）

- 候选 C 源码（Recovery 产物）→ ARM64 .so 构建 → 与原 SO 在 unidbg
  双边执行同一用例，比对输出/副作用
- 差异 → 反例保存 → 自动反馈修复（Recovery 改源码 / Rehost 补环境）
- 契约与 Run 保存约定沿用 [DIFFERENTIAL_EXECUTION](../../future/DIFFERENTIAL_EXECUTION.md)

### 2. 分支触发（F0）

- 强制执行优先：unidbg hook 分支点翻转条件（VM dispatch 分支集中，定向）
- 字节码 fuzz 补充：按覆盖率保留变异
- 覆盖饱和停机：连续 N 次无新分支或预算耗尽
- 探索运行与自然运行永久区分（复用 V0.3.5 mode 机制）
- **fuzz 驱动入口已就位（2026-11-03）**：harness 的 request 协议——`input_file`
  喂固定用例、`{}`（零种子 `{0}`，单零字节）喂变异种子；变异器只改 request
  数据，harness 无需改动。observation 已记录 input 长度与 sha256，
  供覆盖率-输入关联。

### 3. 基准真值来源（差分的前提，需用户决策）

三选一或组合，**开工前确认**：
- a) 真机/沙箱录制：用户提供 DG 在真设备的输入输出对
- b) 原实现自比对：以 unidbg 原始 SO 运行为基准，验证候选等价（不依赖
  真机，但"正确"上限是原实现行为）
- c) 短片段范围收窄：选无 Java 回调的纯 native 段先闭环（VM_RECOVERY
  建议的最小闭环路径）

## 验收（草案）
