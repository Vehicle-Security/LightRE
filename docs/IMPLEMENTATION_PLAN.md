# LightRE 小步实现计划

本文维护能力引入顺序与版本入口。各小版本的范围和验收条件维护在其 PLAN，实际结果维护在 DELIVERY，命令/API 维护在 USAGE；完整文档分工见 [文档入口](README.md)。

本文规划交付步骤。V0.1 已作为基础版本提交，本轮人工验收反馈已落实；最终实现和现场记录以 [V0.1 milestone](milestones/v0.1/DELIVERY.md) 为准。V0.2 的自动初次还原与人工反馈已于 2026-11-01 通过用户人工验收，见 [V0.2 交付记录](milestones/v0.2/DELIVERY.md)与[确认范围](milestones/v0.2/PLAN.md)。代码调整和开发自测不推进产品版本。长期方向见 [设计文档](LLM_DECOMPILER_DESIGN.md)，功能需求见 [需求清单](REQUIREMENTS.md)。

当前已验收版本为 V0.2，基于 V0.1 增加自动初次还原与人工反馈；其余增量按反馈选择。Workspace 是外层分析根目录，每份 SO 使用自己的分析子目录、SQLite 与知识，具体约定见设计文档的“开发基线”。

按最新反馈，先交付 [V0.31：最小 unidbg harness 与任务循环](milestones/v0.31/PLAN.md)：用简单 Android ARM64 测试 SO 跑通整数调用、缓冲区读写、结果保存与独立重放；同时接入最小 Python loop，逐轮完整保存 Codex 返回，按 harness 实际检查结果反馈续做。DG 的 JNI 环境、minilua 的 Android SO 适配分别后移，先不承担候选编译、双边差分和语义自动修复。[V0.3](milestones/v0.3/PLAN.md) 保留为完整闭环的总体方案，不再一次性交付。V0.31 已开始开发，运行与修复入口见 [使用说明](milestones/v0.31/USAGE.md)，实际证据见 [交付记录](milestones/v0.31/DELIVERY.md)，尚待人工验收；V0.2 的验收状态保持不变。

当前动态路线已收敛为 ARM64 + unidbg。minilua 另建 Android ARM64 SO 与薄 C 测试接口，复用同一运行和差分流程；DG 按需补充 JNI。保留原 Linux 样本，当前不接入 Qiling 或其他架构，不建设多后端运行平台。

## 长期主线：自动完成源码工程

已确认以 [Goal Loop](GOAL_LOOP.md) 作为长时间自动化逆向的支柱：一次提交目标，由 Python 循环调用 `codex exec`，验证实际工程，未通过就携带具体失败继续，完成后交付可编译、可独立执行、可维护的源码。直接使用 CLI，不以 SDK、原生 goal 或 Stop hook 为前提。该能力尚未实现，不在已验收 V0.2 的交付范围内。

先以 V0.31 的固定测试 SO 接通运行、重放和 harness 修复循环，再由真实样本的运行、差分与反例修复牵引后续开发。外层循环和可靠续做随实际调用补齐，不以先完成整套执行基础设施作为接入 unidbg 的前提。Web 保持辅助定位。工具可逐项开发和验证，用户的一次完整还原目标不需要在各内部步骤反复确认。

VM 分析按 [语义恢复里程碑](VM_RECOVERY_MILESTONES.md) 推进：M0 可重放入口与边界、M1 取指、M2 解码、M3 dispatch、M4 指令语义、M5 逻辑控制流、M6 业务源码及差分交付。OLLVM 和 MBA 按各阶段的关键切片逐步处理，不要求先对整个解释器去混淆。先在真实入口打通 M0–M3，尽早用一个短片段贯穿后续业务闭环，再扩展范围。以下表格是执行与交付基础能力路线，与分析里程碑互相配合，不表示新的产品版本已经启动或通过验收。

| 顺序 | 最小实现及检查 |
| --- | --- |
| D1. 动态差分闭环 | 一个真实入口可重放，一个候选可构建并独立运行，输出差异能成为反例；最小循环将差异反馈给 Codex 修复并重跑 |
| D2. VM 定点调查与受控探索 | 用状态、内存及转移观测推进 M1–M3；对一个具体未知点引入有记录的强制执行，按需切片和化简 MBA |
| D3. 结构化字节码 fuzz | 对部分已理解的指令格式与上下文产生可执行变体，记录 VM 层面的新行为、语义差异与最小化反例 |
| D4. 扩大语义恢复与工程交付 | 以观测、反例和局部求解驱动 M4–M6，恢复选定入口业务源码，再扩大入口、路径和指令范围；完善长时间续做及独立导出 |

以上为后续能力规划，均未实现或验收；V0.2 已单独通过人工验收，不自动分配或启动新版本。D1–D4 是工具开发阶段，M0–M6 是单个目标的分析进展：工具可提前具备调查能力，并在具体样本需要时使用；二者不一一对应。现有 Goal Loop、源码交付与运行需求继续适用，具体机制以 Goal Loop 文档为准。

源码持续修改后的定位与预览按 [结构化标记和索引设计](SOURCE_NAVIGATION.md) 实现：固定前缀 JSON begin/end、稳定源码 ID、多对多来源关联、文件版本与字节范围、统一 revision 刷新。当前已完成结构化标记、ID 保留、词法解析、旧标记无损迁移与 Web 隐藏机器注释；多对多索引及版本刷新仍待实现，不以增加界面面板或人工认可作为前提。

函数身份与改名按 [实现前确认规则](SOURCE_NAVIGATION.md#实现前确认的身份规则) 和 [检查结果](SOURCE_NAVIGATION.md#实现前检查结果与交付边界) 收敛：当前原始函数继续直接使用 RVA，不增加第二套主键；局部变量不建立身份表。先在一对一链路补齐原始名/当前源码名、名称搜索与提示词，再补原始调用的地址绑定。跨函数改名须接通相关文件一致发布与源码引用检查后启用；多对多及无原始入口 helper 的 ID 分配后续按实际需要引入。此处仅整理设计和实施边界，不表示已开发，也不调整当前其他里程碑的交付范围。

完整定位能力必须包括 [地址定位约束](SOURCE_NAVIGATION.md#地址定位必须保持的约束)：多原始函数合并后，每个原始 RVA 仍可打开当前合并源码；后端校验旧来源的继承与发布连续性，失败保持旧结果。多对多虽可单独分步实现，但不能在缺少它时宣称已保证任意合并后的地址定位；无原始入口 helper 的分配仍可独立后移。

## V0.2 之后的能力引入时机

V0.2 生成未经执行验证的静态候选。D1 按小版本推进：V0.31 先用简单测试 SO 提供纯 native 调用及重放，并以 harness 修复接通原文保存、错误反馈和自动续跑；后续单独适配 DG 或 minilua 中一个目标，再接候选构建、比较及语义自动修复。不要求首个 harness 交付就承担 JNI、Lua 状态、全工程编译或 VM 解释；自动摘要和复杂记忆管理也不作为 loop 的前置。

### D1：unidbg 运行、差分与输入 fuzz

先适配一个真实入口的 harness，保存初始化、JNI 假设、输入及运行产物；候选尚不可执行时，原实现运行与观测仍可先进行。选择一个边界明确、相关状态可以准备的小函数或 VM 片段，补齐候选必要的接口与类型，构建 ARM64 SO，在独立实例中运行并比较声明输出和副作用。

用一个错误候选或实际语义差异验证反馈链路：保存反例，Codex 根据具体差异修改候选，再构建并重跑累计用例。循环至少保留明确任务与轮次、完整返回及检查记录、源码内容依据、取消和执行互斥；默认独立 exec，CLI 会话仅作可选优化。模拟 CLI 用于快速检查故障，不代替真实行为闭环。这是 D1 的完整目标，V0.31 只先实现其中的 harness 基础子集。

原实现可重复运行后即可对入口参数、缓冲区内容、长度及有含义的环境输入进行初步 fuzz，无需先理解字节码。保存种子、环境与首次差异，按实际能力增加覆盖反馈；比较双方之前确保输入处于声明范围且状态含义一致。已复现的原实现异常、候选差异和实验环境失败分别归类。D1 交付时能展示实际反例、修复及回归结果，不能仅展示两个进程都成功退出。

### D2：取指/dispatch 观测与强制执行

在调查 M1–M3 时引入定点读取、寄存器/内存状态、实际跳转目标和虚拟步骤边界观测。优先解决当前问题所需片段，不默认全程指令 trace；指令级信息按需保留原始范围，提供可定位的摘要。

当自然输入暂时无法到达需要调查的分支，且已掌握具体干预点与必要前态时，引入最小强制执行：修改一个条件、相关状态或外部返回值，观察目标区域的作用。无需等待完整解码器或完整 handler 映射，也无需先有可执行候选。尚不能说明目标前态是否相容时，结果只能作为带缺口的探索材料，不能当作有效指令语义或差分通过。

保存干预位置、前后值、初态、原始运行和重放材料。对潜在滚动密钥、解码阶段、栈及对象状态检查相容性；不能只改 PC/VPC。优先尝试生成自然可达输入，必要时使用局部约束求解并具体重放。强制路径覆盖与自然路径覆盖分开，修改原实现的结果不充当未干预业务行为基准。

MBA 规则化简与位向量检查从本阶段的实际瓶颈引入，例如取指地址、分派目标或分支条件；D1 已遇到同类阻碍时可提前使用。不要求先开发通用去混淆器或全程序符号执行。

### D3：字节码 fuzz 分层引入

原始执行环境可重复、能够识别变异字节实际进入 VM 后，可在 D2 做小范围原始字节变异，调查拒绝、解码和异常路径；此类实验不预设输入是合法虚拟程序，不能据此总结一般指令语义。

结构化字节码 fuzz 在 M2–M3 已理解的局部范围引入，不等待全部指令恢复。至少知道变异区域的指令边界、编码及长度约束、必要上下文，以及如何观测相应语义。对已理解的 opcode/操作数、短指令组合或分支目标进行变异，保持所需寄存器、栈、内存和终止条件。

若存在滚动密钥、完整性校验或状态相关编码，需按已知规则生成有效编码；若改在解码后注入，记录其干预性质与缺失的编码验证，不能混作自然有效字节码。状态规则尚不明确时，继续输入 fuzz、原始变异或受控探索，不用随机换密钥制造合法性。

语义 fuzz 的比较对象必须是同一变异虚拟程序：将原 VM 的结果与该程序的解码/步骤模型或对应生成的候选比较。不能修改原 VM 的字节码，却拿原始未变异业务候选作预期。没有对应模型时，实验用于发现新行为或异常，不称作语义差分通过。

保存基线与变异资源、种子、初态、编码上下文和结果；在限制执行步数与时间的运行器中执行。优先反馈新虚拟指令类别、逻辑边、状态转换及语义差异，避免仅因 native dispatcher 路径增多便宣称恢复进展。反例最小化需保持相关编码和状态约束，基础版本可以先人工/脚本缩减，再按需要自动化。

### D4：联合恢复与长时间运行

围绕累计缺口交替使用静态切片、自然执行、fuzz、受控强制执行和局部求解，扩展 handler 状态模型及逻辑 CFG；尽早让一个短片段贯穿 M4–M6，而不是等 D3 完成才开始业务还原。随后扩展调用链、共享状态、文件、类型与命名，在实际工程上完善续做、失败隔离和导出。

工具路线按上述依赖开发，实际任务按需要选用已有能力，不强制每个函数、每轮或每个样本依次运行全部工具。

## 交付原则

每次只完成一个能实际运行、能由人工验证的小增量。先把函数显示出来，让用户使用后提出下一步需求；逐步走向 LLM 还原和 unidbg 差分，不把完整系统作为第一次交付。

- 每次开始前写清本次新增行为和验收例子，只实现这个范围。
- 每次交付提供可复现的 Skill 聊天用语、真实样本、浏览地址、操作步骤和实际验证结果；底层命令留作开发排查资料，不要求用户手动执行。
- 无界面的自动化增量提供一次目标启动方式、产物路径、验证与恢复依据；无需为交付补建 Web 页面或浏览地址。
- 交付后停在可运行状态，用户可直接介入；不自动接着开发后续版本。
- 下一步根据用户反馈重新选定，需求变化时允许调整顺序或放弃尚未实现的方案。
- 只实现本次需要的数据字段、接口和文件。等确有使用场景再拆模块或补抽象。
- 原有功能持续可用；验证以实际行为为主，不为简单页面堆积测试设施。

P0/P1/P2 是长期需求分组，不是需要一次完成的交付包。没有必要实现全部 P0，才让用户打开第一个页面。

## 主线内可拆分的小增量

下表用于将 D1–D4 拆成可运行的小步，不再作为与主线无关的平行路线；按当前阶段需要选择，不要求全部先行完成。若某项仍过大，先拆到一个可演示的入口。

| 增量 | 最小可运行与验收例子 |
| --- | --- |
| 重新打开工作区 | 关闭再启动，从同一工作区读回一个函数及其候选；按实际需要引入最少 SQLite 记录 |
| 候选历史 | 为同一函数保存第二个不可变版本，页面可切换两份代码 |
| 知识深化 | 结合动态实验更新函数上下文，保留原始证据关联 |
| 跨版本公共知识 | 从已分析版本提炼一个有来源和适用条件的规律，用它设计新版本实验；新结果保存回新版本，公共总结据此更新，不继承旧版本的通过状态 |
| 一次原始运行 | 为一个样本建立可重复的 unidbg 入口，执行一次，保存输入、harness 和真实输出；JNI 缺口也有可续做记录 |
| 一条 Evidence | 将一次有用观察登记并关联函数，页面可定位原始 Run；失败观察同样能保存 |
| 候选构建与执行 | 一个候选编译为 ARM64 SO，在独立 unidbg 实例中执行一个固定用例，保存构建和运行结果 |
| 一次函数差分 | 同一用例双边执行，比较声明的返回值与输出，能展示一处真实差异或范围内通过 |
| 一个反例回归 | 固定失败用例，修复后重跑；新的错误候选不能沿用旧通过状态 |
| 多轮调查 | 一个评论任务内连续调查、实验、修正与比较，保存停止原因及未解决项 |

Ghidra 参考伪代码已用于 V0.2 静态候选；后续调用导航、组合验证、符号执行按真实调查需要加入，不作为 V0.31 harness 的前置条件。自动化逐步覆盖已经跑通的操作，不先建设完整策略或调度平台。

## 每次交付的最少记录

每次只报告：本次能做什么、可复现的聊天请求与实际 URL、一个真实操作例子、实际验证结果，以及本次尚未覆盖的范围。底层启动资料保留供 Agent 排查。提供可运行结果后留给用户体验，不自动继续实现整条路线。

实现计划随着体验反馈更新。需求清单保留长期条目，未做到的条目保持未验收，不为某个小版本宣布整个系统完成。
